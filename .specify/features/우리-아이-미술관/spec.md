## Overview

> 작은 손이 남긴 선이, 우리 가족의 한 장면으로.

### Problem Statement

아이는 매일같이 그림을 그리고 무언가를 만들지만, 가정에서는 그 작품을 오래 간직하고 다시 꺼내 보기 어렵다.

1. **보관 부담**: 종이 작품과 만들기 작품은 금방 쌓여 공간을 차지한다. 결국 버리거나 상자에 넣어 두고, 다시 찾아보지 않게 된다.
2. **맥락 유실**: 작품을 만들 때 아이가 한 말, 아이의 나이, 만든 날짜가 따로 기록되지 않는다. 시간이 지나면 "무엇을 왜 그렸는지"가 사라진다.
3. **공동 감상의 부재**: 작품이 흩어져 있으면 가족이 함께 앉아 보며 이야기를 나눌 계기가 생기지 않는다.
4. **정리 수고**: 사진을 찍어도 배경이 섞이고, 어떤 방식으로 보여 줄지 매번 고민해야 한다.

우리 아이 미술관은 휴대폰 사진 속 아이 작품을 찾아내 미술관의 작품으로 바꿔 거는 **가족용 미술관**이다. 모델을 새로 학습하지 않고 **공개 사전학습 모델을 이어 붙여** API 서버 뒤에서 서빙한다. 사진에서 작품을 분리하고(배경 분리), 무엇을 그렸는지 판정을 **제안**하고(제로샷 분류 + 관절 기하 규칙), 보호자가 확정하면 사람·캐릭터 그림은 원본 선을 리깅한 **움직이는 그림**으로, 움직이기 어려우면 **2.5D 입체 부조**로, 그것도 안 되면 **원본 액자**로 만든다. 어느 모델이 실패해도 **한 단계 낮춘 결과**가 돌아온다. 여기에 그날의 말과 제작 당시 나이를 함께 남겨, 가족이 함께 다시 본다. 기술은 기억을 꾸며내는 주체가 아니라 다시 꺼내 보는 수단이다.

### 처리 흐름

접수 → 배경 분리(M1) → 판정 제안(M2 제로샷 분류 + M3 관절 + M4 기하 규칙) → **보호자 확정** → 움직임(M3) / 2.5D 입체 부조(M5) / 원본 액자 생성(낮춤 체인) → 보호자 결과 확인·승인 → 이야기 입력(P0.5: 키워드 설명 초안, M6) → 전시.

다음은 서로 다른 것으로 구분한다. 사진 디지털화와 3D 복원은 다르다. 2.5D 입체 부조(평면 그림에 깊이를 더한 시차 효과)와 3D 조각(만들기 작품의 형상 재구성)은 다르다. 평면 그림에는 image-to-3D를 쓰지 않는다(보이지 않는 뒷면을 지어내므로 재창작 금지 원칙에 어긋난다). 디지털 영화 완성과 실제 아날로그 필름 제작도 다르다.

### Business Value

아래는 모두 **기대 혜택(가설)**이며, 검증 방법과 짝을 이룬다.

- **아이**: 자기 작품이 움직이거나 입체로 떠오르는 즐거움. 아이가 원본을 알아보는지, 스스로 다시 보고 싶어 하는지를 관찰한다. 발달 향상 효과는 주장하지 않는다.
- **보호자**: 사진만 올리면 작품 분리와 전시 방식 제안까지 받아 정리 수고가 준다. 등록부터 전시 완료까지의 시간, 판정 수정 횟수, 설명 초안 승인율(P0.5)로 확인한다.
- **성장한 아이**: 어린 시절의 작품·말·가족 이야기를 돌아보는 기록. 장기 목표이며 짧은 시연으로 입증하지 않는다.
- **서비스 팀**: 모델별 낮춤률과 인프라 실패를 분리해 개선할 모델을 고른다. 모델 교체는 매니페스트 승격·롤백으로 안전하게 한다.
- **외부 개발자(P0.5)**: 인증된 엔드포인트로 작품 분리·판정·2.5D·설명 기능을 조합해 쓸 수 있다. 연동 수요는 가설이다.
- **차별화 가설**: 개별 기능은 이미 시장에 있다(보관 앱, 그림 애니메이션 앱, 가상 갤러리). 차별점으로 가정하는 것은 "분리 → 판정 제안 → 움직임/입체/액자 → 설명 → 전시"로 이어지는 **조합**과, 실패해도 낮춘 결과가 돌아오는 **서빙 구조**다. 최초·유일, 흥미, 재방문, 지불 의향은 검증된 사실로 주장하지 않는다.

### Session 2026-09-28

- Q: 서비스 이름은? → A: "우리 아이 미술관"으로 바꾼다. 파일명·식별자에서는 공백 없이 `우리아이미술관`을 쓴다.
- Q: 모델을 새로 학습하는가? → A: 학습하지 않는다. 공개 사전학습 모델 7종(M1~M7, 그중 M4는 규칙)을 버전 고정해 이어 붙이고, API 서버 뒤 작업 계약 하나로 서빙한다. 모델마다 어댑터와 버전 매니페스트를 둔다.
- Q: 처리 경로는 누가 정하는가? → A: 시스템은 판정을 **제안까지만** 한다(M1 분리 → M2 제로샷 → M3 관절 → M4 기하 규칙). 제안은 문구로만 보여 주고 점수는 노출하지 않는다. 경로는 보호자 확정값으로 정한다. 제안값·확정값·수정 여부를 기록한다. v1.0의 "예/아니요" 질문을 대체한다.
- Q: 움직임이 안 되면? → A: 원본 액자로 바로 가지 않고 **2.5D 입체 부조**(M1 마스크 + M5 깊이)로 한 단계 낮춘다. 2.5D도 안 되면 원본 액자다. 낮춤 체인은 움직임 → 2.5D → 액자, 3D(P1) → 2.5D → 액자, 설명(P0.5) LLM 초안 → 템플릿 → 직접 입력으로 고정한다. 품질 미달은 재시도하지 않고 낮추며, 인프라 장애는 낮춤이 아니라 최대 3회 재시도 뒤 "처리하지 못함"이다.
- Q: 결과 원인은 어떻게 나누는가? → A: ① 보호자 선택 ② 모델 낮춤 ③ 보호자 전환 ④ 인프라 실패 ⑤ 결과 미도달의 5분류를 섞지 않는다.
- Q: 범위는? → A: P0(판정 제안·움직임·2.5D·액자·전시·삭제·모델별 지표·모델 평가·승격·API활용 메뉴) / P0.5(키워드 기반 작품 설명, 외부 모델 기능 엔드포인트) / P1(만들기 작품 3D 조각, 팀 서버 GPU 확인 후) / 후속으로 나눈다.
- Q: 서빙 방식은? → A: CPU 비전 워커(M1~M4, 비동기 큐) · GPU 워커(M5·M7, 전용 큐, 모델 상주. GPU가 없으면 M5는 CPU, M7은 비노출) · LLM 서버(M6, 짧은 동기 또는 스트리밍) 3종으로 나눈다. 모델 기능은 Python 가상환경 + uvicorn API로 제공하고(추가 요구 R3), API 서버는 'API활용' 메뉴를 갖춘다(추가 요구 R4).
- 유스케이스 통합 중 정한 결정(공통 기준 §11, D1~D14, 모두 `[추론]`)을 본문에 반영했다. 요지는 다음과 같다. 재시도는 단계 작업당 첫 시도 포함 최대 3회 시도이며, "처리하지 못함·결과 미도달"은 결과를 만드는 단계(움직임 렌더·깊이·부조·3D)에만 쓴다(D1). 재시도 소진 뒤 액자로 걸기는 보호자 전환이 아니다(D2). 전시 화면에는 낮춤·원인을 표시하지 않는다(D3). "삭제 중"은 과도 상태이며 취소된 단계 작업은 지표에서 뺀다(D4). 승격하면 직전 활성 버전이 롤백 후보가 된다(D5). LLM 초안과 템플릿 설명은 모두 "AI 작성" 표시(D6). 규칙 검사 전 문장은 보이지도 저장하지도 않는다(D7). 외부 호출 입력·결과는 워커 임시 영역에만 둔다(D8). M7은 외부에 열지 않는다(D9). 3D는 노출 설정으로 켠다(D10). 결정은 작품당 1회 반영(D11). 시험 호출은 P0.5(D12). 첫 결과 승인율 분모는 결과가 도달한 작품의 첫 결정(D14).

### Core Requirements (Mandatory)

#### FR-1: 아이 등록 (최소 수집)

**Description**: 보호자는 아이를 **별칭** 하나로만 등록한다. 실명, 생년월일, 출생연도는 받지 않고 저장하지도 않는다. 보호자 한 명이 여러 아이를 등록할 수 있다.

**Acceptance Criteria**:
- [ ] 아이 등록 화면에는 별칭 입력란만 있다. 실명·생년월일·출생연도 입력란은 없다
- [ ] 별칭은 같은 가족 안에서 서로 구분된다. 같은 가족 안에 같은 별칭을 두 번 등록하면 거절하고 이유를 안내한다
- [ ] 보호자는 아이를 2명 이상 등록하고, 작품을 올릴 때 어느 아이의 작품인지 고를 수 있다
- [ ] 별칭은 등록 후 수정할 수 있다
- [ ] 별칭은 작품 설명 생성(FR-27)과 외부 모델 기능(FR-28)의 입력으로 쓰이지 않는다

#### FR-2: 작품 사진 내구 접수

**Description**: 보호자는 휴대폰으로 찍었거나 기기에 저장된 작품 사진을 올린다. 시스템은 형식·용량·이미지 판독 가능 여부를 검사한다. 그다음 **원본, 작품 기록, 처리 작업 기록이 모두 저장에 성공한 경우에만** "접수 완료"로 응답하고, 분리·판정 단계 작업을 등록한다. 하나라도 실패하면 접수하지 않은 것으로 처리한다. 저장이 일부만 된 흔적도 남기지 않는다.

**Acceptance Criteria**:
- [ ] 허용 형식 밖의 파일, 용량 상한을 넘는 파일, 이미지로 판독되지 않는 파일은 접수 전에 거절한다. 거절 이유(형식/용량/판독 불가)를 보호자가 이해할 수 있는 말로 안내한다
- [ ] 원본·작품 기록·작업 기록 중 하나라도 저장에 실패하면 보호자에게 "접수되지 않음"을 알리고 다시 올리도록 안내한다. 이때 저장이 일부만 된 원본이나 기록이 남지 않는다
- [ ] 접수 완료 응답은 분리·판정 결과를 기다리지 않는다. 접수 완료 뒤 작품은 "판정 중"으로 넘어간다
- [ ] 접수 완료 응답을 받은 작품은 이후 서버가 재시작하거나 워커가 실패해도 사라지지 않고, 최종 상태(확인 대기, 처리하지 못함, 삭제 중 하나)에 도달한다
- [ ] 같은 올리기 요청이 네트워크 문제로 두 번 전송되어도 작품은 하나만 생긴다
- [ ] 원본은 올린 그대로 보존된다. 모든 모델은 원본을 읽기만 하며, 어떤 후속 처리도 원본을 덮어쓰거나 변형하지 않는다

#### FR-3: 판정 제안과 보호자 확정값에 따른 처리 경로 결정

**Description**: 접수 뒤 시스템은 판정 단계 작업에서 배경 분리(M1), 제로샷 종류 판정(M2), 관절 추정(M3), 관절 기하 규칙(M4)을 합쳐 **전시 방식 하나를 제안**한다. 보호자는 제안을 보고 전시 방식을 **확정**한다. 처리 경로는 제안이 아니라 **보호자 확정값**으로 정한다. 확정값은 움직임 / 2.5D 부조 / 원본 액자(P1에서 3D 조각 추가) 중 하나다.
- 움직임 확정 → 움직임 렌더(M3)를 시도하고, 품질 미달이면 낮춤 체인(FR-23)을 따른다
- 2.5D 부조 확정 → 깊이·부조(M5)를 시도하고, 품질 미달이면 원본 액자로 낮춘다
- 원본 액자 확정 → M3·M5를 부르지 않고 원본 액자를 결과로 만든다. 이 경로는 어떤 모델이 멈춰도 동작한다

**Acceptance Criteria**:
- [ ] 보호자가 전시 방식을 확정하기 전에는 움직임·2.5D·3D 처리가 시작되지 않는다. 작품 상태는 "확정 대기"로 보인다
- [ ] 보호자는 제안과 다른 전시 방식을 고를 수 있으며, 시스템은 이를 막거나 경고로 되묻지 않는다
- [ ] 원본 액자로 확정한 작품은 M3 움직임 렌더와 M5를 한 번도 거치지 않는다. 결과 원인은 "보호자 선택"으로 기록된다
- [ ] 2.5D 부조로 확정한 작품은 M3 움직임 렌더를 거치지 않는다. 결과 원인은 "보호자 선택"으로 기록된다
- [ ] M3·M5가 모두 멈춘 상태에서도 원본 액자로 확정한 작품은 확정부터 확인 대기까지 정상 진행된다
- [ ] 제안이 늦어지거나 판정 단계가 실패해도 보호자는 제안 없이 직접 확정할 수 있다 [추론]
- [ ] 제안값, 확정값, 수정 여부(제안과 다르게 골랐는지)가 작품에 기록된다(FR-21)
- [ ] P1 3D 조각은 FR-29의 조건을 충족하기 전에는 확정 선택지에 나타나지 않는다

#### FR-4: 백그라운드 처리와 상태 조회

**Description**: 오래 걸리는 처리는 올리기·확정 요청과 분리해 단계 작업으로 백그라운드에서 진행한다. 보호자는 기다리지 않고 화면을 떠날 수 있다. 나중에 작품별 진행 상태와 단계별 진행을 확인할 수 있다.

**Acceptance Criteria**:
- [ ] 접수 완료 응답과 확정 응답은 모델 처리가 끝나기를 기다리지 않는다
- [ ] 보호자는 작품별로 다음 상태를 볼 수 있다: 접수됨 → 판정 중 → 확정 대기 → 처리 중 → 확인 대기 → 승인됨 → 전시 중(필수 이야기 입력 뒤). 종료 상태로 처리하지 못함, 삭제 중이 있다
- [ ] 작품 상세에서 단계 작업(분리·판정·움직임 렌더·깊이·부조, P0.5 설명, P1 3D)별 진행과 낮춤 여부가 보인다. 모델 점수나 오류 원문은 보이지 않는다
- [ ] 같은 단계 작업은 동시에 두 워커가 중복 처리하지 않는다. 워커가 중간에 멈추면 정해진 시간 뒤 다른 워커가 이어받는다
- [ ] 처리 중인 작품의 상태가 바뀌면, 보호자가 다음에 작품 목록을 열 때 바뀐 상태가 보인다

#### FR-5: 결과 종류와 낮춤·인프라 실패의 분리

**Description**: 결과 종류는 **움직임 / 2.5D 부조 / 원본 액자 / (P1) 3D 조각**의 4종이다. 결과에 이른 원인은 아래 5분류로 기록하고 서로 섞지 않는다. 특히 **모델 품질 미달에 따른 낮춤**과 **인프라 장애**는 다르게 처리한다.

| 원인 분류 | 조건 | 보호자에게 보이는 것 | 기록 |
|------|------|------------------|------|
| ① 보호자 선택 | 확정 시 2.5D 또는 원본 액자를 고름 | 고른 결과의 미리보기 | 결과 종류 + 원인 = 보호자 선택 |
| ② 모델 낮춤 | 모델은 실행됐지만 결과가 품질 기준에 못 미쳐 한 단계 낮춤 | 낮춘 결과의 미리보기와 "움직임을 만들 수 없어 입체 부조로 준비했어요" 같은 안내 [추론 문구] | 결과 종류 + 원인 = 모델 낮춤 + 어느 단계에서 어디로 |
| ③ 보호자 전환 | 결과 확인 시 낮춘 결과나 원본 액자로 바꿈 | 바꾼 결과 | 최종 결과 종류 + 원인 = 보호자 전환 |
| ④ 인프라 실패 | 엔진 다운·시간 초과·저장소·DB·모델 미준비 | 재시도 중에는 "처리 중" | 오류 분류 + 시도 횟수 |
| ⑤ 결과 미도달 | 결과를 만드는 단계(움직임 렌더·깊이·부조·3D)에서 인프라 재시도를 다 씀(첫 시도 포함 최대 3회 시도) | "처리하지 못했어요" 안내와 선택지(원본 액자로 걸기 / 다시 찍기) | 상태 = 처리하지 못함, 결과 미도달 1건 |

**Acceptance Criteria**:
- [ ] 결과 종류는 움직임, 2.5D 부조, 원본 액자, (P1) 3D 조각 중 하나로 기록된다
- [ ] 인프라 장애(엔진 다운·시간 초과·저장소·DB·모델 미준비)는 절대 "모델 낮춤"으로 바꿔 처리하지 않는다. 같은 단계 작업을 첫 시도 포함 최대 3회 시도하고, 결과를 만드는 단계에서 다 쓰면 "처리하지 못함"으로 알린다
- [ ] "처리하지 못함"과 "결과 미도달"은 결과를 만드는 단계(움직임 렌더·깊이·부조·3D)에만 쓴다. 분리·판정·설명 단계의 재시도 소진은 인프라 실패로만 집계하고, 각 FR(FR-20, FR-21, FR-27)의 규칙을 따른다 [추론 — 통합 결정 D1]
- [ ] 모델 품질 미달은 재시도하지 않고 곧바로 낮춤 체인(FR-23)으로 한 단계 낮춘다
- [ ] 재시도를 다 쓴 건은 "결과 미도달"로 집계된다. 목표는 0이다
- [ ] 단계 작업마다 모델 ID, 모델 버전, 상태, 시도 횟수, 처리 시간, 낮춤 원인 또는 오류 분류, 진단 이유(정해진 코드), 모델 점수(기록용)가 남는다
- [ ] 모델 점수는 기록만 하고 자동 전시, 승인, 확정의 근거로 쓰지 않는다(집 그림이 사람 점수 0.946으로 잡힌 사례 때문)
- [ ] 5가지 원인 분류는 한 작품에서 서로 다른 필드로 남아, 한 분류가 다른 분류로 집계되지 않는다

#### FR-6: 보호자 결과 확인 (승인 전 비전시)

**Description**: 모든 결과는 보호자가 확인해야만 전시된다. 확인 대기 상태의 작품에서 보호자가 고를 수 있는 것은 다음과 같다.

| 선택지 | 뜻 | 기록 |
|--------|----|------|
| **좋아요** | 보여 준 결과를 그대로 승인 | 첫 결과 승인 |
| **낮춘 결과로 걸기**(해당 시) | 움직임 대신 2.5D 부조로, 또는 (P1) 3D 대신 2.5D 부조로 전시 | 보호자 전환 |
| **액자로 걸기** | 원본 액자로 전시 | 보호자 전환(이미 액자 결과면 좋아요와 같다 [추론]) |
| **다시 찍기** | 이 건을 닫고 새 사진을 새 작품으로 접수 | 다시 찍기로 닫힘 |

"처리하지 못함" 상태의 작품에는 **액자로 걸기**(원본은 저장돼 있으므로 모델 없이 원본 액자로 전시) / **다시 찍기**만 보인다. 이때 액자로 걸기의 결정은 원본 액자이지만, 원인은 인프라 실패·결과 미도달로 유지하고 보호자 전환으로 세지 않는다 [추론 — 통합 결정 D2].

**Acceptance Criteria**:
- [ ] 결정은 작품당 한 번만 반영된다. 같은 결정 요청이 중복으로 오면 첫 결정을 유지한다 [추론 — 통합 결정 D11]
- [ ] "처리하지 못함" 뒤의 액자로 걸기는 보호자 전환으로 집계되지 않고, 첫 결과 승인율의 분모에서 빠진다 [추론 — 통합 결정 D2]
- [ ] 승인하지 않은 작품(확정 대기·처리 중·확인 대기·처리하지 못함·다시 찍기로 닫힘)은 가족 전시 화면 어디에도 나타나지 않는다
- [ ] "낮춘 결과로 걸기"는 보여 준 결과보다 낮은 단계의 결과가 체인에 있을 때만 보인다. 2.5D 결과가 아직 없으면 이때 깊이·부조 단계 작업을 등록하고, 결과가 나오면 다시 확인 대기로 돌아온다. 이것은 다른 결과 종류를 새로 만드는 것이므로 "같은 결과 재생성 금지"에 걸리지 않으며, 처음 결과는 보관한다 [추론 — 통합 결정 D11]
- [ ] "액자로 걸기"를 고르면 원본을 액자로 전시한다. 이미 만든 움직임·2.5D 결과는 전시하지 않는다
- [ ] 결과 확인에서 바꾼 선택은 "보호자 전환"으로 기록되고, 확정 시의 "보호자 선택"이나 "모델 낮춤"과 섞이지 않는다
- [ ] "다시 찍기"를 고르면 해당 건이 닫히고 새 올리기가 시작된다. 새 사진은 **새 작품·새 작업**으로 접수되며 이전 원본을 덮어쓰지 않는다. 이전 건은 삭제 규칙(FR-10)을 따른다
- [ ] 결과물은 처음 만든 것을 보관하고, 같은 원본으로 같은 결과 종류를 다시 만들지 않는다
- [ ] 결과 화면에 모델 점수는 보이지 않는다. 낮춘 결과이면 낮춘 사실이 보인다(FR-23)

#### FR-7: 이야기 직접 입력

**Description**: 보호자는 작품마다 **제목, 제작일, 제작 당시 연령**을 입력하고, 원하면 **아이의 한마디**를 덧붙인다. 입력한 말은 그대로 저장하고 그대로 보여 준다. 시스템이 아이의 한마디를 만들거나, 고치거나, 감정을 해석하지 않는다. P0.5의 AI 작품 설명(FR-27)은 아이의 한마디와 다른 필드에 저장한다.

**Acceptance Criteria**:
- [ ] 제목, 제작일, 제작 당시 연령을 모두 채워야 전시할 수 있다. 아이의 한마디는 비워도 된다
- [ ] 제작일은 오늘보다 뒤의 날짜일 수 없다. 제작 당시 연령은 0~18 범위의 정수(만 나이, 세)로만 받는다
- [ ] 아이의 한마디는 입력한 글자 그대로 저장되고 표시된다(자동 요약·교정·감정 태그 없음)
- [ ] 아이의 한마디와 AI 작품 설명은 저장 필드와 화면 영역이 분리되어 있다
- [ ] 이야기는 보호자 확인 전후 언제든 입력하고 수정할 수 있다. 수정 내용은 전시 화면에 곧바로 반영된다
- [ ] 이야기 입력은 결과 종류와 무관하다. 움직임·2.5D·액자·(P1) 3D 모두 같은 항목을 가진다

#### FR-8: 가족용 전시

**Description**: 가족은 승인되고 필수 이야기가 채워진 작품만 모인 전시 화면에서 작품을 한 점씩 골라 감상한다. 작품과 아이의 실제 말이 먼저 보이게 한다.

**Acceptance Criteria**:
- [ ] 전시 화면은 아이별로 나뉜다. 한 아이 안에서는 제작 당시 연령별로 묶이고, 묶음 안에서는 제작일 순서로 정렬된다
- [ ] 작품을 고르면 결과(움직임, 2.5D 부조, 원본 액자, P1 3D 조각)와 함께 제목, 제작일, 제작 당시 연령, 아이의 한마디가 보인다
- [ ] 움직임·2.5D·(P1) 3D 결과에서도 원본 사진을 볼 수 있다
- [ ] 움직임 재생, 2.5D 시차 효과, (P1) 3D 회전은 보호자가 고를 때만 동작하고, 멈출 수 있다. 다음 작품으로 저절로 넘어가거나 끝없이 이어지는 피드는 없다
- [ ] 원본 액자와 2.5D 부조는 움직이는 작품과 같은 크기와 대우로 전시되며, "실패"나 "대체" 같은 표시를 붙이지 않는다. 점수나 비교 표시도 없다
- [ ] 전시 화면에는 낮춤 원인과 결과 원인 분류를 표시하지 않는다. 낮춤 표시는 진행 확인과 결과 확인 화면에서만 한다 [추론 — 통합 결정 D3]
- [ ] (P1) 3D 노출 설정이 꺼져 있으면 3D 결과는 원본 액자로 보인다. 저장된 3D 결과를 감상하는 데에는 GPU가 필요 없다 [추론 — 통합 결정 D10]
- [ ] (P0.5) 승인된 AI 작품 설명은 "AI 작성" 표시와 함께 아이의 한마디와 분리된 영역에 보인다
- [ ] 과도한 필터나 꾸밈 효과, 발달 점수, 아이 간 비교 표시는 없다
- [ ] 보호자는 제목이나 제작일로 특정 작품을 다시 찾을 수 있다
- [ ] 움직이는 작품과 2.5D 결과를 전시에 싣는 파일 형식은 정해져 있다 [NEEDS CLARIFICATION: U9 — 움직이는 작품·2.5D 결과의 서비스 파일 형식(GIF / MP4 / 깊이맵+셰이더 등)은?]

#### FR-9: 가족 단위 접근 권한

**Description**: 작품, 이야기, 작품 설명, 아이 정보는 해당 가족만 볼 수 있다. 팀원(운영자·평가 담당·연동 개발)과 외부 클라이언트는 가족 데이터에 접근하지 못한다. 가족 구성원의 접근 범위는 다음과 같다. [NEEDS CLARIFICATION: U1 — P0에서 한 가족 공간에 접근하는 계정 모델은? (a) 보호자 계정 1개만 두고, 공동 감상은 같은 화면을 함께 보는 방식 / (b) 공동 보호자 계정을 초대해 같은 권한으로 관리 / (c) 관리 보호자 1명 + 감상 전용 가족 초대]

**Acceptance Criteria**:
- [ ] 다른 가족의 작품·원본·마스크·결과·이야기·설명은 목록, 상세, 직접 주소 입력 어떤 경로로도 볼 수 없다
- [ ] 로그인하지 않은 사용자는 어떤 작품도 볼 수 없다
- [ ] 서비스 운영자, 평가 담당 팀원, 연동 개발 팀원은 운영 화면·평가 화면·'API활용' 메뉴에서 가족의 원본·결과 이미지와 이야기를 볼 수 없다
- [ ] 팀원 역할(운영자·평가 담당·연동 개발)은 서로 분리되어, 역할에 없는 기능(예: 운영자의 모델 승격)은 쓸 수 없다
- [ ] 외부 클라이언트의 API 키로는 가족 데이터 경로(작품·전시)에 접근할 수 없다
- [ ] 작품 삭제와 아이 삭제는 보호자만 할 수 있다

#### FR-10: 삭제와 실행 중 취소

**Description**: 보호자는 작품 하나 또는 아이 한 명(그 아이의 모든 작품 포함)을 삭제할 수 있다. 시스템은 새 단계 작업을 막고, 진행 중인 모든 단계 작업이 끝났거나 취소됐음을 확인한다. 그다음 원본, 작품 마스크, 깊이 결과, 중간 결과, 최종 결과, 작품 설명, (P1) GLB, 임시 파일을 지운다. 작업 기록에서는 작품과의 연결, 저장 위치, 자유 입력(제목·한마디·키워드 등)을 제거하고 집계용 필드만 남긴다.

**Acceptance Criteria**:
- [ ] 삭제를 요청하면 해당 작품은 곧바로 전시와 목록에서 사라진다. 그 작품의 새 단계 작업은 시작되지 않는다
- [ ] "삭제 중"은 삭제 절차가 도는 동안의 과도 상태다. 이 상태의 작품에는 확정·결과 결정·이야기·설명 요청을 받지 않고, 워커 이어받기 대상에서 뺀다. 취소된 단계 작업은 "취소"로 분류해 서빙 지표에서 뺀다 [추론 — 통합 결정 D4]
- [ ] 처리 중인 단계 작업이 있으면(CPU 비전·GPU·LLM 어느 서빙이든) 취소한다. 모든 단계 작업이 멈춘 것을 확인한 뒤에 파일을 지운다. 취소 이후 결과 파일이 새로 생기지 않는다
- [ ] 삭제가 끝나면 원본, 마스크, 깊이 결과, 중간·최종 결과, 작품 설명(초안·승인본), (P1) GLB, 임시 파일이 모두 남아 있지 않다
- [ ] 삭제 후 남는 작업 기록에는 작품·아이와의 연결, 저장 위치, 자유 입력이 없고 집계 필드(단계, 모델 ID·버전, 결과 종류, 원인 분류, 오류 분류, 단계별 시간, 시도 횟수)만 있다
- [ ] 삭제 도중 일부가 실패하면 삭제를 자동으로 다시 시도한다. 끝내 완료되지 않은 건은 운영자에게 "삭제 미완료"로 집계되어 보인다(이미지와 식별 정보는 제외)
- [ ] 아이를 삭제하면 그 아이의 모든 작품에 위 규칙이 적용된다
- [ ] 다시 찍기로 닫힌 이전 작품도 같은 삭제 규칙을 따른다
- [ ] 백업에 남는 사본의 보존·삭제는 P0 범위 밖이며, 운영 전에 결정할 항목으로 명시한다 [NEEDS CLARIFICATION: U15 — 백업 사본 보존·삭제 정책은?]

#### FR-11: 임시 파일과 중간 결과 정리

**Description**: 단계 작업 중에 생긴 임시 파일은 단계가 끝나면(성공, 모델 낮춤, 처리하지 못함, 취소 모두) 지운다. 다른 단계가 재사용하는 중간 결과(M1 마스크, M3 관절, M2 태그)는 작품 기록에 연결해 보관하고, 작품이 삭제될 때 함께 지운다. 비정상 종료로 남은 임시 파일은 주기적으로 정리한다.

**Acceptance Criteria**:
- [ ] 끝난 단계 작업의 임시 파일은 정해진 시간 안에 남아 있지 않다
- [ ] 재사용 대상 중간 결과(마스크·관절·태그)는 작품에 연결된 것만 남고, 연결 없는 중간 결과는 정리 주기에 지워진다
- [ ] 워커(CPU 비전·GPU·LLM)가 비정상 종료한 뒤 남은 임시 파일은 다음 정리 주기에 지워진다

#### FR-12: 서비스 생존·준비 상태 확인 (모델별 준비)

**Description**: 운영자는 서비스가 살아 있는지(생존, `/live`)와 작품을 받아 처리할 준비가 됐는지(준비, `/ready`)를 따로 확인할 수 있다. 준비 상태는 **모델별**로 표시한다. 한 모델이 멈춰도 그 모델이 필요 없는 경로는 계속 동작한다.

**Acceptance Criteria**:
- [ ] 생존 확인은 API 서버 프로세스가 응답하는지만 알려 준다
- [ ] 준비 확인은 원본·결과 저장소, 작품·작업 기록 저장소, 작업 큐 중 하나라도 쓸 수 없으면 "준비 안 됨"을 알린다
- [ ] 준비 확인은 M1~M6(P1에서 M7)의 준비 상태와 활성 버전을 모델별로 따로 표시한다. M4는 규칙이므로 판정 워커의 준비에 포함한다 [추론]
- [ ] M3만 멈춘 경우 움직임 경로는 인프라 재시도 규칙을 따르고, 접수·판정 확정·2.5D·원본 액자 경로는 계속 동작한다
- [ ] M5만 멈춘 경우 2.5D 경로는 인프라 재시도 규칙을 따르고, 움직임·원본 액자 경로는 계속 동작한다
- [ ] (P0.5) M6만 멈춘 경우 설명 단계는 재시도 규칙을 따르고, 소진되면 보호자가 "템플릿으로 받기 / 나중에 다시 / 직접 쓰기"를 고른다(FR-27). 다른 경로는 영향이 없다 [추론 — 통합 결정 D1]
- [ ] 모델 미준비로 실행하지 못한 단계는 오류 분류 "모델 미준비"로 기록되고, 모델 낮춤으로 집계되지 않는다

#### FR-13: 서빙 지표

**Description**: 운영자는 아래 서빙 지표를 이미지나 식별 정보 없이 볼 수 있다. 지표는 **정의와 검증 계획**이며 달성 실적이 아니다.

| 지표 | 정의 |
|------|------|
| 첫 결과 승인율 | 좋아요 ÷ 결과 확인 건(결과가 도달한 작품의 첫 결정. "처리하지 못함" 뒤의 결정은 제외) [통합 결정 D2·D14] |
| 판정 수정률 | 보호자가 제안과 다르게 확정한 건 ÷ 제안 제시 건(제안 전 직접 확정 건은 제외) [통합 결정 D14] |
| 모델별 낮춤률 | 움직임→2.5D, 2.5D→액자, 설명→템플릿(P0.5), 3D→2.5D(P1) 건 ÷ 해당 모델 시도 |
| 설명 규칙 검사 실패율 (P0.5) | 규칙 검사를 통과하지 못한 초안 ÷ 생성된 초안 [추론 — 분모 정의] |
| 모델별 처리 시간 p95 | 단계 작업의 시작부터 종료까지 걸린 시간의 95백분위, 모델별 |
| 재시도율 | 인프라 재시도가 1회 이상 발생한 단계 작업 ÷ 해당 모델 시도 |
| 큐 적체 | 서빙군별(CPU 비전·GPU·LLM) 대기 중인 단계 작업 수와 가장 오래 기다린 시간 |
| 결과 미도달 수 | 결과를 만드는 단계에서 인프라 재시도를 다 써 "처리하지 못함"이 된 건. 목표 0 |
| 삭제 미완료 수 | 자동 재시도 뒤에도 삭제가 끝나지 않은 건 |

**Acceptance Criteria**:
- [ ] 위 지표를 기간별로 볼 수 있다. 모델별 지표는 모델 ID와 버전으로 나눠 볼 수 있다(FR-26)
- [ ] 지표 계산에서 보호자 선택, 모델 낮춤, 보호자 전환, 인프라 실패, 결과 미도달이 서로 다른 항목으로 집계된다. 삭제로 취소된 단계 작업은 지표에서 뺀다
- [ ] 결과 미도달 건은 요청 번호로 개별 추적할 수 있다(이미지·저장 위치·자유 입력 제외)
- [ ] 지표 화면과 지표 데이터에는 이미지, 저장 위치, 작품 번호, 별칭, 제목, 한마디, 키워드가 없다
- [ ] 지표에 목표값을 붙일 때는 "검증 목표"로 표시하고 실적처럼 보고하지 않는다

#### FR-14: 아동 정보 보호 원칙

**Description**: 아동의 그림과 사진에는 이름, 유치원, 얼굴이 담길 수 있으므로, 이를 전제로 보호한다. 여러 모델과 외부 엔드포인트를 두더라도 아이의 데이터는 서비스 밖으로 나가지 않는다.

**Acceptance Criteria**:
- [ ] 운영 로그에는 이미지, 저장 위치 키, 사용자가 입력한 자유 텍스트, 가공되지 않은 오류 원문을 남기지 않는다. 오류는 정해진 분류 코드와 요청 번호로만 남긴다
- [ ] 얼굴 인식 기능이 없다
- [ ] 올린 사진과 결과물을 모델 학습이나 다른 목적에 재사용하지 않는다
- [ ] 가족의 기록을 외부 업체나 외부 모델 API로 자동 전달하지 않는다
- [ ] 작품 설명 생성에 외부 LLM API를 쓰지 않는다. 과정 제공 LLM은 데이터 처리 조건을 확인한 뒤에만 쓴다(FR-27)
- [ ] 설명 생성 입력에는 이미지와 아이 이름(별칭 포함)을 넣지 않는다
- [ ] 모델 런타임(TorchServe, Ollama 등)의 포트와 관리 기능은 외부 네트워크에서 직접 접근할 수 없다

#### FR-15: 자원 상한

**Description**: 과소비와 장애 전파를 막기 위해 처리 자원에 상한을 둔다. 모델별 상한은 FR-25에서 정한다.

**Acceptance Criteria**:
- [ ] 파일 용량 상한, 서빙군·모델별 동시 처리 수 상한, 단계 작업당 처리 시간 상한, 인프라 재시도 횟수 상한(첫 시도 포함 최대 3회 시도)이 정해져 있다. 상한을 넘으면 정해진 방식(거절, 대기, 시간 초과)으로 처리된다
- [ ] 처리 시간 상한을 넘긴 단계 작업은 "시간 초과"로 분류되어 재시도 규칙을 따른다. 모델 낮춤으로 집계되지 않는다
- [ ] 동시 처리 상한에 도달하면 새 단계 작업은 거절되지 않고 대기열에서 순서를 기다린다
- [ ] 움직임 렌더(M3)의 처리 시간 상한은 기본값 10분이다. 다른 모델의 상한은 재현 시험 뒤 정한다 [NEEDS CLARIFICATION: U6 — M3 외 모델별 시간 상한·동시 처리 수·처리 시간은? 현재 자료 없음]

### Core Requirements — 모델 조합·서빙 (v2.0 추가)

#### FR-20: 배경·작품 분리 (M1)

**Description**: 접수된 사진에서 배경(책상, 바닥 등)과 작품을 분리해 **작품 마스크와 컷아웃**을 만든다. 이 마스크는 판정 제안의 입력이자 2.5D 부조 마스크의 기본 출처다. 원본은 읽기만 한다.

**Acceptance Criteria**:
- [ ] 접수된 모든 작품에 분리 단계 작업이 먼저 실행되고, 결과 마스크·컷아웃은 원본과 별도로 저장된다
- [ ] 분리 결과가 품질 기준에 못 미치면 재시도하지 않고 "분리 품질 미달"로 기록한다. 이때 판정 제안은 계속 진행하며, 이 작품은 2.5D를 건너뛴다(FR-22)
- [ ] 분리 단계의 인프라 장애는 재시도 규칙(첫 시도 포함 최대 3회 시도)을 따르고, 모델 낮춤으로 집계되지 않는다. 소진되면 마스크 없음으로 두고 판정을 계속하며, 인프라 실패로만 집계한다. 결과 미도달로 세지 않는다 [추론 — 통합 결정 D1을 분리 단계에 적용]
- [ ] 분리 결과는 모델 ID·버전과 함께 단계 작업에 기록된다
- [ ] 분리 품질 기준은 평가 묶음 측정 뒤 정한다(U5, FR-17)

#### FR-21: 판정 제안과 보호자 확정·수정 기록 (M2·M4, 점수 비노출)

**Description**: 판정 단계 작업은 M1 분리 결과, M2 제로샷 종류 판정("사람 그림 / 동물 / 집 / 사물"), M3 관절 추정, M4 관절 기하 규칙(팔다리 길이·좌우 대칭·몸통 비율)을 합쳐 전시 방식을 **제안까지만** 한다. 제안은 문구로만 보여 준다. 예: "움직일 수 있을 것 같아요" / "입체 부조가 어울려요" / "액자로 거는 것을 추천해요" [추론 문구]. 보호자는 제안을 보고 확정한다(FR-3).

**Acceptance Criteria**:
- [ ] 제안 화면에는 제안 문구와 선택지만 있고 모델 점수, 확률, 순위는 보이지 않는다
- [ ] 엔진(M3)의 사람 점수 단독으로 움직임을 제안하지 않는다. 움직임 제안에는 M2 종류 판정과 M4 기하 규칙이 함께 반영된다
- [ ] 제안과 다른 선택을 막지 않는다. 제안값, 확정값, 수정 여부가 기록되어 판정 수정률(FR-13)의 원천이 된다
- [ ] 제안이 늦거나 판정 단계가 실패해도 보호자는 직접 확정할 수 있다. 판정 단계의 재시도가 소진되면 작품은 "확정 대기"로 머물고, 인프라 실패로만 집계되며 결과 미도달로 세지 않는다. 제안값은 "제안 없음"으로 기록되고, 판정 수정률의 분모에서 빠진다 [추론 — 통합 결정 D1·D14]
- [ ] M2 태그는 작품 기록에 남겨 설명 키워드 후보(FR-27)로 쓸 수 있게 한다. 태그는 보호자 화면에 판정 근거로 노출하지 않는다 [추론]
- [ ] M3 관절 결과는 판정과 움직임 렌더가 함께 쓰며, 움직임으로 확정하면 다시 추정하지 않는다 [추론]
- [ ] 제안 문구와 제안 지연 시 화면이 정해져 있다 [NEEDS CLARIFICATION: U10 — 판정 제안 문구 확정과, 제안이 늦을 때 보호자에게 보일 화면(기다리기 / 바로 직접 고르기)은?]

#### FR-22: 2.5D 입체 부조 생성 (M5, 마스크 출처 규칙)

**Description**: 작품 마스크와 깊이 추정(M5, Depth Anything V2 Small)을 합쳐 도톰하게 떠오르는 **2.5D 입체 부조**를 만든다. 평면 그림의 선과 색은 그대로 두고 시차 효과만 더한다. 2.5D는 보호자가 확정으로 고르거나, 움직임·(P1) 3D에서 한 단계 낮출 때 만든다.

**Acceptance Criteria**:
- [ ] 2.5D 마스크의 기본 출처는 M1 분리 결과다. 다른 마스크를 새로 추정하지 않는다
- [ ] M1이 품질 미달이면 2.5D를 건너뛰고 원본 사진 전체를 액자로 건다. 이 낮춤은 "모델 낮춤(분리 품질 미달 → 액자)"으로 기록된다
- [ ] 사람을 찾지 못한 그림(M3 인물 미검출)도 M1 마스크가 있으면 2.5D를 만들 수 있다
- [ ] 깊이 결과가 품질 기준에 못 미치면 재시도하지 않고 원본 액자로 낮춘다
- [ ] 2.5D 결과는 원본의 선과 색을 바꾸지 않는다. 보이지 않는 면을 지어내지 않는다
- [ ] GPU가 없으면 M5는 CPU에서 실행되고, 이 경우에도 같은 결과 계약을 지킨다(처리 시간은 미측정, U2·U6)
- [ ] 2.5D 결과의 서비스 파일 형식은 U9에서 정한다

#### FR-23: 낮춤 체인과 원인 기록·표시

**Description**: 품질이 모자라면 재시도하지 않고 **한 단계 낮춘 결과**를 돌려준다. 낮춤 체인은 아래로 고정한다. 낮춘 사실은 숨기지 않고 기록·표시한다. 실패를 성공처럼 꾸미지 않는다.
- 움직임 → 2.5D 부조 → 원본 액자
- (P1) 3D 조각 → 2.5D 부조 → 원본 액자
- (P0.5) 설명: LLM 초안 → 템플릿 설명 → 보호자 직접 입력

**Acceptance Criteria**:
- [ ] 체인 밖으로 건너뛰지 않는다. 움직임 품질 미달은 먼저 2.5D를 시도하고, 2.5D도 품질 미달이거나 M1 마스크가 없을 때만 원본 액자가 된다
- [ ] 원본 액자는 모델 없이 만들어지므로 체인의 끝에서 항상 결과가 돌아온다
- [ ] 낮춤이 일어날 때마다 "어느 단계에서 어디로"(예: 움직임 → 2.5D, 원인 코드 인물 미검출)가 단계 작업에 기록된다
- [ ] 보호자 결과 화면에 낮춘 사실이 짧은 문구로 보인다. 전시 화면에는 낮춤 표시를 붙이지 않는다(FR-8)
- [ ] 인프라 장애는 낮춤 체인을 타지 않는다(FR-5)
- [ ] 모델별 품질 기준(낮춤 조건)은 평가 묶음 측정 뒤 정한다 [NEEDS CLARIFICATION: U5 — 모델별 품질 임계값(분리·판정·관절·깊이·설명 규칙 검사)과 승격 기준은? 평가 묶음 1차 측정 뒤 결정]

#### FR-24: 모델 어댑터·버전 매니페스트·평가 후 승격·롤백

**Description**: 모델마다 어댑터를 두어 API 서버가 모델을 직접 import하지 않게 한다. 모델마다 **버전 매니페스트**(모델 ID, 가중치 SHA-256, 런타임, 이미지 다이제스트, 설정 해시, 활성/롤백 후보)를 둔다. 새 버전은 평가 묶음(FR-17) 전체를 재평가해 통과해야 **승격**하고, 문제가 생기면 직전 활성 후보로 **롤백**한다.

**Acceptance Criteria**:
- [ ] M1~M7 각각에 매니페스트가 있고, 활성 버전과 롤백 후보가 구분된다
- [ ] 평가 담당 팀원은 매니페스트를 조회하고, 새 버전의 평가를 실행하고, 통과한 버전을 승격하고, 직전 활성 후보로 롤백할 수 있다. 운영자·연동 개발 역할은 승격·롤백을 할 수 없다
- [ ] 평가 묶음 전체를 통과하지 못한 버전은 승격할 수 없다. 모든 항목을 끝내지 못한 평가는 승격 근거가 될 수 없다
- [ ] 승격하면 직전 활성 버전이 롤백 후보로 자동 지정된다. 롤백은 재평가 없이 즉시 이루어지며, 새 단계 작업부터 적용된다 [추론 — 통합 결정 D5]
- [ ] 승격·롤백 뒤에도 보호자 흐름과 API 계약은 바뀌지 않는다
- [ ] 단계 작업마다 실행한 모델 ID와 버전이 기록되어, 어느 버전이 어떤 결과를 냈는지 추적된다
- [ ] 라이선스 조건이 확인되지 않은 모델은 활성화하지 않는다. AGPL 예비 모델은 소스 공개 결정 전까지 비활성이다 [NEEDS CLARIFICATION: U4 — OpenCLIP 가중치 · Qwen3 · TRELLIS 의존성 라이선스 조건과 AGPL 예비 모델 채택 여부는?]

#### FR-25: 서빙 3종 분리와 모델별 시간 상한·동시 처리 제한

**Description**: 성격이 다른 모델을 **작업 계약 하나** 뒤에서 세 가지 서빙으로 나눈다.
- **CPU 비전 워커**: M1·M2·M3·M4, 비동기 작업 큐
- **GPU 워커**: M5·M7, 전용 큐, 모델 상주. GPU가 없으면 M5는 CPU에서 실행하고 M7은 노출하지 않는다
- **LLM 서버**: M6, 짧은 동기 요청 또는 스트리밍(P0.5)

**Acceptance Criteria**:
- [ ] 세 서빙은 서로 다른 큐 또는 요청 경로를 쓰며, 한 서빙의 적체나 장애가 다른 서빙의 처리를 막지 않는다
- [ ] API 서버는 세 서빙에 같은 형식의 단계 작업 계약으로 요청하고, 단계 작업 응답 분류와 작업 기록 분류가 1:1로 맞는다
- [ ] 모델별로 시간 상한, 동시 처리 수, 재시도 횟수가 설정되어 있고, 상한에 닿으면 대기열에 둔다
- [ ] GPU 워커의 모델은 상주해, 단계 작업마다 모델을 새로 불러오지 않는다
- [ ] 모델 런타임 포트는 내부망에만 열린다
- [ ] GPU 유무에 따른 동작이 정해져 있다 [NEEDS CLARIFICATION: U2 — 팀 서버에 GPU가 있는가? M5 처리 속도와 M7(P1) 가능 여부가 이에 달려 있다]
- [ ] 모델별 상한 수치는 U6에서 정한다

#### FR-26: 모델별 지표

**Description**: 서빙 지표(FR-13)를 모델별로 나눠 수집한다. 수집 항목은 처리 시간 p95, 낮춤률, 재시도율, 큐 적체, 판정 수정률, 설명 규칙 검사 실패율(P0.5), 결과 미도달 수다. 지표 라벨에는 식별 정보를 넣지 않는다.

**Acceptance Criteria**:
- [ ] 각 지표는 모델 ID, 모델 버전, 서빙군 라벨로 나눠 볼 수 있다
- [ ] 지표 라벨과 값에 이미지, 작품 번호, 요청 번호, 별칭 등 식별 정보가 없다(결과 미도달 개별 추적은 FR-13의 별도 목록으로만 한다)
- [ ] 지표는 운영용 지표 엔드포인트(`/metrics`)로 수집할 수 있다
- [ ] 원인 5분류(FR-5)가 지표에서도 섞이지 않는다

#### FR-27: 키워드 기반 작품 설명 생성 (P0.5)

**Description**: 보호자가 원하면 키워드로 **작품 설명 초안**을 받는다. 설명 생성(M6)의 입력은 보호자 키워드, 보호자가 고른 M2 태그, 아이의 실제 발언, 제작 당시 나이, 제작일뿐이다. 이미지와 아이 이름은 넣지 않는다. 생성 뒤 규칙 검사를 거치고, 통과하지 못하면 재생성하며, 상한을 넘으면 템플릿 설명(기준선)으로 낮춘다. 보호자가 수정·승인해야 전시에 붙는다.

**Acceptance Criteria**:
- [ ] 설명 초안 받기는 이야기 입력 화면에서 보호자가 고를 때만 실행된다
- [ ] M2 태그는 키워드 후보로만 제안되고, 보호자가 골라야 입력이 된다
- [ ] 생성 입력에 이미지, 별칭, 실명이 들어가지 않는다
- [ ] 규칙 검사는 입력에 없는 사건·감정·발달 상태 표현을 찾아낸다. 걸리면 재생성하고, 재생성 상한(기본 2회 [추론])을 넘으면 템플릿 설명을 제안한다. 템플릿도 맞지 않으면 보호자가 직접 입력한다
- [ ] 규칙 검사 전 문장과 검사에 걸린 초안은 보호자에게 보이지 않고 저장하지 않는다. 실패 분류만 기록한다. 스트리밍 응답은 진행 표시에만 쓴다 [추론 — 통합 결정 D7]
- [ ] LLM 초안과 템플릿 설명에는 모두 "AI 작성" 표시가 붙는다. 보호자가 직접 입력한 설명에는 표시가 없다. 보호자가 고친 LLM 초안은 출처를 LLM으로 유지하고 수정 여부를 따로 기록한다 [추론 — 통합 결정 D6]
- [ ] 출처(LLM / 템플릿 / 직접), 규칙 검사 결과, 생성 횟수가 기록된다
- [ ] 설명 단계(M6)의 인프라 재시도가 소진되면 보호자가 "템플릿으로 받기 / 나중에 다시 / 직접 쓰기" 중 하나를 고른다. 결과 미도달로 세지 않고, 설명 낮춤률에도 넣지 않는다 [추론 — 통합 결정 D1]
- [ ] 보호자는 초안을 수정·승인·폐기할 수 있다. 승인 전에는 재생성할 수 있고, 승인 뒤에는 고정되어 재생성할 수 없다
- [ ] 승인된 설명을 내리거나 교체하는 절차가 정해져 있다 [NEEDS CLARIFICATION: U16 — 승인된 설명을 전시에서 내리거나 다른 설명으로 교체하는 절차는?]
- [ ] 승인된 설명만 전시에 붙고, 아이의 한마디와 다른 영역에 보인다(FR-7, FR-8)
- [ ] 외부 LLM API로 아이 데이터를 보내지 않는다. 기본은 자체 호스팅 LLM이다 [NEEDS CLARIFICATION: U3 — 과정 제공 LLM 엔드포인트가 있는가, 있다면 데이터 처리 조건은? M6 실행 방식이 이에 달려 있다]
- [ ] 규칙 검사 방식이 정해져 있다 [NEEDS CLARIFICATION: U11 — 설명 규칙 검사의 금지어·사건 판별 방식과 재생성 상한은?]

#### FR-28: 외부 모델 기능 엔드포인트 (P0.5)

**Description**: 외부 클라이언트(연동 앱)가 모델 기능을 조합해 쓸 수 있도록 분리·판정·관절·2.5D·설명 기능을 엔드포인트로 연다(`/v1/models/{segment|classify|pose|relief|caption}`). 인증, 요청 한도, 요청 크기 제한, 입력 비보존을 필수로 한다. 지금은 시연·포트폴리오용이며 상품화하지 않는다.

**Acceptance Criteria**:
- [ ] API 키 없이 호출하면 거절한다
- [ ] 요청 한도와 요청 크기 상한을 넘으면 거절하고 이유를 코드로 알린다
- [ ] 외부 호출의 입력(이미지·텍스트)은 처리 뒤 보관하지 않고 로그에도 남기지 않는다
- [ ] 외부 호출의 입력과 결과는 워커 임시 영역에만 두고 원본·결과 저장소에 쓰지 않는다. 결과를 내려받거나 보관 상한이 지나면 삭제한다. 처리 중 임시 보관은 "보관"으로 보지 않는다 [추론 — 통합 결정 D8. 보관 상한은 자료 없음, U12]
- [ ] 오래 걸리는 기능은 작업 번호를 돌려주고, 외부 클라이언트가 작업 상태와 결과를 따로 조회한다 [추론 — 통합 결정 D13, 경로는 U8]
- [ ] 3D 조각(M7)은 외부 엔드포인트에 열지 않는다. 요청하면 "없음"으로 응답한다 [추론 — 통합 결정 D9]
- [ ] 외부 클라이언트는 가족 데이터(작품·전시)에 접근할 수 없다
- [ ] 연동 오류(잘못된 입력 등)의 분류 코드가 정해져 있다 [NEEDS CLARIFICATION: U18 — `invalid_input` 등 연동 오류 분류는? Intent의 오류 분류 5종(엔진 다운·시간 초과·저장소·DB·모델 미준비)에는 없다]
- [ ] 외부 엔드포인트는 보호자 흐름과 같은 모델 어댑터·활성 버전을 쓰며, 모델 버전이 응답에 표시된다 [추론]
- [ ] 외부 호출도 모델별 시간 상한·동시 처리 제한을 받고, 보호자 흐름의 처리를 밀어내지 않는다 [추론]
- [ ] 엔드포인트 이름·응답 형식·인증 방식이 확정되어 있다 [NEEDS CLARIFICATION: U8 — 엔드포인트 이름·응답 형식·포트·인증 방식은? 현재 경로는 추론이다]
- [ ] API 키 발급·한도·약관이 정해져 있다 [NEEDS CLARIFICATION: U12 — 외부 클라이언트 API 키 발급 주체, 요청 한도 수치, 약관은?]

#### FR-29: 만들기 작품 3D 조각 (P1)

**Description**: 점토·종이 공작 같은 **만들기 작품**을 3D 조각(M7, TripoSR / 대안 TRELLIS)으로 복원해 GLB로 저장하고, 화면에서 회전해 볼 수 있게 한다. 팀 서버 GPU를 확인한 뒤 결정하며, 그 전에는 화면에 노출하지 않는다. 평면 그림에는 쓰지 않는다.

**Acceptance Criteria**:
- [ ] 3D 노출은 노출 설정으로 켠다. 기본은 꺼짐이며, GPU가 확인되고(U2) M7 매니페스트가 승격된 뒤에 켠다. 꺼져 있으면 3D 선택지는 어떤 화면에도 나타나지 않고, 이미 만든 3D 결과는 원본 액자로 보인다 [추론 — 통합 결정 D10]
- [ ] 3D 조각은 외부 모델 기능 엔드포인트(FR-28)에 열지 않는다
- [ ] 3D 조각은 만들기 작품에만 적용한다. 평면 그림에는 3D를 제안하거나 확정 선택지로 보이지 않는다. 만들기 작품 여부를 판정 제안으로 가릴지, 보호자가 올릴 때 고를지는 P1 착수 시 정한다 [추론]
- [ ] 3D 결과에는 "뒷면은 AI가 추정했어요"가 표시되고, 원본 사진이 함께 보인다
- [ ] 3D 품질 미달은 2.5D 부조 → 원본 액자로 낮춘다(FR-23)
- [ ] 3D 회전은 보호자가 고를 때만 동작한다
- [ ] 삭제 시 GLB도 지운다(FR-10)
- [ ] GPU 유무는 U2에서 정한다. 대안 TRELLIS는 의존성 라이선스 확인(U4) 전 활성화하지 않는다

#### FR-30: 모델 API 서버와 'API활용' 메뉴

**Description**: 모델 기능은 **Python 가상환경 + uvicorn**으로 띄운 API로 제공한다(추가 요구 R3). 보호자 앱 API는 접수·상태·권한을 맡고 모델을 직접 import하지 않는다. API 서버는 **엔드포인트 · 가이드라인 · 매뉴얼** 3영역을 담은 **'API활용' 메뉴**를 팀원 전용으로 갖춘다(추가 요구 R4).

**Acceptance Criteria**:
- [ ] 모델 기능 API는 Python 가상환경에 설치되고 uvicorn으로 실행된다. 가상환경 구성은 재현할 수 있게 기록된다
- [ ] 'API활용' 메뉴는 엔드포인트, 가이드라인, 매뉴얼 3영역을 가진다
- [ ] 엔드포인트 영역은 서비스가 내보내는 API 명세(`/openapi.json`)에서 생성되어, 실제 API·활성 모델 버전과 어긋나지 않는다
- [ ] 'API활용' 메뉴는 팀원(연동 개발·운영자) 로그인과 역할 확인 뒤에만 열리며, 보호자 화면에는 없다
- [ ] (P0.5) 메뉴의 시험 호출은 외부 모델 기능 엔드포인트(FR-28)를 부르므로 P0.5에 연다. 시험 호출에는 평가 묶음 작품만 쓸 수 있고, 가족 작품은 고를 수 없다 [추론 — 통합 결정 D12]
- [ ] 메뉴 위치와 역할별 조회 범위가 정해져 있다 [NEEDS CLARIFICATION: U17 — 'API활용' 메뉴를 어디에 두며, 연동 개발 팀원이 관리 엔드포인트(모델 매니페스트·승격 등)의 명세를 조회할 수 있는가?]
- [ ] 보호자 앱 API 스택이 정해져 있다 [NEEDS CLARIFICATION: U7 — 보호자 앱 API 스택을 Intent-Plan 후보 4종(Vue+Node+MariaDB, React+FastAPI+PostgreSQL, Django, Next.js) 중 무엇으로 하며, 모델 서빙 계층(Python)과 분리하는가? [추론] 모델 서빙 계층은 R3와 모델 생태계 때문에 Python(uvicorn)으로 고정하고 보호자 앱 API 스택만 `/speckit.plan`에서 정한다]

### Secondary Requirements (검증·운영 요구사항)

#### FR-16: 모델 7종 재현과 교체 가능성

**Description**: 모델 7종(M1~M7, M4는 규칙)을 버전 고정해 팀 서버에서 반복 재현하고 검증한다. 핵심 엔진(M3 Animated Drawings)과 그 런타임(TorchServe)은 관리가 종료(보관 처리)되었으므로 조건부로 채택한다. 어떤 모델을 바꾸더라도 가족이 쓰는 흐름은 달라지지 않아야 한다.

**Acceptance Criteria**:
- [ ] 팀 서버에서 모델마다 설치·실행을 재현하고 버전, 처리 시간, 메모리, 오인 사례를 기록한다. 기록은 매니페스트(FR-24)에 연결된다
- [ ] P0 모델(M1~M5)의 재현을 먼저 끝내고, M6(P0.5), M7(P1)은 해당 구간 착수 전에 재현한다
- [ ] 단계 작업마다 모델 ID와 버전이 기록된다
- [ ] 어떤 모델을 예비안으로 바꿔도 접수, 판정 확정, 보호자 확인, 이야기, 전시, 삭제 흐름과 화면은 바뀌지 않는다
- [ ] 보관 처리된 엔진과 런타임은 내부망에 격리하고, 고정 이미지와 체크섬으로 운영한다. 관리 기능과 외부 포트는 닫혀 있다
- [ ] 모델 파일의 팀 서버 위치가 매니페스트에 기록된다 [NEEDS CLARIFICATION: U14 — 팀 서버의 모델 파일 경로는?]

#### FR-17: 평가 묶음

**Description**: 팀원이 직접 만든 작품으로 **평가 묶음**을 관리한다. 묶음은 사람 그림, 비인물 그림(동물·집·사물), 촬영 조건(배경·조명·기울기), 입체 작품(만들기), 설명 입력 세트로 구성하고, 각 작품의 기대 경로를 적는다. 설명은 템플릿 설명을 기준선으로 비교한다. 모델 버전이 바뀔 때마다 전체를 다시 평가한다. 시연과 평가에는 팀원이 직접 만든 작품만 쓴다.

**Acceptance Criteria**:
- [ ] 평가 묶음의 작품마다 종류(사람 / 동물 / 집 / 사물 / 입체), 촬영 조건, 기대 제안, 기대 경로가 기록되어 있다
- [ ] 설명 입력 세트마다 입력(키워드·태그·발언·나이·제작일)과 템플릿 기준선 설명이 기록되어 있다
- [ ] 어떤 모델 버전을 바꾸면 전체 평가 묶음을 다시 실행하고, 기대 제안·경로와 달라진 건, 낮춤 건, 규칙 검사 실패 건을 목록으로 남긴다
- [ ] 평가 기록에는 오인 사례(예: 집 그림을 사람으로 잡아 벽에 관절을 붙인 경우)가 분류되어 남는다
- [ ] 평가 결과는 승격 판단(FR-24)의 근거가 된다. 모델별 품질 임계값과 승격 기준은 1차 측정 뒤 정한다(U5)

#### FR-18: 사용 관찰 기록

**Description**: 보호자 역할 사용자가 등록 → 판정 확정 → 결과 확인 → 이야기 → 전시를 수행하는 과정과 막힌 지점을 직접 관찰해 기록한다. 실제 아동 참여 관찰은 적절한 동의와 수집 조건이 확정된 뒤에만 한다.

**Acceptance Criteria**:
- [ ] 관찰 세션마다 완료 여부, 막힌 단계, 막힌 이유, 판정 수정 여부와 이유, 다시 보기 행동과 그 이유가 기록된다
- [ ] (P0.5) 설명 초안을 승인했는지, 얼마나 고쳤는지가 기록된다
- [ ] 아이가 자기 작품을 알아보는지, 가족이 원본과 결과를 함께 보는지는 동의·수집 조건이 확정된 뒤에만 관찰한다
- [ ] 동의·수집 조건이 확정되기 전에는 실제 아동을 관찰 대상에 포함하지 않는다 [NEEDS CLARIFICATION: U13 — 상용화 전 법정대리인 동의 절차(고지·확인·보유 기간·철회)는?]
- [ ] 짧은 시연 결과를 장기 보관 가치의 증거로 보고하지 않는다

#### FR-19: 추적성

**Description**: 이 명세의 요구사항은 유스케이스, 작업, 검증 증거로 추적된다. 유스케이스는 UC1~UC12이며, FR과의 연결은 요구사항 목록 표를 따른다.

**Acceptance Criteria**:
- [ ] 모든 FR은 하나 이상의 유스케이스 또는 검증 활동에 연결되고, 유스케이스는 작업과 검증 증거에 연결된다(REQ → UC → T → 증거)
- [ ] 유스케이스 문서는 `design/` 아래 공통 기준의 파일명을 따르고, FR 번호는 이 명세 v2.0의 번호를 그대로 쓴다
- [ ] 유스케이스 명세의 서식 검증은 14속성 서식 기준(`~/.claude/skills/usecase/references/format-spec.md`)에 따라 수행하고, 검증을 마치기 전에는 "완료"로 표시하지 않는다
- [ ] P0.5·P1 요구사항은 해당 구간 착수 전까지 "미착수"로 표시하고, P0 완료율에 섞지 않는다

## User Scenarios & Testing

### Primary User Flow

1. 보호자가 로그인하고 아이를 별칭으로 등록한다(최초 1회).
2. 보호자가 아이를 고르고 작품 사진을 올린다.
3. 시스템이 파일을 검사한다. 원본, 작품 기록, 작업 기록을 모두 저장한 뒤 "접수 완료"를 알린다.
4. 백그라운드에서 배경 분리(M1)와 판정(M2·M3·M4)이 진행된다. 보호자는 화면을 떠나도 된다.
5. 작품이 "확정 대기"가 되면 보호자는 제안 문구(예: "움직일 수 있을 것 같아요")를 보고 움직임 / 2.5D 부조 / 원본 액자 중 하나로 확정한다.
6. 백그라운드에서 확정한 경로가 처리된다. 품질이 모자라면 한 단계 낮춘 결과가 만들어진다.
7. 작품이 "확인 대기"가 되면 보호자가 결과를 보고 좋아요 / 낮춘 결과로 걸기 / 액자로 걸기 / 다시 찍기 중 하나를 고른다.
8. 보호자가 제목, 제작일, 제작 당시 연령을 입력하고, 원하면 아이의 한마디를 입력한다. (P0.5) 원하면 키워드로 설명 초안을 받아 고치고 승인한다.
9. 승인되고 이야기가 채워진 작품이 아이별·연령별 전시 화면에 나타난다. 가족이 함께 한 점씩 골라 감상한다.
10. 필요하면 보호자가 작품이나 아이를 삭제한다.

### Acceptance Scenarios

#### Scenario 1: 사람 그림이 움직이는 작품으로 전시됨
**Given**: 아이 "하늘"이 등록된 보호자
**When**: 사람 그림을 올리고, 제안 "움직일 수 있을 것 같아요"를 보고 움직임으로 확정한다. 확인 대기에서 "좋아요"를 누르고 제목·제작일·연령을 입력한다
**Then**: "하늘"의 전시 화면에서 해당 연령 묶음에 움직이는 작품이 보인다. 작품을 고르면 재생되고, 원본과 이야기도 함께 보인다. 판정 수정 여부는 "아니요"로 기록된다

#### Scenario 2: 집 그림은 점수가 높아도 움직임을 제안하지 않음
**Given**: 엔진(M3)이 사람 점수를 높게 내는 집 그림(과거 0.946 사례와 같은 유형)
**When**: 보호자가 올리고 판정이 끝난다
**Then**: 제안은 M2 종류 판정과 M4 기하 규칙을 함께 반영해 "입체 부조가 어울려요" 또는 "액자로 거는 것을 추천해요" 같은 문구로 보인다 [추론 문구]. 점수는 화면에 없다

#### Scenario 3: 보호자가 제안과 다르게 확정
**Given**: 제안이 "움직일 수 있을 것 같아요"인 사람 그림
**When**: 보호자가 원본 액자로 확정한다
**Then**: M3 움직임 렌더와 M5가 한 번도 실행되지 않고 원본 액자가 확인 대기에 도달한다. 원인은 "보호자 선택", 판정 수정 여부는 "예"로 기록된다

#### Scenario 4: 움직임 품질 미달은 2.5D로 낮춤
**Given**: 보호자가 움직임으로 확정했지만 M3가 인물을 찾지 못했다. M1 마스크는 정상이다
**When**: 처리가 끝난다
**Then**: 재시도 없이 M1 마스크로 2.5D 부조가 만들어지고, 결과 화면에 "움직임을 만들 수 없어 입체 부조로 준비했어요" 안내가 보인다 [추론 문구]. 원인은 "모델 낮춤(움직임 → 2.5D)", 오류 분류는 비어 있다

#### Scenario 5: 분리 실패는 2.5D를 건너뛰고 원본 액자로
**Given**: 배경과 작품 경계가 흐린 사진이라 M1 분리가 품질 미달이다. 보호자는 2.5D 부조로 확정했다
**When**: 처리가 끝난다
**Then**: 2.5D를 시도하지 않고 원본 사진 전체가 액자로 준비된다. 원인은 "모델 낮춤(분리 품질 미달 → 액자)"으로 기록된다

#### Scenario 6: 인프라 장애는 낮춤이 아니라 재시도 후 "처리하지 못함"
**Given**: 움직임 렌더 중 저장소 장애가 계속된다
**When**: 같은 단계의 시도가 첫 시도 포함 3회에 도달한다
**Then**: 보호자에게 "처리하지 못했어요"와 함께 "액자로 걸기 / 다시 찍기" 선택지가 보인다. 오류 분류는 "저장소", 결과 미도달 수가 1 늘어난다. "모델 낮춤"으로는 집계되지 않고, 2.5D로 자동 전환되지도 않는다

#### Scenario 7: 모델 하나가 멈춰도 다른 경로는 동작
**Given**: M3가 멈춰 준비 확인에 "M3 준비 안 됨"이 표시된다
**When**: 보호자가 다른 작품을 2.5D 부조로 확정한다
**Then**: 2.5D 작품은 확인 대기에 정상 도달한다. 움직임으로 확정한 작품은 "모델 미준비" 재시도 규칙을 따른다

#### Scenario 8: 결과 확인에서 낮춘 결과로 전환
**Given**: 움직이는 결과가 어색하게 나온 작품이 확인 대기 상태다
**When**: 보호자가 "낮춘 결과로 걸기"를 고른다
**Then**: 2.5D 부조가 결과가 된다(없으면 이때 만들어진 뒤 다시 확인 대기) [추론]. 어색한 움직임은 어디에도 전시되지 않는다. 원인은 "보호자 전환"으로 기록된다

#### Scenario 9: 접수 중 저장 실패 시 접수하지 않음
**Given**: 원본 저장은 성공했지만 작업 기록 저장이 실패한다
**When**: 보호자가 올리기를 마친다
**Then**: 보호자에게 "접수되지 않았어요. 다시 올려 주세요"가 보인다. 목록에 해당 작품이 없고, 저장된 원본도 남지 않는다

#### Scenario 10: 다시 찍기
**Given**: 흐리게 찍힌 사진의 결과가 확인 대기 상태다
**When**: 보호자가 "다시 찍기"를 누르고 새 사진을 올린다
**Then**: 새 사진은 새 작품·새 작업으로 접수되고, 이전 원본은 덮어쓰이지 않는다. 이전 건은 전시되지 않고 삭제 규칙을 따른다

#### Scenario 11: 처리 중 삭제
**Given**: GPU 워커에서 깊이·부조 단계가 진행 중인 작품
**When**: 보호자가 작품을 삭제한다
**Then**: 작품이 즉시 목록에서 사라진다. 진행 중이던 단계 작업이 취소되고, 멈춘 것이 확인된 뒤 원본·마스크·깊이 결과·중간·최종 결과·임시 파일이 모두 지워진다. 작업 기록에는 집계 필드만 남는다

#### Scenario 12: 다른 가족 작품 접근 차단
**Given**: 가족 A의 보호자가 로그인해 있다
**When**: 가족 B의 작품 주소를 직접 입력한다
**Then**: 작품이 보이지 않고 접근이 거부된다. 원본·마스크·결과·이야기·설명 어느 것도 노출되지 않는다

#### Scenario 13: 승인 전 비전시
**Given**: 확인 대기인 2.5D 작품 1건, 확정 대기 작품 1건, 전시된 작품 3건
**When**: 가족이 전시 화면을 연다
**Then**: 전시된 3건만 보이고, 나머지는 보이지 않는다

#### Scenario 14: 운영자의 원인별·모델별 지표 확인
**Given**: 한 주 동안 보호자 선택, 모델 낮춤, 보호자 전환, 인프라 실패, 결과 미도달이 섞여 발생했다
**When**: 운영자가 지표 화면을 연다
**Then**: 다섯 가지가 서로 다른 항목으로 보이고, 모델별 처리 시간 p95·낮춤률·재시도율·큐 적체가 모델 ID·버전별로 보인다. 결과 미도달 건은 요청 번호로 추적된다. 화면에 이미지·작품 번호·별칭·제목·한마디는 없다

#### Scenario 15: 모델 버전 승격과 롤백
**Given**: 평가 담당 팀원이 M1의 새 버전을 등록했다
**When**: 평가 묶음 전체를 실행한다
**Then**: 기대 경로와 달라진 건과 낮춤 건이 목록으로 나온다. 통과하면 승격할 수 있고, 통과하지 못하면 승격 버튼이 막힌다. 승격 뒤 문제가 생기면 직전 활성 후보로 롤백되고, 보호자 흐름은 바뀌지 않는다

#### Scenario 16: 'API활용' 메뉴 확인
**Given**: 연동 개발 팀원이 로그인했다
**When**: 'API활용' 메뉴를 연다
**Then**: 엔드포인트·가이드라인·매뉴얼 3영역이 보이고, 엔드포인트 목록은 현재 API 명세와 일치한다. (P0.5) 시험 호출에는 평가 묶음 작품만 고를 수 있다. 보호자 계정으로는 이 메뉴가 보이지 않는다

#### Scenario 17: (P0.5) 키워드로 설명 초안 받기
**Given**: 아이의 한마디 "엄마랑 바다 갔어"와 제작 당시 연령 5세가 입력된 작품
**When**: 보호자가 키워드 "바다, 파란색"과 제안된 태그 하나를 골라 설명 초안을 받는다
**Then**: "AI 작성" 표시가 붙은 초안이 보인다. 입력에 없는 사건·감정이 들어간 초안은 규칙 검사에서 걸러져 재생성되고, 상한을 넘으면 템플릿 설명이 제안된다. 보호자가 승인하면 전시에 아이의 한마디와 분리된 영역으로 붙고, 이후 재생성할 수 없다

#### Scenario 18: (P0.5) 인증 없는 외부 호출 거절
**Given**: API 키가 없는 외부 클라이언트
**When**: 분리 기능 엔드포인트를 호출한다
**Then**: 호출이 거절되고, 입력은 저장되지 않으며 로그에도 남지 않는다

#### Scenario 19: (P1) 만들기 작품의 3D 조각
**Given**: GPU가 확인되고 M7이 승격된 상태에서 점토 작품 사진이 올라왔다
**When**: 보호자가 3D 조각으로 확정하고 결과를 확인한다
**Then**: 회전해 볼 수 있는 3D 조각과 함께 "뒷면은 AI가 추정했어요" 표시와 원본 사진이 보인다. 3D 품질 미달이면 2.5D 부조로 낮춘 결과가 돌아온다

### Edge Cases

- **허용 형식이지만 깨진 파일**: 판독 검사에서 거절하고 "사진을 열 수 없어요"라고 안내한다. 접수하지 않는다.
- **같은 요청의 중복 전송**: 작품은 하나만 생성된다(FR-2).
- **워커의 중도 정지**: 정해진 시간이 지나면 다른 워커가 이어받는다. 이어받기도 시도 횟수에 포함되고, 3회를 넘으면 "처리하지 못함"이 된다.
- **판정 단계만 실패**: 재시도가 소진되면 작품은 "확정 대기"로 머물고, 보호자가 제안 없이 직접 확정할 수 있다. 제안값은 "제안 없음"으로 기록되고, 인프라 실패로만 집계된다(결과 미도달 아님) [추론 — 통합 결정 D1].
- **"삭제 중" 작품에 확정·결정 요청**: 받지 않는다. 취소된 단계 작업은 "취소"로 분류되어 지표에서 빠진다 [추론 — 통합 결정 D4].
- **같은 결과 결정이 두 번 전송됨**: 첫 결정을 유지한다 [추론 — 통합 결정 D11].
- **보호자가 확정하지 않고 떠남**: 작품은 "확정 대기"에 머물고 전시되지 않는다. 확정 대기의 보관 기한은 두지 않는다 [추론].
- **엔진(M3)이 사람 점수는 높지만 사람이 아닌 그림**: 점수는 기록만 한다. 제안은 M2·M4와 함께 판단하고, 보호자 확정과 확인 없이는 전시되지 않는다.
- **M1 실패 + 움직임 확정 + M3 품질 미달**: 2.5D를 건너뛰고 원본 액자로 낮춘다. 원인은 "모델 낮춤(움직임 → 액자, 마스크 없음)"으로 기록된다 [추론].
- **GPU 없음**: M5는 CPU에서 실행되어 느릴 수 있다. 3D 선택지는 보이지 않는다.
- **모델 미준비 상태에서 확정**: 해당 단계는 "모델 미준비"로 재시도 규칙을 따르고, 낮춤 체인을 타지 않는다.
- **이야기를 입력하지 않고 승인만 누름**: 승인 선택은 기록되지만, 필수 이야기 항목을 채우기 전까지 전시되지 않는다. 보호자에게 "이야기를 채우면 전시돼요"라고 안내한다.
- **미래 제작일 또는 범위 밖 연령**: 입력을 거절하고 이유를 안내한다.
- **다시 찍기 후 새 사진을 올리지 않음**: 이전 건은 닫힌 채 전시되지 않는다. 새 작품은 생기지 않는다.
- **처리하지 못함 건에서 원본까지 읽을 수 없는 경우**(저장소 장애 지속): "액자로 걸기"를 비활성화하고 "다시 찍기"만 제공한다.
- **(P0.5) 설명 승인 뒤 재생성 요청**: 거절하고 "승인한 설명은 고정돼요"라고 안내한다. 승인된 설명을 내리거나 교체하는 절차는 U16에서 정한다.
- **(P0.5) LLM 서버 다운**: 설명 단계는 재시도 규칙을 따르고, 소진되면 보호자가 "템플릿으로 받기 / 나중에 다시 / 직접 쓰기"를 고른다. 인프라 장애이므로 설명 낮춤률과 결과 미도달에 넣지 않고 재시도율·인프라 실패로 집계한다 [추론 — 통합 결정 D1].
- **삭제 중 일부 파일 삭제 실패**: 자동으로 다시 시도한다. 끝내 완료되지 않으면 운영 지표에 "삭제 미완료"로 보인다.
- **아이 삭제 시 처리 중인 작품 포함**: 해당 작품의 모든 단계 작업 취소를 확인한 뒤 삭제한다.
- **동시 처리 상한 도달**: 새 단계 작업은 해당 서빙군 대기열에서 순서를 기다린다. 대기 시간은 큐 적체 지표에 반영된다.
- **(P0.5) 외부 호출이 한도를 넘음**: 거절하고 이유 코드를 돌려준다. 보호자 흐름의 처리는 영향받지 않는다.

## Success Criteria

> 아래 목표값은 **검증 목표**다. 달성 실적이 아니며, 성능 수치는 팀 서버 재현 시험 뒤 확정한다. v1.0의 잠정 목표 중 원천에서 이어받은 것은 "(v1.0 잠정)"으로 표시했다.

### Quantitative Metrics

- **결과 미도달 수**: 검증 기간 동안 0건
- **승인 전 전시**: 확정 대기·처리 중·확인 대기·처리하지 못함·다시 찍기 상태의 작품이 전시 화면에 노출된 건수 0건(자동 시험과 관찰로 확인)
- **원본 변형**: 모델 처리로 원본이 덮어쓰이거나 변형된 건수 0건
- **원인 분리 정확도**: 장애 주입 시험(엔진 정지, 시간 초과, 저장소 장애, DB 장애, 모델 미준비)에서 인프라 장애가 "모델 낮춤"으로 집계되는 건수 0건. 각 장애가 해당 오류 분류로 100% 기록됨
- **확정 결정성**: 원본 액자로 확정한 작품 중 M3 움직임 렌더·M5를 시도한 건수 0건. 2.5D로 확정한 작품 중 M3 움직임 렌더를 시도한 건수 0건
- **점수 비노출**: 보호자 화면 점검에서 모델 점수·확률 노출 0건
- **낮춤 체인 준수**: 품질 미달 주입 시험에서 체인 밖 이동(예: 움직임 → 액자 직행, M1 정상인데 2.5D 건너뜀) 0건
- **삭제 완전성**: 삭제 시험(처리 중 삭제 포함)에서 삭제 완료 후 남은 원본·마스크·깊이·중간·최종 결과·설명·GLB·임시 파일 0건, 남은 작업 기록의 작품 연결·저장 위치·자유 입력 0건
- **로그 정보 보호**: 운영 로그 표본 점검에서 이미지, 저장 위치 키, 자유 입력, 오류 원문 0건
- **접근 차단**: 가족 간 교차 접근 시험, 팀원 역할의 가족 데이터 접근 시험, 외부 API 키의 가족 경로 접근 시험에서 노출 0건
- **매니페스트 완결성**: 활성 모델 중 매니페스트 필드(모델 ID·가중치 SHA-256·런타임·이미지 다이제스트·설정 해시)가 빠진 모델 0개
- **API 문서 일치**: 'API활용' 엔드포인트 영역과 실제 API 명세의 불일치 0건
- **(P0.5) 외부 입력 비보존**: 외부 호출 시험 뒤 저장소·로그에 남은 입력 0건
- **(P0.5) 승인 전 설명 비전시**: 승인하지 않은 설명이 전시에 붙은 건수 0건
- **움직임 경로 시간**: 팀 서버 단일 처리 조건에서 확정부터 확인 대기까지 p95 3분 이내(v1.0 잠정. 1차 개인 PC 실측은 한 장당 53~62초)
- **원본 액자 경로 시간**: 확정부터 확인 대기까지 p95 30초 이내(v1.0 잠정)
- **분리·판정·2.5D·설명 처리 시간**: 목표값을 정하지 않는다. 재현 시험에서 측정한 뒤 정한다(U6)
- **보호자 작업 완료율**: 관찰 세션에서 보호자 역할 사용자의 80% 이상이 도움 없이 등록 → 확정 → 확인 → 이야기 입력 → 전시를 끝냄(v1.0 잠정)
- **보호자 조작 시간**: 처리 대기 시간을 빼고, 작품 한 점을 올리고 확정하고 확인하고 이야기를 입력하는 데 3분 이내(v1.0 잠정)
- **다시 찾기**: 전시된 작품 20점 이상 중 지정한 작품을 30초 안에 찾음(v1.0 잠정)
- **첫 결과 승인율·판정 수정률·모델별 낮춤률·재시도율·설명 규칙 검사 실패율·큐 적체**: 목표값을 정하지 않는다. 기간별·모델별로 측정하고 원인별로 분해해, 모델 버전과 경로 개선의 기준선으로 쓴다

### Qualitative Measures

- **작품 알아보기**: 보호자 역할 사용자가 움직임·2.5D 결과에서 원본의 선과 색을 알아볼 수 있다고 답하는지, 관찰과 짧은 인터뷰로 확인한다. 아동 관찰은 동의 조건 확정 후에만 한다.
- **액자·2.5D의 완성감**: 원본 액자와 2.5D 부조가 "실패작"이 아닌 완성된 작품으로 느껴지는지 보호자 역할 사용자 인터뷰로 확인한다.
- **제안의 수용성**: 제안 문구가 강요로 느껴지지 않는지, 제안과 다르게 고를 때 망설임이 있었는지 관찰한다.
- **(P0.5) 설명의 충실성**: 승인된 설명이 입력에 없는 내용을 담지 않았는지, 보호자가 얼마나 고쳤는지 확인한다.
- **공동 감상 맥락**: 가족이 원본과 이야기를 함께 보는 장면이 관찰되는지, 어떤 계기로 다시 보는지를 기록한다. 재열람을 장기 보관 가치의 증거로 확대하지 않는다.
- **막힌 지점**: 관찰 기록에서 반복되는 막힘을 모아 개선 목록을 만든다.
- **평가 묶음 결과**: 모델 버전별로 기대 경로와 달라진 건, 낮춤 건, 오인 사례 목록이 남아, 승격 여부를 판단할 수 있다.

## Key Entities

### Entity: 가족(보호자 계정)
**Attributes**:
- 보호자 식별자: 로그인 주체
- 가족 공간: 작품, 아이, 이야기, 설명의 접근 경계

**Relationships**:
- 가족 1 : 아이 N

### Entity: 아이
**Attributes**:
- 별칭: 보호자가 정함, 가족 안에서 서로 구분됨, 등록 후 수정 가능
- (저장하지 않음): 실명, 생년월일, 출생연도

**Relationships**:
- 아이 1 : 작품 N

### Entity: 작품
**Attributes**:
- 제목, 제작일, 제작 당시 연령(만 나이 정수), 아이의 한마디(선택, 입력한 그대로)
- 원본 위치: 변경 불가
- 작품 마스크 위치(M1 결과, 없을 수 있음)
- 판정 제안값(움직임 / 2.5D / 액자 / 제안 없음), 보호자 확정값(움직임 / 2.5D / 액자, P1 3D), 수정 여부
- 결과 종류(움직임 / 2.5D 부조 / 원본 액자, P1 3D 조각)와 처음 만든 결과의 위치
- 낮춤 원인(어느 단계에서 어디로), 결과 원인 분류(보호자 선택 / 모델 낮춤 / 보호자 전환 / 인프라 실패 / 결과 미도달)
- 보호자 결정(좋아요 / 낮춘 결과로 걸기 / 액자로 걸기 / 다시 찍기), 승인 시각
- 상태: 접수됨 / 판정 중 / 확정 대기 / 처리 중 / 확인 대기 / 승인됨 / 전시 중 / 처리하지 못함 / 삭제 중

**Relationships**:
- 작품 1 : 처리 작업 1(단계 작업 N개를 묶음). 다시 찍기는 새 작품을 만들므로 같은 원본으로 같은 결과를 다시 만들지 않음
- 작품 1 : 작품 설명 0..1(승인본 기준, P0.5)

### Entity: 작품 설명 (P0.5)
**Attributes**:
- 보호자 키워드, 보호자가 고른 태그(M2 후보 중)
- 초안, 출처(LLM / 템플릿 / 직접), 보호자 수정 여부, 규칙 검사 결과(실패 분류만. 걸린 초안은 저장하지 않음), 생성 횟수
- 승인본, 승인 시각, "AI 작성" 표시 여부(LLM·템플릿은 표시, 직접 입력은 표시 없음)
- (입력에 넣지 않음): 이미지, 아이 이름·별칭

**Relationships**:
- 작품에 속한다. 승인 뒤 고정되며 재생성하지 않는다. 작품 삭제 시 함께 지운다

### Entity: 처리 작업
**Attributes**:
- 요청 번호, 작품 연결(삭제 시 제거), 전체 상태
- 결과 원인 분류, 결과 미도달 여부

**Relationships**:
- 작품 1 : 처리 작업 1, 처리 작업 1 : 단계 작업 N
- 작품이 삭제되면 작품 연결, 저장 위치, 자유 입력을 지우고 집계 필드만 남긴다

### Entity: 단계 작업
**Attributes**:
- 단계: 분리(M1) / 판정(M2 + M3 관절 + M4) / 움직임 렌더(M3) / 깊이·부조(M5) / 설명(M6, P0.5) / 3D(M7, P1)
- 모델 ID, 모델 버전, 서빙군(CPU 비전 / GPU / LLM)
- 상태(취소 포함 — 삭제로 취소된 단계 작업은 지표에서 뺀다), 시도 횟수, 처리 시간
- 낮춤 원인(품질 미달 코드) 또는 오류 분류(엔진 다운 / 시간 초과 / 저장소 / DB / 모델 미준비) — 둘은 섞지 않는다
- 진단 이유(정해진 코드), 모델 점수(기록용, 비노출)

**Relationships**:
- 처리 작업에 속한다. 중간 결과(마스크·관절·태그)는 다음 단계가 재사용한다(M1 → M5, M3 → M4·움직임 렌더, M2 → M6 키워드 후보)

### Entity: 모델 매니페스트
**Attributes**:
- 모델 ID(M1~M7), 버전, 가중치 SHA-256, 런타임, 이미지 다이제스트, 설정 해시
- 활성 / 롤백 후보 표시, 라이선스 확인 상태 [추론 — 활성화 조건 확인용]
- 재현 기록(처리 시간, 메모리), 모델 파일 위치(U14)

**Relationships**:
- 모델 1 : 매니페스트 N(버전별). 단계 작업은 실행한 매니페스트 버전을 참조한다
- 승격은 평가 묶음 통과를 조건으로 한다

### Entity: 평가 묶음
**Attributes**:
- 팀원이 직접 만든 작품: 종류(사람 / 동물 / 집 / 사물 / 입체), 촬영 조건, 기대 제안, 기대 경로, 제작자(팀원)
- 설명 입력 세트: 키워드·태그·발언·나이·제작일, 템플릿 기준선 설명
- 평가 결과(모델 버전별): 기대와 달라진 건, 낮춤 건, 오인 사례, 규칙 검사 실패 건

**Relationships**:
- 모델 버전이 바뀔 때마다 전체를 다시 평가한다. 'API활용' 메뉴의 시험 호출은 평가 묶음 작품만 쓴다

### Entity: 운영 지표
**Attributes**:
- 첫 결과 승인율, 판정 수정률, 모델별 낮춤률, 설명 규칙 검사 실패율(P0.5), 모델별 처리 시간 p95, 재시도율, 큐 적체, 결과 미도달 수, 삭제 미완료 수
- 라벨: 모델 ID, 모델 버전, 서빙군, 원인 분류(이미지·작품 번호·식별 정보 없음)

**Relationships**:
- 단계 작업과 처리 작업의 집계 필드에서 계산한다

## Constraints & Boundaries

### In Scope

**P0**
- 별칭만 받는 아이 등록
- 작품 사진 내구 접수(검사 → 원본·작품·작업 기록 저장 성공 후 접수 완료)
- 배경·작품 분리(M1), 판정 제안(M2·M3·M4)과 보호자 확정, 수정 기록
- 움직임(M3), 2.5D 입체 부조(M5), 원본 액자와 낮춤 체인
- 결과 원인 5분류와 인프라 실패(최대 3회 재시도)의 분리
- 보호자 결과 확인(좋아요·낮춘 결과로 걸기·액자로 걸기·다시 찍기)과 승인 전 비전시
- 이야기 직접 입력(제목·제작일·제작 당시 연령·선택형 한마디)
- 아이별·연령별 가족용 전시
- 가족 단위 접근 권한, 팀원 역할 분리, 작품·아이 삭제, 실행 중 취소, 임시 파일 정리
- 생존·준비(모델별) 상태 확인, 서빙 지표와 모델별 지표
- 서빙 3종 분리, 모델 어댑터·매니페스트·평가 후 승격·롤백
- 모델 API 서버(Python 가상환경 + uvicorn)와 'API활용' 메뉴
- 모델 재현 검증, 평가 묶음, 사용 관찰, 추적성 관리

**P0.5** (P0 완료 뒤 착수)
- 키워드 기반 작품 설명 초안(M6), 규칙 검사, 템플릿 기준선, AI 작성 표시, 승인 후 고정
- 외부 클라이언트용 모델 기능 엔드포인트(인증·한도·크기 제한·입력 비보존)

**P1** (팀 서버 GPU 확인 후, 그 전에는 비노출)
- 만들기 작품의 3D 조각(M7), GLB 저장, 회전 보기, 뒷면 추정 표시

### Out of Scope (후속 검증 범위)
- 하이라이트 영화(장면 선택, 순서, 자막, 음악)
- 실물 필름 제작·주문, 인화물·3D 출력 주문
- 결제, 구독, 가격 실험
- 촬영 보정(원근 보정·자동 자르기 보정). 배경 분리(M1)는 P0에 포함하지만 원본을 보정하지는 않는다
- 큐레이션(작품 선정·배치)
- 내보내기, 성장 후 접근권한 이전, 장기 보관 기간 정책, 서비스 종료 시 이관
- 상용화용 법정대리인 동의 절차(고지·확인·보유 기간·철회)
- 백업 사본의 보존·삭제 정책
- 유치원·미술학원 등 기관용 다아동 권한
- 외부 업체(알림장 앱, 인화·필름 업체) 연동, 외부 엔드포인트의 상품화·사용량 과금
- 모델 학습·미세조정
- 평면 그림의 image-to-3D

### Constraints
- **승인 전 비전시**: 보호자가 승인하지 않은 결과·설명은 어디에도 전시하지 않는다.
- **원본 불변**: 원본을 덮어쓰거나 변형하지 않는다. 모든 모델은 원본을 읽기만 한다. 결과물은 처음 만든 것을 보관한다. 설명은 승인 전까지만 다시 만들 수 있다.
- **결과는 늘 돌아온다**: 품질이 모자라면 한 단계 낮춘 결과를 돌려주고, 낮춘 사실을 숨기지 않는다.
- **원인 분리**: 보호자 선택·모델 낮춤·보호자 전환·인프라 실패·결과 미도달을 섞지 않는다.
- **제안은 제안까지**: 판정은 문구로 제안만 하고 보호자가 확정한다. 점수를 보이지 않는다. 모델 점수를 승인 근거로 쓰지 않는다.
- **최소 수집**: 실명, 생년월일, 출생연도를 받지 않는다. 아이의 한마디는 선택 입력이다. 설명 생성에 이미지·이름을 넣지 않는다. 외부 호출 입력은 보관하지 않는다.
- **동의 오판 금지**: 보호자 계정이 있다고 해서 법정대리인 확인이 끝났다고 보지 않는다. 실제 아동 데이터를 운영에 쓰기 전에 동의 절차를 확정해야 한다(U13).
- **시연 데이터**: 시연, 평가, 시험 호출에는 팀원이 직접 만든 작품만 쓴다.
- **기억 왜곡 금지**: 시스템은 입력에 없는 사건, 감정, 발달 상태를 만들지 않는다. AI 설명은 "AI 작성"으로 표시하고 아이의 실제 말과 섞지 않는다. 자동 감정 해석, 발달 평가, 아이 간 비교를 하지 않는다.
- **재창작 금지**: 평면 그림에 보이지 않는 면을 지어내는 3D 복원을 쓰지 않는다. 3D 조각(P1)은 만들기 작품에만 쓰고 추정 면을 표시한다.
- **과도한 화면 소비 억제**: 자동 반복과 무한 피드 대신, 가족이 골라서 감상하는 흐름을 둔다.
- **약속 금지**: 무료, 무제한, 평생 보관을 약속하지 않는다. 짧은 시연을 장기 가치의 증거로 제시하지 않는다.
- **학습 없음**: 공개 사전학습 모델을 학습·미세조정하지 않고 버전 고정해 이어 붙인다. 올린 작품을 학습에 쓰지 않는다.
- **라이선스 조건부 활성화**: 라이선스 조건이 확인되지 않은 모델은 활성화하지 않는다. 비상업 라이선스 모델(Depth Anything V2 Base·Large)과 적용 지역 제한 모델(Hunyuan3D)은 쓰지 않는다.
- **관리 종료 엔진의 조건부 채택**: M3 엔진과 그 런타임은 보안 업데이트가 없다. 외부 접근을 차단하고, 고정 실행 환경으로 격리하고, 어댑터로 교체할 수 있게 둬야 한다(FR-16, FR-24).
- **모델과 API 계약의 분리**: API 서버는 모델을 import하지 않는다. 모델을 바꿔도 가족 흐름과 API 계약은 바뀌지 않는다.

## Assumptions

- **대상 규모**: P0는 팀 내부 검증용이다. 보호자 역할 사용자(팀원)가 직접 만든 작품으로 사용한다. 동시 사용자는 소수(10명 이하)로 가정한다.
- **접근 방식**: 보호자는 휴대폰 웹 브라우저로 사진을 올리고 전시를 본다. 로그인은 일반적인 계정 로그인 방식을 쓴다.
- **허용 형식·용량(기본값)**: 휴대폰 사진의 일반 형식(JPEG, PNG, HEIC). 한 장 20MB 이하. 계획 단계에서 조정할 수 있다.
- **재시도·시간 상한(기본값)**: 인프라 장애는 단계 작업당 최대 3회 시도하고, 시도 사이 간격을 점점 늘린다. 움직임 렌더(M3) 처리 시간 상한은 10분이다. 다른 모델의 시간 상한과 동시 처리 수 상한은 팀 서버 재현 시험 뒤 정한다(U6).
- **제작 당시 연령**: 만 나이 정수(0~18세)로 받는다.
- **첫 결과 승인율의 모수**: v2.0에서는 결과가 도달한 작품의 첫 결정 전체(움직임·2.5D·액자)를 분모로 한다(Intent 정의, 통합 결정 D14). "처리하지 못함" 뒤의 결정은 뺀다(D2). v1.0은 움직이는 작품만 대상으로 했다. 액자·2.5D 결과에도 "좋아요" 선택지가 있다 [추론].
- **판정 수정률의 모수**: 제안이 제시된 건만 대상으로 한다. 제안 전에 직접 확정한 건은 빠진다(통합 결정 D14).
- **재시도 횟수**: "최대 3회"는 첫 시도를 포함한 시도 횟수다(통합 결정 D1).
- **다시 찍기로 닫힌 건의 파일**: 최소 보관 원칙에 따라 원본과 결과는 삭제 규칙(FR-10)과 같은 방식으로 지우고, 집계 필드만 남긴다.
- **처리하지 못함 건의 액자 선택**: 실패는 접수 이후 단계에서 일어나므로 원본은 저장돼 있다. 따라서 보호자가 모델 없이 원본 액자로 전시를 고를 수 있다. 원본을 읽을 수 없으면 이 선택지는 비활성화된다.
- **이야기 필수 항목**: 제목, 제작일, 제작 당시 연령은 전시에 필요한 필수 항목으로 본다. 원천에서 선택 입력으로 명시한 것은 아이의 한마디뿐이다.
- **품질 미달 기준**: 분리 품질 미달, 인물 미검출, 관절 추정 불가, 렌더 결과 없음, 깊이 품질 미달 같은 기준은 평가 묶음을 바탕으로 정한다(U5). 기준이 놓친 오인은 보호자 확인이 거른다.
- **모델 서빙 계층 언어**: 모델 기능 API는 R3에 따라 Python 가상환경 + uvicorn으로 제공한다. 보호자 앱 API와 같은 스택일지는 U7에서 정한다 [추론].
- **엔드포인트 이름**: 본문에 적은 `/v1/models/{…}`, `/live`, `/ready`, `/metrics`, `/openapi.json`은 Intent와 공통 기준에서 가져온 것이며, 최종 이름·형식은 `/speckit.plan`에서 OpenAPI로 확정한다(U8).
- **운영자·팀원 권한**: 팀원은 지표·상태·매니페스트·평가 묶음·API 문서만 보고, 가족의 이미지와 이야기에는 접근하지 않는다.

## Glossary

| Term | Definition |
|------|------------|
| 우리 아이 미술관 | 이 서비스의 이름. 파일명·식별자에서는 `우리아이미술관` |
| 움직이는 작품 | 사람·캐릭터 그림을 관절 추정·리깅해 원본 선 그대로 움직이게 만든 결과물(M3) |
| 2.5D 입체 부조 | 작품 마스크(M1)와 깊이 추정(M5)을 합쳐 도톰하게 떠오르는 시차 효과를 준 결과물. 원본의 선과 색은 바꾸지 않는다 |
| 원본 액자 | 올린 원본 사진을 액자 형태로 보여 주는 결과물. 모델 없이 만들며, 완성된 작품으로 대한다 |
| 3D 조각 (P1) | 만들기 작품을 3D로 복원해 GLB로 저장하고 회전해 보는 결과물(M7). 뒷면은 모델이 추정한다 |
| 작품 마스크 | 사진에서 배경을 걷어 내고 작품 영역만 표시한 결과(M1). 2.5D 마스크의 기본 출처 |
| 판정 제안 | M1·M2·M3·M4를 합쳐 전시 방식을 문구로 제안하는 것. 점수는 보이지 않으며 경로를 정하지 않는다 |
| 보호자 확정 | 보호자가 제안을 보고 전시 방식을 정하는 것. 처리 경로는 확정값으로 정한다 |
| 판정 수정률 | 보호자가 제안과 다르게 확정한 건의 비율 |
| 낮춤 체인 | 품질 미달 시 재시도 없이 한 단계 낮춘 결과로 가는 고정 순서. 움직임 → 2.5D → 액자, 3D → 2.5D → 액자, LLM 설명 → 템플릿 → 직접 입력 |
| 모델 낮춤 | 모델 품질 미달로 낮춤 체인을 따라 한 단계 낮춘 것. 인프라 실패와 섞지 않는다 |
| 결과 원인 5분류 | 보호자 선택 / 모델 낮춤 / 보호자 전환 / 인프라 실패 / 결과 미도달 |
| 오류 분류 | 인프라 장애 원인: 엔진 다운 / 시간 초과 / 저장소 / DB / 모델 미준비. 낮춤 원인과 섞지 않는다 |
| 결과 미도달 | 결과를 만드는 단계(움직임 렌더·깊이·부조·3D)에서 인프라 재시도(첫 시도 포함 최대 3회 시도)를 다 써서 "처리하지 못함"이 된 건. 목표 0 |
| 내구 접수 | 원본, 작품 기록, 처리 작업 기록이 모두 저장된 뒤에만 "접수 완료"로 응답하는 방식 |
| 단계 작업 | 작품 하나의 처리를 분리·판정·움직임 렌더·깊이·부조·설명·3D로 나눈 작업 단위. 모델 ID·버전·시도 횟수를 가진다 |
| 서빙 3종 | CPU 비전 워커(비동기 큐), GPU 워커(전용 큐·모델 상주), LLM 서버(짧은 동기·스트리밍) |
| 모델 어댑터 | API 서버가 모델을 직접 import하지 않도록 모델마다 두는 호출 계층 |
| 모델 매니페스트 | 모델 ID·가중치 SHA-256·런타임·이미지 다이제스트·설정 해시·활성/롤백 후보를 적은 버전 기록 |
| 평가 묶음 | 팀원이 직접 만든 사람·비인물·촬영 조건·입체 작품과 기대 경로, 설명 입력 세트. 모델 버전이 바뀔 때마다 재평가한다 |
| 승격 / 롤백 | 평가 묶음을 통과한 버전을 활성으로 바꾸는 것 / 직전 활성 후보로 되돌리는 것 |
| 템플릿 기준선 | LLM 없이 입력 필드로 채우는 설명 틀. 설명 낮춤의 도착점이자 설명 품질 비교 기준 |
| AI 작성 표시 | AI가 만든 설명임을 알리는 표시. 아이의 실제 말과 분리해 보인다 |
| 'API활용' 메뉴 | 엔드포인트·가이드라인·매뉴얼 3영역을 담은 팀원 전용 메뉴(추가 요구 R4) |
| 외부 모델 기능 엔드포인트 (P0.5) | 외부 클라이언트가 API 키로 분리·판정·관절·2.5D·설명 기능을 호출하는 경로 |
| 확정 대기 / 확인 대기 | 판정 제안이 나와 보호자 확정을 기다리는 상태 / 결과가 준비되어 보호자 선택을 기다리는 상태 |

| 보관 처리(archived) | 공개 저장소의 관리가 종료되어 업데이트와 보안 수정이 더 이상 없는 상태 |
