## Overview

> 작은 손이 남긴 선이, 우리 가족의 한 장면으로.

### Problem Statement

아이는 매일같이 그림을 그리지만, 가정에서는 그 그림을 오래 간직하고 다시 꺼내 보기 어렵다.

1. **보관 부담**: 종이 작품은 금방 쌓여 공간을 차지한다. 결국 버리거나 상자에 넣어 두고, 다시 찾아보지 않게 된다.
2. **맥락 유실**: 그림을 그릴 때 아이가 한 말, 아이의 나이, 그린 날짜가 따로 기록되지 않는다. 시간이 지나면 "무엇을 왜 그렸는지"가 사라진다.
3. **공동 감상의 부재**: 작품이 흩어져 있으면 가족이 함께 앉아 보며 이야기를 나눌 계기가 생기지 않는다.

이 서비스는 휴대폰으로 찍은 그림을 **움직이는 작품** 또는 **원본 액자**로 보관한다. 여기에 그날의 말과 제작 당시 나이를 함께 남겨, 가족이 함께 다시 보는 **가족용 미술관**을 만든다. 기술은 기억을 꾸며내지 않는다. 다시 꺼내 보는 수단일 뿐이다.

### 비전과 이번 범위(P0)의 위치

| 단계 | 내용 | 이번 명세 |
|------|------|-----------|
| 1. 디지털화 | 휴대폰 사진으로 작품 접수·원본 보존 | **P0 포함** |
| 2. 애니메이션화 | 사람 형태 그림을 움직이는 작품으로 변환, 불가하면 원본 액자 | **P0 포함** |
| 3. 이야기 | 부모가 제목·제작일·제작 당시 연령·아이의 한마디를 **직접** 입력 | **P0 포함** (직접 입력만) |
| 4. 전시 | 부모가 승인한 작품만 보이는 가족용 2D 전시 | **P0 포함** |
| 5. 키워드 기반 설명·큐레이션 | 키워드 → 설명 초안 → 부모 확인 → 작품 선정·배치 | 후속 |
| 6. 하이라이트 영화 | 부모가 고른 장면 → 순서·자막·음악 → 디지털 영화 | 후속 |
| 7. 3D 복원·3D 전시·실물 필름 | 별도 타당성 검토 | 후속 (P0를 밀어내지 않음) |

다음 세 가지는 서로 다른 것으로 구분한다. 사진 디지털화와 3D 복원은 다르다. 디지털 영화 완성과 실제 아날로그 필름 제작도 다르다. 3D 전시(화면 표현)와 3D 복원(형상 재구성)도 별개 기술이다.

### Target Users

| 사용자 | 특성 | 주요 니즈 |
|--------|------|-----------|
| **보호자(부모)** — 주 사용자·잠재 구매자(가설) | 아이 작품을 찍어 올리고, 결과를 확인·승인하고, 이야기를 입력하고, 작품을 삭제한다 | 작품을 한곳에 모아 정리 부담을 덜고, 아이의 말·나이와 함께 간직하며, 가족과 함께 감상한다 |
| **아이** — 주 수혜자, 결제 대상 아님 | 계정이 없으며 보호자와 함께 화면을 본다 | 자기 그림을 알아보고, 그 그림이 움직이는 즐거움을 경험한다. 움직이지 않는 액자도 완성된 작품으로 대접받는다 |
| **성장한 아이** — 장기 수혜자(후속 가치) | 어린 시절의 기록을 돌아보는 미래 사용자 | 그림·말·가족 이야기를 다시 만난다. 내보내기·권한 이전·보존 정책이 필요하며, P0에서 보장하지 않는다 |
| **서비스 운영자** | 서비스 상태와 운영 지표를 확인하는 팀원 | 이미지를 보지 않고도 모델 품질 문제와 인프라 장애를 구분하고, 결과가 사용자에게 도달하지 못한 건을 찾는다 |
| **평가 담당 팀원** | 직접 그린 평가 그림으로 품질을 점검하고 사용 흐름을 관찰한다 | 엔진 버전이 바뀔 때마다 같은 기준으로 다시 평가하고, 부모 역할 사용자가 막힌 지점을 기록한다 |

### Business Value

아래는 모두 **기대 혜택(가설)**이며, 검증 방법과 짝을 이룬다.

- **아이**: 자기 그림이 움직이는 것을 보는 즐거움과 작품에 대한 관심. 아이가 원본을 알아보는지, 스스로 다시 보고 싶어 하는지를 관찰한다. 발달 향상 효과는 주장하지 않는다.
- **부모**: 처치 곤란한 작품을 모아 보고, 찾는 수고를 줄이고, 아이와 이야기할 계기를 얻는다. 등록부터 전시까지 완료하는지, 특정 작품을 다시 찾을 수 있는지, 함께 감상한 맥락이 있는지를 확인한다.
- **서비스 팀**: 모델 품질 미달과 인프라 실패를 분리해 개선 우선순위를 정한다. 접수 이후 결과가 도달하지 않은 건을 추적한다.
- **차별화 가설**: 개별 기능은 이미 시장에 있다(보관 앱, 가상 갤러리, 원본 선 리깅). 차별점으로 가정하는 것은 "디지털화 → 움직임 → 이야기 → 영화"로 이어지는 **경험의 조합**이다. P0는 이야기 직접 입력과 2D 전시까지만 다룬다. 최초·유일, 흥미, 재방문, 지불 의향은 검증된 사실로 주장하지 않는다.

## Functional Requirements

> 요구사항 ID(FR-n)는 REQ → UC → 작업(T) → 검증 증거 추적의 출발점인 **REQ 식별자**다.

### Core Requirements (Mandatory)

#### FR-1: 아이 등록 (최소 수집)

**Description**: 보호자는 아이를 **별칭** 하나로만 등록한다. 실명, 생년월일, 출생연도는 받지 않고 저장하지도 않는다. 보호자 한 명이 여러 아이를 등록할 수 있다.

**Acceptance Criteria**:
- [ ] 아이 등록 화면에는 별칭 입력란만 있다. 실명·생년월일·출생연도 입력란은 없다
- [ ] 별칭은 같은 가족 안에서 서로 구분된다. 같은 가족 안에 같은 별칭을 두 번 등록하면 거절하고 이유를 안내한다
- [ ] 보호자는 아이를 2명 이상 등록하고, 작품을 올릴 때 어느 아이의 작품인지 고를 수 있다
- [ ] 별칭은 등록 후 수정할 수 있다

#### FR-2: 작품 사진 내구 접수

**Description**: 보호자는 휴대폰으로 찍었거나 기기에 저장된 그림 사진을 올린다. 시스템은 형식·용량·이미지 판독 가능 여부를 검사한다. 그다음 **원본, 작품 기록, 처리 작업 기록이 모두 저장에 성공한 경우에만** "접수 완료"로 응답한다. 하나라도 실패하면 접수하지 않은 것으로 처리한다. 저장이 일부만 된 흔적도 남기지 않는다.

**Acceptance Criteria**:
- [ ] 허용 형식 밖의 파일, 용량 상한을 넘는 파일, 이미지로 판독되지 않는 파일은 접수 전에 거절한다. 거절 이유(형식/용량/판독 불가)를 보호자가 이해할 수 있는 말로 안내한다
- [ ] 원본·작품 기록·작업 기록 중 하나라도 저장에 실패하면 보호자에게 "접수되지 않음"을 알리고 다시 올리도록 안내한다. 이때 저장이 일부만 된 원본이나 기록이 남지 않는다
- [ ] 접수 완료 응답을 받은 작품은 이후 서버가 재시작하거나 처리 담당이 실패해도 사라지지 않고, 최종 상태(확인 대기, 실패, 삭제 중 하나)에 도달한다
- [ ] 같은 올리기 요청이 네트워크 문제로 두 번 전송되어도 작품은 하나만 생긴다
- [ ] 원본은 올린 그대로 보존되며, 어떤 후속 처리도 원본을 덮어쓰거나 변형하지 않는다

#### FR-3: 부모 답변에 따른 처리 경로 결정

**Description**: 시스템은 작품을 올릴 때 보호자에게 "사람이나 팔다리가 있는 캐릭터 그림인가요?"라고 묻는다. 답에 따라 처리 경로가 정해진다.
- "예" → **움직임 경로**: 애니메이션 엔진 처리를 시도한다
- "아니요" → **원본 액자 경로**: 엔진을 시도하지 않고 원본 액자를 결과로 만든다. 이 경로는 애니메이션 엔진 없이 동작한다

**Acceptance Criteria**:
- [ ] 이 질문에 답하지 않으면 올리기를 마칠 수 없다
- [ ] "아니요"로 답한 작품은 엔진을 한 번도 거치지 않는다. 대체 분류는 "사람 그림 아님"으로 기록된다
- [ ] 애니메이션 엔진이 멈춘 상태에서도 원본 액자 경로의 작품은 접수부터 확인 대기까지 정상 진행된다
- [ ] 질문 옆에 짧은 예시 안내가 있다(사람·캐릭터 예시와 동물·사물·풍경 예시)

#### FR-4: 백그라운드 처리와 상태 조회

**Description**: 오래 걸리는 처리는 올리기 요청과 분리해 백그라운드에서 진행한다. 보호자는 기다리지 않고 화면을 떠날 수 있다. 나중에 작품별 진행 상태를 확인할 수 있다.

**Acceptance Criteria**:
- [ ] 접수 완료 응답은 엔진 처리가 끝나기를 기다리지 않는다
- [ ] 보호자는 작품별로 다음 상태 중 하나를 볼 수 있다: 접수됨 → 처리 중 → 확인 대기 / 실패. 확인 대기 이후에는 전시됨 / 다시 찍기로 닫힘 / 삭제 중으로 넘어간다
- [ ] 한 작품은 동시에 두 처리 담당이 중복 처리하지 않는다. 처리 담당이 중간에 멈추면 정해진 시간 뒤 다른 담당이 이어받는다
- [ ] 처리 중인 작품이 확인 대기나 실패로 바뀌면, 보호자가 다음에 작품 목록을 열 때 바뀐 상태가 보인다

#### FR-5: 결과 분류 — 정상 액자·품질 미달·인프라 실패의 분리

**Description**: 처리 결과는 아래처럼 서로 섞이지 않게 분류해 기록한다.

| 결과 | 조건 | 보호자에게 보이는 것 | 기록되는 분류 |
|------|------|------------------|----------------|
| 움직이는 작품 | 엔진이 정상 결과를 만듦 | 움직이는 작품 미리보기 | 결과 종류 = 움직임 |
| 원본 액자 (정상) | 보호자가 "사람 그림 아님"으로 답함 | 원본 액자 미리보기 | 대체 분류 = 사람 그림 아님 |
| 원본 액자 (품질 대체) | 엔진은 실행됐지만 결과가 품질 기준에 못 미침(인물 미검출, 관절 추정 불가 등) | 원본 액자 미리보기와 "움직임을 만들 수 없어 액자로 준비했어요" 안내 | 대체 분류 = 품질 미달 |
| 실패 | 엔진 다운, 시간 초과, 저장소·기록 장애가 제한된 재시도 뒤에도 계속됨 | "처리하지 못했어요" 안내와 선택지(FR-6) | 오류 분류 = 엔진 다운 / 시간 초과 / 저장소 / 기록(DB) |

**Acceptance Criteria**:
- [ ] 인프라 장애(엔진 다운·시간 초과·저장소·기록 장애)는 절대 "품질 미달 액자"로 바꿔 처리하지 않는다. 먼저 재시도하고, 재시도를 다 쓰면 실패로 알린다
- [ ] 모델 품질 미달은 재시도하지 않고 곧바로 원본 액자로 대체한다
- [ ] 인프라 장애 재시도는 작품당 정해진 최대 횟수를 넘지 않는다. 재시도를 다 쓴 건은 "결과 미도달"로 집계된다
- [ ] 처리 작업마다 요청 번호, 경로, 엔진 버전, 상태, 대체 분류 또는 오류 분류, 진단 이유(정해진 코드), 엔진 검출 점수(기록용), 단계별 소요 시간, 시도 횟수가 남는다
- [ ] 엔진 검출 점수는 기록만 하고 자동 전시나 승인의 근거로 쓰지 않는다(집 그림이 사람 점수 0.946으로 잡힌 사례 때문)

#### FR-6: 부모 확인 (승인 전 비전시)

**Description**: 모든 결과는 보호자가 확인해야만 전시된다. 확인 대기 상태의 작품에서 보호자가 고를 수 있는 것은 다음과 같다.

| 결과 | 선택지 |
|------|--------|
| 움직이는 작품 | **좋아요**(움직이는 작품으로 전시) / **액자로 걸기**(움직임 대신 원본 액자로 전시) / **다시 찍기** |
| 원본 액자(정상·품질 대체) | **액자로 걸기** / **다시 찍기** |
| 실패 | **액자로 걸기**(원본은 저장돼 있으므로 원본 액자로 전시) / **다시 찍기** |

**Acceptance Criteria**:
- [ ] 승인하지 않은 작품(확인 대기·실패·다시 찍기로 닫힘)은 가족 전시 화면 어디에도 나타나지 않는다
- [ ] "액자로 걸기"를 고르면 원본을 액자로 전시한다. 이미 만든 움직이는 결과는 전시하지 않는다. 대체 분류는 "부모 선택"으로 기록된다
- [ ] "다시 찍기"를 고르면 해당 건이 닫히고 새 올리기가 시작된다. 새 사진은 **새 작품·새 작업**으로 접수되며 이전 원본을 덮어쓰지 않는다
- [ ] 결과물은 처음 만든 것을 보관하고, 같은 원본으로 다시 만들지 않는다
- [ ] 보호자의 선택(좋아요/액자로 걸기/다시 찍기)은 해당 작업의 결과 종류·처리 원인과 연결되어 기록된다

#### FR-7: 이야기 직접 입력

**Description**: 보호자는 작품마다 **제목, 제작일, 제작 당시 연령**을 입력하고, 원하면 **아이의 한마디**를 덧붙인다. 입력한 말은 그대로 저장하고 그대로 보여 준다. 시스템이 문장을 만들거나, 고치거나, 감정을 해석하지 않는다.

**Acceptance Criteria**:
- [ ] 제목, 제작일, 제작 당시 연령을 모두 채워야 전시할 수 있다. 아이의 한마디는 비워도 된다
- [ ] 제작일은 오늘보다 뒤의 날짜일 수 없다. 제작 당시 연령은 정해진 범위의 정수(만 나이, 세)로만 받는다
- [ ] 아이의 한마디는 입력한 글자 그대로 저장되고 표시된다(자동 요약·교정·감정 태그 없음)
- [ ] 이야기는 부모 확인 전후 언제든 입력하고 수정할 수 있다. 수정 내용은 전시 화면에 곧바로 반영된다
- [ ] 이야기 입력은 처리 결과와 무관하다. 움직이는 작품과 원본 액자 모두 같은 항목을 가진다

#### FR-8: 가족용 2D 전시

**Description**: 가족은 승인된 작품만 모인 2D 전시 화면에서 작품을 한 점씩 골라 감상한다. 작품과 실제 말이 먼저 보이게 한다.

**Acceptance Criteria**:
- [ ] 전시 화면은 아이별로 나뉜다. 한 아이 안에서는 제작 당시 연령별로 묶이고, 묶음 안에서는 제작일 순서로 정렬된다
- [ ] 작품을 고르면 결과(움직이는 작품 또는 원본 액자)와 함께 제목, 제작일, 제작 당시 연령, 아이의 한마디가 보인다
- [ ] 움직이는 작품에서도 원본 사진을 볼 수 있다
- [ ] 움직이는 작품은 보호자가 고를 때만 재생되고, 정지할 수 있다. 다음 작품으로 저절로 넘어가거나 끝없이 이어지는 피드는 없다
- [ ] 원본 액자는 움직이는 작품과 같은 크기와 대우로 전시되며, "실패"나 "대체" 같은 표시를 붙이지 않는다
- [ ] 과도한 필터나 꾸밈 효과, 발달 점수, 아이 간 비교 표시는 없다
- [ ] 보호자는 제목이나 제작일로 특정 작품을 다시 찾을 수 있다

#### FR-9: 가족 단위 접근 권한

**Description**: 작품, 이야기, 아이 정보는 해당 가족만 볼 수 있다. 가족 구성원의 접근 범위는 다음과 같다. [NEEDS CLARIFICATION: P0에서 한 가족 공간에 접근하는 계정 모델은? (a) 보호자 계정 1개만 두고, 공동 감상은 같은 화면을 함께 보는 방식 / (b) 공동 보호자 계정을 초대해 같은 권한으로 관리 / (c) 관리 보호자 1명 + 감상 전용 가족 초대]

**Acceptance Criteria**:
- [ ] 다른 가족의 작품·원본·결과·이야기는 목록, 상세, 직접 주소 입력 어떤 경로로도 볼 수 없다
- [ ] 로그인하지 않은 사용자는 어떤 작품도 볼 수 없다
- [ ] 서비스 운영자는 운영 화면과 지표에서 가족의 원본이나 결과 이미지를 볼 수 없다
- [ ] 작품 삭제와 아이 삭제는 보호자만 할 수 있다

#### FR-10: 삭제와 실행 중 취소

**Description**: 보호자는 작품 하나 또는 아이 한 명(그 아이의 모든 작품 포함)을 삭제할 수 있다. 시스템은 새 처리를 막고, 진행 중인 처리가 끝났거나 취소됐음을 확인한다. 그다음 원본, 결과, 임시 파일을 지운다. 처리 작업 기록에서는 작품과의 연결, 저장 위치, 자유 입력(제목·한마디 등)을 제거하고 집계용 필드만 남긴다.

**Acceptance Criteria**:
- [ ] 삭제를 요청하면 해당 작품은 곧바로 전시와 목록에서 사라진다. 그 작품의 새 처리는 시작되지 않는다
- [ ] 처리 중인 작품을 삭제하면 진행 중인 처리를 취소한다. 처리가 멈춘 것을 확인한 뒤에 파일을 지운다. 취소 이후 결과 파일이 새로 생기지 않는다
- [ ] 삭제가 끝나면 원본, 결과, 임시 파일이 모두 남아 있지 않다
- [ ] 삭제 후 남는 작업 기록에는 작품·아이와의 연결, 저장 위치, 자유 입력이 없고 집계 필드(경로, 결과 종류, 분류, 단계별 시간, 시도 횟수, 엔진 버전)만 있다
- [ ] 삭제 도중 일부가 실패하면 삭제를 자동으로 다시 시도한다. 끝내 완료되지 않은 건은 운영자에게 "삭제 미완료"로 집계되어 보인다(이미지와 식별 정보는 제외)
- [ ] 아이를 삭제하면 그 아이의 모든 작품에 위 규칙이 적용된다
- [ ] 백업에 남는 사본의 보존·삭제는 P0 범위 밖이며, 운영 전에 결정할 항목으로 명시한다

#### FR-11: 임시 파일 정리

**Description**: 처리 중에 생긴 임시 파일은 처리가 끝나면(성공, 품질 대체, 실패, 취소 모두) 지운다. 비정상 종료로 남은 임시 파일은 주기적으로 정리한다.

**Acceptance Criteria**:
- [ ] 처리가 끝난 작업의 임시 파일은 정해진 시간 안에 남아 있지 않다
- [ ] 처리 담당이 비정상 종료한 뒤 남은 임시 파일은 다음 정리 주기에 지워진다

#### FR-12: 서비스 생존·준비 상태 확인

**Description**: 운영자는 서비스가 살아 있는지(생존)와 작품을 받아 처리할 준비가 됐는지(준비)를 따로 확인할 수 있다.

**Acceptance Criteria**:
- [ ] 생존 확인은 서비스 프로세스가 응답하는지만 알려 준다
- [ ] 준비 확인은 원본 저장소, 작품·작업 기록 저장소, 처리 대기열 중 하나라도 쓸 수 없으면 "준비 안 됨"을 알린다
- [ ] 애니메이션 엔진만 멈춘 경우 준비 확인은 "엔진 불가"를 따로 표시한다. 이때 접수와 원본 액자 경로는 계속 동작한다

#### FR-13: 운영 지표

**Description**: 운영자는 아래 서빙 지표를 이미지나 식별 정보 없이 볼 수 있다.

| 지표 | 정의 |
|------|------|
| 첫 결과 승인율 | 좋아요 ÷ (좋아요 + 액자 전환 + 다시 찍기). 첫 결과가 움직이는 작품인 건만 대상 |
| 비인물 액자율 | 엔진을 시도하지 않은 액자 ÷ 접수 완료 |
| 모델 품질 대체율 | 품질 미달 액자 ÷ 엔진 시도 |
| 재시도율 | 인프라 재시도가 1회 이상 발생한 작업 ÷ 엔진 시도 |
| 미리보기 시간 p95 | 접수 완료부터 확인 대기까지 걸린 시간의 95백분위 |
| 결과 미도달 수 | 재시도를 다 쓴 건. 목표는 0 |

**Acceptance Criteria**:
- [ ] 여섯 지표를 기간별로 볼 수 있다
- [ ] 지표 계산에서 정상 액자(사람 그림 아님), 품질 미달 액자, 부모 선택 액자, 인프라 실패가 서로 다른 항목으로 집계된다
- [ ] 결과 미도달 건은 요청 번호로 개별 추적할 수 있다(이미지·저장 위치·자유 입력 제외)
- [ ] 지표 화면과 지표 데이터에는 이미지, 저장 위치, 별칭, 제목, 한마디가 없다

#### FR-14: 아동 정보 보호 원칙

**Description**: 아동의 그림과 사진에는 이름, 유치원, 얼굴이 담길 수 있으므로, 이를 전제로 보호한다.

**Acceptance Criteria**:
- [ ] 운영 로그에는 이미지, 저장 위치 키, 사용자가 입력한 자유 텍스트, 가공되지 않은 오류 원문을 남기지 않는다. 오류는 정해진 분류 코드와 요청 번호로만 남긴다
- [ ] 얼굴 인식 기능이 없다
- [ ] 올린 그림과 결과물을 모델 학습이나 다른 목적에 재사용하지 않는다
- [ ] 가족의 기록을 외부 업체에 자동으로 전달하지 않는다
- [ ] 애니메이션 엔진은 외부 네트워크에서 직접 접근할 수 없다

#### FR-15: 자원 상한

**Description**: 과소비와 장애 전파를 막기 위해 처리 자원에 상한을 둔다.

**Acceptance Criteria**:
- [ ] 파일 용량 상한, 동시 처리 수 상한, 작업당 처리 시간 상한, 인프라 재시도 횟수 상한이 정해져 있다. 상한을 넘으면 정해진 방식(거절, 대기, 시간 초과 실패)으로 처리된다
- [ ] 처리 시간 상한을 넘긴 작업은 "시간 초과"로 분류되어 재시도 규칙을 따른다
- [ ] 동시 처리 상한에 도달하면 새로 접수된 작품은 거절되지 않고 대기열에서 순서를 기다린다

### Secondary Requirements (검증·운영 요구사항)

#### FR-16: 애니메이션 엔진 재현과 교체 가능성

**Description**: 핵심 엔진은 관리가 종료(보관 처리)된 공개 저장소이므로 조건부로 채택한다. 팀 서버에서 반복 재현해 검증한다. 엔진을 바꾸더라도 가족이 쓰는 흐름은 달라지지 않아야 한다.

**Acceptance Criteria**:
- [ ] 팀 서버에서 엔진 설치·실행을 재현하고 버전, 소요 시간, 메모리, 오인 사례를 기록한다
- [ ] 처리 작업마다 엔진 버전이 기록된다
- [ ] 엔진을 예비안으로 바꿔도 접수, 부모 확인, 이야기, 전시, 삭제 흐름과 화면은 바뀌지 않는다
- [ ] 엔진의 관리 기능과 외부 포트는 닫혀 있고, 검증된 고정 실행 환경으로 격리되어 있다

#### FR-17: 평가 그림 세트

**Description**: 팀원이 직접 그린 사람, 동물, 사물 그림과 각 그림의 기대 경로(움직임/원본 액자)를 평가 세트로 관리한다. 엔진 버전이 바뀔 때마다 다시 평가한다. 시연과 평가에는 팀원이 직접 그린 그림만 쓴다.

**Acceptance Criteria**:
- [ ] 평가 세트의 그림마다 종류(사람/동물/사물)와 기대 경로가 기록되어 있다
- [ ] 엔진 버전을 바꾸면 전체 평가 세트를 다시 실행하고, 기대 경로와 달라진 건을 목록으로 남긴다
- [ ] 평가 기록에는 오인 사례(예: 사물을 사람으로 잡아 관절을 붙인 경우)가 분류되어 남는다

#### FR-18: 사용 관찰 기록

**Description**: 부모 역할 사용자가 등록 → 확인 → 전시를 수행하는 과정과 막힌 지점을 직접 관찰해 기록한다. 실제 아동 참여 관찰은 적절한 동의와 수집 조건이 확정된 뒤에만 한다.

**Acceptance Criteria**:
- [ ] 관찰 세션마다 완료 여부, 막힌 단계, 막힌 이유, 다시 보기 행동과 그 이유가 기록된다
- [ ] 동의·수집 조건이 확정되기 전에는 실제 아동을 관찰 대상에 포함하지 않는다
- [ ] 짧은 시연 결과를 장기 보관 가치의 증거로 보고하지 않는다

#### FR-19: 추적성

**Description**: 이 명세의 요구사항은 유스케이스, 작업, 검증 증거로 추적된다.

**Acceptance Criteria**:
- [ ] 모든 FR은 하나 이상의 유스케이스에 연결되고, 유스케이스는 작업과 검증 증거에 연결된다(REQ → UC → T → 증거)
- [ ] 유스케이스 명세의 공식 서식 검증은 참조 14속성 원본 서식을 확보하기 전에는 "완료"로 표시하지 않는다

## User Scenarios & Testing

### Primary User Flow

1. 보호자가 로그인하고 아이를 별칭으로 등록한다(최초 1회).
2. 보호자가 아이를 고르고 그림 사진을 올린다. "사람이나 캐릭터 그림인가요?"에 답한다.
3. 시스템이 파일을 검사한다. 원본, 작품 기록, 작업 기록을 모두 저장한 뒤 "접수 완료"를 알린다.
4. 보호자는 화면을 떠나도 된다. 백그라운드에서 움직임 경로 또는 원본 액자 경로가 처리된다.
5. 작품 상태가 "확인 대기"로 바뀐다. 보호자가 미리보기를 보고 좋아요 / 액자로 걸기 / 다시 찍기 중 하나를 고른다.
6. 보호자가 제목, 제작일, 제작 당시 연령을 입력하고, 원하면 아이의 한마디를 입력한다.
7. 승인된 작품이 아이별·연령별 2D 전시 화면에 나타난다. 가족이 함께 한 점씩 골라 감상한다.
8. 필요하면 보호자가 작품이나 아이를 삭제한다.

### Acceptance Scenarios

#### Scenario 1: 사람 그림이 움직이는 작품으로 전시됨
**Given**: 아이 "하늘"이 등록된 보호자
**When**: 사람 그림을 올리고 "예"라고 답한 뒤, 확인 대기 상태에서 "좋아요"를 누르고 제목·제작일·연령을 입력한다
**Then**: "하늘"의 전시 화면에서 해당 연령 묶음에 움직이는 작품이 보인다. 작품을 고르면 재생되고, 원본과 이야기도 함께 보인다

#### Scenario 2: 사물 그림은 엔진 없이 원본 액자로
**Given**: 애니메이션 엔진이 멈춘 상태
**When**: 보호자가 집 그림을 올리고 "아니요"라고 답한다
**Then**: 작품이 확인 대기에 도달하고 원본 액자 미리보기가 보인다. 작업 기록의 대체 분류는 "사람 그림 아님", 엔진 시도는 0회다

#### Scenario 3: 오인된 움직임을 부모가 거름
**Given**: 보호자가 사물 그림에 "예"라고 잘못 답했고, 엔진이 벽에 관절을 붙인 어색한 움직임을 만들었다
**When**: 보호자가 확인 대기 화면에서 "액자로 걸기"를 누른다
**Then**: 전시에는 원본 액자만 나타나고, 어색한 움직임은 어디에도 전시되지 않는다. 작업의 대체 분류는 "부모 선택"이다

#### Scenario 4: 모델 품질 미달은 원본 액자로 대체
**Given**: 보호자가 "예"라고 답했지만 엔진이 인물을 찾지 못했다
**When**: 처리가 끝난다
**Then**: 재시도 없이 원본 액자 미리보기와 안내 문구가 보인다. 대체 분류는 "품질 미달", 오류 분류는 비어 있다

#### Scenario 5: 인프라 장애는 재시도 후 실패로 알림
**Given**: 처리 중 저장소 장애가 계속된다
**When**: 인프라 재시도가 최대 횟수에 도달한다
**Then**: 보호자에게 "처리하지 못했어요"와 함께 "액자로 걸기 / 다시 찍기" 선택지가 보인다. 오류 분류는 "저장소"로 기록되고, 결과 미도달 수가 1 늘어난다. "품질 미달"로는 집계되지 않는다

#### Scenario 6: 접수 중 저장 실패 시 접수하지 않음
**Given**: 원본 저장은 성공했지만 작업 기록 저장이 실패한다
**When**: 보호자가 올리기를 마친다
**Then**: 보호자에게 "접수되지 않았어요. 다시 올려 주세요"가 보인다. 목록에 해당 작품이 없고, 저장된 원본도 남지 않는다

#### Scenario 7: 다시 찍기
**Given**: 흐리게 찍힌 사진의 결과가 확인 대기 상태다
**When**: 보호자가 "다시 찍기"를 누르고 새 사진을 올린다
**Then**: 새 사진은 새 작품·새 작업으로 접수되고, 이전 원본은 덮어쓰이지 않는다. 이전 건은 전시되지 않는다

#### Scenario 8: 처리 중 삭제
**Given**: 움직임 처리가 진행 중인 작품
**When**: 보호자가 작품을 삭제한다
**Then**: 작품이 즉시 목록에서 사라진다. 진행 중이던 처리가 취소되고, 멈춘 것이 확인된 뒤 원본·결과·임시 파일이 모두 지워진다. 작업 기록에는 집계 필드만 남는다

#### Scenario 9: 다른 가족 작품 접근 차단
**Given**: 가족 A의 보호자가 로그인해 있다
**When**: 가족 B의 작품 주소를 직접 입력한다
**Then**: 작품이 보이지 않고 접근이 거부된다. 원본·결과·이야기 어느 것도 노출되지 않는다

#### Scenario 10: 승인 전 비전시
**Given**: 확인 대기인 움직이는 작품 1건과 전시된 작품 3건
**When**: 가족이 전시 화면을 연다
**Then**: 전시된 3건만 보이고, 확인 대기 작품은 보이지 않는다

#### Scenario 11: 운영자의 원인별 지표 확인
**Given**: 한 주 동안 정상 액자, 품질 미달, 부모 선택 액자, 인프라 실패가 섞여 발생했다
**When**: 운영자가 지표 화면을 연다
**Then**: 네 가지가 서로 다른 항목으로 보이고, 결과 미도달 건은 요청 번호로 추적된다. 화면에 이미지·별칭·제목·한마디는 없다

### Edge Cases

- **허용 형식이지만 깨진 파일**: 판독 검사에서 거절하고 "사진을 열 수 없어요"라고 안내한다. 접수하지 않는다.
- **같은 요청의 중복 전송**: 작품은 하나만 생성된다(FR-2).
- **처리 담당의 중도 정지**: 정해진 시간이 지나면 다른 담당이 이어받는다. 이어받기도 시도 횟수에 포함되고, 상한을 넘으면 실패로 처리된다.
- **엔진만 멈춘 상태**: 접수와 원본 액자 경로는 동작한다. 움직임 경로는 재시도 규칙을 따른 뒤 실패로 알린다. 준비 상태 확인에 "엔진 불가"가 표시된다.
- **엔진이 사람 점수는 높지만 사람이 아닌 그림을 처리**: 점수는 기록만 한다. 부모 확인 없이는 전시되지 않는다.
- **이야기를 입력하지 않고 승인만 누름**: 승인 선택은 기록되지만, 필수 이야기 항목을 채우기 전까지 전시되지 않는다. 보호자에게 "이야기를 채우면 전시돼요"라고 안내한다.
- **미래 제작일 또는 범위 밖 연령**: 입력을 거절하고 이유를 안내한다.
- **다시 찍기 후 새 사진을 올리지 않음**: 이전 건은 닫힌 채 전시되지 않는다. 새 작품은 생기지 않는다.
- **실패 건에서 원본까지 읽을 수 없는 경우**(저장소 장애 지속): "액자로 걸기"를 비활성화하고 "다시 찍기"만 제공한다.
- **삭제 중 일부 파일 삭제 실패**: 자동으로 다시 시도한다. 끝내 완료되지 않으면 운영 지표에 "삭제 미완료"로 보인다.
- **아이 삭제 시 처리 중인 작품 포함**: 해당 작품마다 취소를 확인한 뒤 삭제한다.
- **동시 처리 상한 도달**: 새 작품은 대기열에서 순서를 기다린다. 대기 시간도 미리보기 시간 p95에 포함된다.

## Success Criteria

> 아래 목표값은 P0 **검증 목표**다. 달성 실적이 아니며, 성능 수치는 팀 서버 재현 시험 뒤 확정한다.

### Quantitative Metrics

- **결과 미도달 수**: 검증 기간 동안 0건
- **승인 전 전시**: 확인 대기·실패·다시 찍기 상태의 작품이 전시 화면에 노출된 건수 0건(자동 시험과 관찰로 확인)
- **원본 변형**: 후속 처리로 원본이 덮어쓰이거나 변형된 건수 0건
- **원인 분리 정확도**: 장애 주입 시험(엔진 정지, 시간 초과, 저장소 장애, 기록 장애)에서 인프라 장애가 "품질 미달"로 집계되는 건수 0건. 각 장애가 해당 오류 분류로 100% 기록됨
- **비인물 경로 결정성**: "아니요"로 답한 작품 중 엔진을 시도한 건수 0건
- **삭제 완전성**: 삭제 시험(처리 중 삭제 포함)에서 삭제 완료 후 남은 원본·결과·임시 파일 0건, 남은 작업 기록의 작품 연결·저장 위치·자유 입력 0건
- **로그 정보 보호**: 운영 로그 표본 점검에서 이미지, 저장 위치 키, 자유 입력, 오류 원문 0건
- **접근 차단**: 가족 간 교차 접근 시험에서 노출 0건
- **미리보기 시간 p95**: 팀 서버 단일 처리 조건에서 접수부터 확인 대기까지 3분 이내(잠정 목표. 1차 개인 PC 실측은 한 장당 53~62초이며, 동시 처리 조건의 목표는 부하 시험 후 확정)
- **원본 액자 경로 시간**: "아니요" 경로의 접수부터 확인 대기까지 p95 30초 이내
- **부모 작업 완료율**: 관찰 세션에서 부모 역할 사용자의 80% 이상이 도움 없이 등록 → 확인 → 이야기 입력 → 전시를 끝냄
- **부모 조작 시간**: 처리 대기 시간을 빼고, 작품 한 점을 올리고 확인하고 이야기를 입력하는 데 3분 이내
- **다시 찾기**: 전시된 작품 20점 이상 중 지정한 작품을 30초 안에 찾음
- **첫 결과 승인율·비인물 액자율·모델 품질 대체율·재시도율**: 목표값을 정하지 않는다. 기간별로 측정하고 원인별로 분해해, 엔진 버전과 경로 개선의 기준선으로 쓴다

### Qualitative Measures

- **작품 알아보기**: 부모 역할 사용자가 움직이는 결과에서 원본의 선과 색을 알아볼 수 있다고 답하는지, 관찰과 짧은 인터뷰로 확인한다. 아동 관찰은 동의 조건 확정 후에만 한다.
- **액자의 완성감**: 원본 액자가 "실패작"이 아닌 완성된 작품으로 느껴지는지 부모 역할 사용자 인터뷰로 확인한다.
- **공동 감상 맥락**: 가족이 원본과 이야기를 함께 보는 장면이 관찰되는지, 어떤 계기로 다시 보는지를 기록한다. 재열람을 장기 보관 가치의 증거로 확대하지 않는다.
- **막힌 지점**: 관찰 기록에서 반복되는 막힘을 모아 개선 목록을 만든다.
- **평가 세트 결과**: 엔진 버전별로 기대 경로와 달라진 건과 오인 사례 목록이 남아, 버전 채택 여부를 판단할 수 있다.

## Key Entities

### Entity: 가족(보호자 계정)
**Attributes**:
- 보호자 식별자: 로그인 주체
- 가족 공간: 작품, 아이, 이야기의 접근 경계

**Relationships**:
- 가족 1 : 아이 N

### Entity: 아이
**Attributes**:
- 별칭: 보호자가 정함, 가족 안에서 서로 구분됨, 등록 시 1회 입력(수정 가능)
- (저장하지 않음): 실명, 생년월일, 출생연도

**Relationships**:
- 아이 1 : 작품 N

### Entity: 작품
**Attributes**:
- 제목, 제작일, 제작 당시 연령(만 나이 정수), 아이의 한마디(선택, 입력한 그대로)
- 원본 저장 위치: 변경 불가
- 처음 만든 결과의 저장 위치, 결과 종류(움직임 / 원본 액자)
- 부모 선택: 좋아요 / 액자로 걸기 / 다시 찍기
- 전시 상태: 확인 대기 / 전시됨 / 닫힘 / 삭제 중

**Relationships**:
- 작품 1 : 처리 작업 1 이상(다시 찍기는 새 작품을 만들므로 같은 원본으로 결과를 다시 만들지 않음)

### Entity: 처리 작업
**Attributes**:
- 요청 번호, 경로(움직임 / 원본 액자), 엔진 버전, 상태
- 대체 분류: 사람 그림 아님 / 품질 미달 / 부모 선택
- 오류 분류(대체 분류와 별개): 엔진 다운 / 시간 초과 / 저장소 / 기록(DB)
- 진단 이유(정해진 코드), 엔진 검출 점수(기록용), 단계별 소요 시간, 시도 횟수

**Relationships**:
- 요청마다 생성된다. 작품이 삭제되면 작품 연결, 저장 위치, 자유 입력을 지우고 집계 필드만 남긴다

### Entity: 평가 그림
**Attributes**:
- 종류(사람 / 동물 / 사물), 기대 경로, 제작자(팀원), 평가 결과(엔진 버전별)

**Relationships**:
- 엔진 버전이 바뀔 때마다 전체를 다시 평가한다

### Entity: 운영 지표
**Attributes**:
- 첫 결과 승인율, 비인물(정상) 액자율, 모델 품질 대체율, 재시도율, 미리보기 시간 p95, 결과 미도달 수, 삭제 미완료 수

**Relationships**:
- 처리 작업의 집계 필드에서 계산한다. 이미지와 식별 정보는 포함하지 않는다

## Constraints & Boundaries

### In Scope
- 별칭만 받는 아이 등록
- 작품 사진 내구 접수(검사 → 원본·작품·작업 기록 저장 성공 후 접수 완료)
- 부모 답변 기반 경로 결정, 백그라운드 처리, 상태 조회
- 움직이는 작품 / 원본 액자(정상·품질 대체) / 인프라 실패(제한 재시도)의 분리
- 부모 확인(좋아요·액자로 걸기·다시 찍기)과 승인 전 비전시
- 이야기 직접 입력(제목·제작일·제작 당시 연령·선택형 한마디)
- 아이별·연령별 가족용 2D 전시
- 가족 단위 접근 권한, 작품·아이 삭제, 실행 중 취소, 임시 파일 정리
- 생존·준비 상태 확인, 운영 지표
- 엔진 재현 검증, 평가 그림 세트, 사용 관찰, 추적성 관리

### Out of Scope (후속 검증 범위)
- 키워드 입력, 설명 초안 생성, 큐레이션(작품 선정·배치)
- 하이라이트 영화(장면 선택, 순서, 자막, 음악)
- 3D 복원, 3D 전시, 실물 필름 제작·주문
- 결제, 구독, 가격 실험
- 촬영 보정(원근 보정·작품 영역 자동 자르기)
- 내보내기, 성장 후 접근권한 이전, 장기 보관 기간 정책, 서비스 종료 시 이관
- 상용화용 법정대리인 동의 절차(고지·확인·보유 기간·철회)
- 백업 사본의 보존·삭제 정책
- 유치원·미술학원 등 기관용 다아동 권한
- 외부 업체(알림장 앱, 인화·필름 업체) 연동

### Constraints
- **승인 전 비전시**: 부모 승인 없이 어떤 결과도 전시하지 않는다.
- **원본 불변**: 원본을 덮어쓰거나 변형하지 않는다. 결과물은 처음 만든 것을 보관하고 다시 만들지 않는다.
- **최소 수집**: 실명, 생년월일, 출생연도를 받지 않는다. 아이의 한마디는 선택 입력이다.
- **동의 오판 금지**: 보호자 계정이 있다고 해서 법정대리인 확인이 끝났다고 보지 않는다. 실제 아동 데이터를 운영에 쓰기 전에 동의 절차를 확정해야 한다.
- **시연 데이터**: 시연과 평가에는 팀원이 직접 그린 그림만 쓴다.
- **기억 왜곡 금지**: 시스템은 입력에 없는 사건, 감정, 발달 상태를 만들지 않는다. 자동 감정 해석, 발달 평가, 아이 간 비교를 하지 않는다.
- **과도한 화면 소비 억제**: 자동 반복과 무한 피드 대신, 가족이 골라서 감상하는 흐름을 둔다.
- **약속 금지**: 무료, 무제한, 평생 보관을 약속하지 않는다. 짧은 시연을 장기 가치의 증거로 제시하지 않는다.
- **관리 종료 엔진의 조건부 채택**: 핵심 엔진과 그 모델 실행 구성요소는 보안 업데이트가 없다. 외부 접근을 차단하고, 고정 실행 환경으로 격리하고, 교체할 수 있게 둬야 한다(FR-16).

## Dependencies

### External Dependencies
- **Meta Animated Drawings**: 사람 형태 그림의 검출, 관절 추정, 리깅, 렌더를 맡는 핵심 엔진. 코드와 가중치는 MIT 라이선스이며, 2025-09-03 보관 처리되었다.
- **엔진의 모델 실행 구성요소(TorchServe)**: 2025-08-07 보관 처리되어 예정된 보안 수정이 없다. 내부 네트워크로 격리한다.
- **검출·자세 추정 구성요소(OpenMMLab MMDetection·MMPose)**: Apache 2.0 라이선스.
- **예비 엔진 후보**: 그림 전용 자세 모델(가중치 AGPL-3.0)과 rtmlib(Apache-2.0). 라이선스 영향은 채택할 때 검토한다.
- **팀 서버와 원본·결과 저장소**: 실제 연산 자원, 메모리, 비용은 재현 시험 뒤 확정한다.
- 공개 저장소는 공급 의존성일 뿐 협력 계약이 아니다. 현재 계약되거나 확보된 외부 파트너는 없다.

### Internal Dependencies
- 유스케이스 문서화(개요 → 개별 정상·대체·예외 흐름 → 검토. 원천 추적, 업무규칙, 유스케이스·시퀀스 다이어그램 포함)
- 팀 서버에서의 엔진 반복 재현 결과(버전, 시간, 메모리, 오인 사례)
- 팀원이 그린 평가 그림 세트
- 기술 선택의 정본 문서: `기술_유사서비스_리서치.md`
- 역할 묶음(엔진 담당, 백엔드, 화면, 검증)과 담당자·공식 기한·서버 문서 대상 확인

## Assumptions

- **대상 규모**: P0는 팀 내부 검증용이다. 부모 역할 사용자(팀원)가 직접 그린 그림으로 사용한다. 동시 사용자는 소수(10명 이하)로 가정한다.
- **접근 방식**: 보호자는 휴대폰 웹 브라우저로 사진을 올리고 전시를 본다. 로그인은 일반적인 계정 로그인 방식을 쓴다.
- **허용 형식·용량(기본값)**: 휴대폰 사진의 일반 형식(JPEG, PNG, HEIC). 한 장 20MB 이하. 계획 단계에서 조정할 수 있다.
- **재시도·시간 상한(기본값)**: 인프라 장애는 작품당 최대 3회 시도하고, 시도 사이 간격을 점점 늘린다. 작업당 처리 시간 상한은 10분이다. 동시 처리 수 상한은 팀 서버 재현 시험 뒤 정한다.
- **제작 당시 연령**: 만 나이 정수(0~18세)로 받는다. 아동기 이후 작품도 막지 않는다.
- **첫 결과 승인율의 모수**: 첫 결과가 움직이는 작품인 건만 대상으로 한다. 원본 액자로 시작한 건은 "좋아요" 선택지가 없기 때문이다.
- **다시 찍기로 닫힌 건의 파일**: 최소 보관 원칙에 따라 다시 찍기로 닫힌 건의 원본과 결과는 삭제 규칙(FR-10)과 같은 방식으로 지우고, 집계 필드만 남긴다.
- **실패 건의 액자 선택**: 실패는 접수 이후 단계에서 일어나므로 원본은 저장돼 있다. 따라서 보호자가 원본 액자로 전시를 고를 수 있다. 원본을 읽을 수 없으면 이 선택지는 비활성화된다.
- **이야기 필수 항목**: 제목, 제작일, 제작 당시 연령은 전시에 필요한 필수 항목으로 본다. 원천에서 선택 입력으로 명시한 것은 아이의 한마디뿐이다.
- **품질 미달 판정 기준**: 인물 미검출, 관절 추정 불가, 렌더 결과 없음 같은 판정 기준은 평가 그림 세트를 바탕으로 계획 단계에서 정한다. 판정이 놓친 오인은 부모 확인이 거른다.
- **운영자 권한**: 운영자는 지표와 상태만 보고, 가족의 이미지와 이야기에는 접근하지 않는다.

## Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| 엔진 재현 실패·설치 붕괴: 원본 그대로 설치되지 않았고(기반 시스템 저장소가 내려가 보관 저장소로 우회), 빌드 약 36분, 설치 크기 32.9GB | High | High | 팀 서버 반복 재현, 운영 전 기반 교체, 예비 엔진 후보 유지, 교체 가능 구조(FR-16) |
| 모델 실행 구성요소의 보안 공백(보관 처리, 보안 수정 없음) | High | Medium | 외부 포트와 관리 기능 차단, 고정 실행 환경 격리, 내부 네트워크 한정 |
| 오인 움직임이 완료처럼 보임(집 그림 사람 점수 0.946으로 벽에 관절이 붙음) | High | High | 올릴 때 부모에게 질문, 점수를 승인 근거로 쓰지 않음, 부모 확인 필수, 원본 액자 전환 |
| 처리 시간·자원 부족(CPU 4코어·3.8GB에서 한 장 53~62초, 그중 렌더 약 40초, 모델 서버 약 3.1GB) | Medium | High | 백그라운드 처리, 동시 처리·시간 상한, 팀 서버 부하 시험 뒤 목표 확정 |
| 모델 실패와 저장소·기록 장애가 섞여 원인 파악 불가 | Medium | Medium | 대체 분류와 오류 분류 분리(FR-5), 장애 주입 시험 |
| 아동 개인정보 노출(원본에 이름·유치원·얼굴) | High | Medium | 가족 단위 격리, 로그에 이미지·위치·자유 입력 금지, 얼굴 인식·학습 재사용 금지, 운영자 이미지 접근 차단 |
| 동의 오판(보호자 계정 = 법정대리인 확인으로 간주) | High | Medium | P0는 팀원 그림만 사용, 실제 아동 참여는 동의 조건 확정 뒤, 상용화 전 절차 확정 |
| 삭제 누락(실행 중 작업, 임시 파일, 백업) | High | Medium | 새 작업 차단 → 취소 확인 → 삭제 순서, 임시 파일 주기 정리, 삭제 미완료 집계, 백업 정책은 운영 전 결정 |
| 범위 확장(3D·영화 구현이 핵심 서빙 범위를 밀어냄) | Medium | Medium | Out of Scope 명시, P0 완료 전 후속 착수 금지 |
| 시장 차별점 부재·결제 의향 미검증 | Medium | High | 차별화를 경험 조합 가설로 한정, P0는 경험 검증에 집중, 결제는 범위 밖 |
| 장기 보관에 대한 기대(평생 보관 오해) | Medium | Medium | 평생 보관 약속 금지, 내보내기·이관·삭제 정책을 운영 전 설계 항목으로 명시 |

## Glossary

| Term | Definition |
|------|------------|
| 움직이는 작품 | 사람 형태 그림을 검출, 관절 추정, 리깅해 움직이게 만든 결과물 |
| 원본 액자 | 올린 원본 사진을 액자 형태로 보여 주는 결과물. 움직이지 않아도 완성된 작품으로 대한다 |
| 내구 접수 | 원본, 작품 기록, 처리 작업 기록이 모두 저장된 뒤에만 "접수 완료"로 응답하는 방식 |
| 대체 분류 | 움직이는 작품 대신 원본 액자가 된 이유: 사람 그림 아님 / 품질 미달 / 부모 선택 |
| 오류 분류 | 인프라 장애 원인: 엔진 다운 / 시간 초과 / 저장소 / 기록(DB). 대체 분류와 섞지 않는다 |
| 결과 미도달 | 인프라 재시도를 다 써서 결과가 보호자에게 도달하지 못한 건 |
| 확인 대기 | 결과가 준비되어 보호자의 좋아요 / 액자로 걸기 / 다시 찍기를 기다리는 상태 |
| 제작 당시 연령 | 작품을 그린 시점의 아이 나이(만 나이 정수). 출생연도 없이 작품마다 입력한다 |
| 생존 / 준비 상태 | 서비스가 응답하는지(생존)와 작품을 받아 처리할 수 있는지(준비)를 구분한 상태 확인 |
| 보관 처리(archived) | 공개 저장소의 관리가 종료되어 업데이트와 보안 수정이 더 이상 없는 상태 |
