## 3. 문제 (1:30)
**화면**: 네 가지 문제 — 보관 부담 · 맥락 유실 · 함께 볼 계기 없음 · 정리 수고
**대본**
> 아이는 매일 그림을 그리고 무언가를 만들지만, 가정에서 그 작품을 오래 간직하고 다시 꺼내 보기는 어렵습니다. 저희는 문제를 네 가지로 정리했습니다.
> 첫째, 보관 부담입니다. 종이 작품은 금방 쌓여 공간을 차지하고, 결국 상자에 들어가거나 버려집니다.
> 둘째, 맥락이 사라집니다. 그릴 때 아이가 한 말, 그때의 나이, 날짜가 따로 남지 않습니다. 몇 년 뒤에는 무엇을 왜 그렸는지 아무도 기억하지 못합니다.
> 셋째, 함께 볼 계기가 없습니다. 작품이 흩어져 있으면 가족이 함께 앉아 이야기 나눌 기회가 생기지 않습니다.
> 넷째, 정리 수고입니다. 사진을 찍어도 책상 같은 배경이 섞이고, 어떻게 보여 줄지 매번 고민해야 합니다.
**근거**: spec "Problem Statement" 1~4

## 4. 우리의 답 — 흐름 (2:00)
**화면**: 흐름도 — 사진 올리기 → 배경 분리(M1) → 판정 제안(M2 · M3 · M4) → 보호자 확정 → 움직이는 그림(M3) / 입체 그림(M5) / 원본 액자 → 이야기 → 전시. 아래 "결과는 늘 돌아온다: 움직임 → 입체 → 액자"
**대본**
> 저희의 답은 휴대폰 사진 한 장을 미술관 작품으로 바꾸는 것입니다.
> 사진이 들어오면 먼저 배경에서 작품만 분리합니다. 그다음 무엇을 그렸는지 판정을 "제안"합니다. 사람 그림인지, 동물인지, 집인지를 보고 "움직일 수 있을 것 같아요"처럼 권합니다. 결정은 보호자가 합니다.
> 사람이나 캐릭터 그림은 아이가 그린 선을 그대로 살려 움직이는 그림으로 만듭니다. 움직이기 어려우면 깊이를 추정해 입체 그림으로, 그것도 어려우면 원본을 액자에 담습니다.
> 여기서 가장 중요한 설계는 "결과는 늘 돌아온다"입니다. 어느 모델이 실패해도 한 단계 낮춘 결과가 돌아오고, 낮췄다는 사실을 숨기지 않습니다. 마지막으로 아이의 한마디와 그린 날, 나이를 함께 남기면 전시됩니다.
**근거**: spec "처리 흐름" · REF §9 "결과는 늘 돌아온다"

> 기술은 기억을 꾸며내는 주체가 아니라 다시 꺼내 보는 수단이라는 것이 저희 팀 기준입니다.

## 6. 아키텍처 (2:00)
**화면**: 구성도 — 브라우저(Vue 3) → nginx 9501 → 앱 API 9521(Node · Express · MariaDB · 작업 큐) → worker-cpu · worker-gpu(TorchServe 956x) / 모델 API 9541(FastAPI, 외부 /v1/models/*) / llm-server 8200(P0.5)
**대본**
> 이제 기술 이야기로 넘어가겠습니다. 구조는 이렇습니다.
> 보호자는 Vue 3로 만든 웹 화면을 씁니다. 입구의 nginx가 요청을 받아 나눕니다. 앱 API는 Node와 Express로 만들었고, MariaDB 하나에 도메인 데이터와 작업 큐를 함께 둡니다.
> 모델 작업은 무겁습니다. 움직이는 그림 한 장을 만드는 데 개인 PC 실측으로 53초에서 62초가 걸렸습니다. 그래서 요청은 큐에 넣고 바로 돌려주고, CPU 워커와 GPU 워커가 차례로 가져가 처리합니다. 화면은 기다리지 않아도 되고, 닫았다 다시 와도 어디까지 왔는지 보입니다.
> 모델 기능은 FastAPI로 만든 모델 API가 팀 밖에도 제공합니다. 포트도 설계서의 결정으로 정했습니다. 화면 9501, 백엔드 9521, 모델 API 9541이고, 내부 모델 서버는 956x 대역에 모았습니다.
**근거**: CLAUDE.md 기술 컨텍스트 · REF D19 · SD_04 · spec(M3 53~62초) · `docs/B/API개선결과`(A6)

## 7. 모델 7종 (2:00)

**대본**
> 저희는 모델을 새로 학습하지 않았습니다. 공개된 사전학습 모델을 이어 붙였습니다. 짧은 기간 안에 서비스를 완성하려면 학습보다 연결과 운영에 집중하는 편이 맞다고 판단했습니다.

> 모델마다 라이선스를 확인하고 기록했습니다. 예를 들어 Depth Anything은 Base와 Large가 비상업 라이선스라서 Small만 씁니다.

## 8. MLOps — 평가 · 승격 · 점검 (2:00)
**화면**: 모델 버전 흐름 — 후보 → [G22: 평가 묶음 전체 재평가 · 라이선스 · 응답 계약] → 활성 → 롤백 후보 / 옆: 점검 API(D20) / 아래: D27 임시 활성 예외
**대본**
> MLOps 과정의 핵심인 모델 운영입니다. 모델은 올려 두는 것으로 끝나지 않습니다.
> 새 버전은 먼저 후보로 등록됩니다. 평가 묶음 전체를 다시 평가하고, 라이선스와 응답 계약이 맞아야 활성으로 승격됩니다. 저희는 이 관문을 G22라고 부릅니다. 승격되면 직전 버전은 롤백 후보로 남아서 문제가 생기면 되돌릴 수 있습니다.
> 평가와는 따로 점검 API도 만들었습니다. 운영자가 모델 하나를 샘플 한 장으로 실제 추론해서 "지금 결과를 내는가"만 봅니다. 점검 통과는 승격 근거로 쓰지 않습니다. 평가와 점검은 목적이 다르기 때문입니다.
> 정직하게 말씀드리면, 평가용 그림 묶음을 아직 다 모으지 못해 평가 항목이 0장이었습니다. 그래서 팀 시험을 위해 모델 네 개를 예외로 임시 활성화했습니다. 이 예외는 숨기지 않고 결정 D27로 기록했습니다.
**근거**: SD_01 8.7(G22) · REF D20 · REF D27 · spec FR-33

## 9. 실패를 다루는 방식 (1:30)
**화면**: 두 갈래 — 품질 미달 → 재시도 없이 한 단계 낮춤(움직임 → 입체 → 액자) / 인프라 장애(엔진 다운 · 시간 초과 · 저장소 · DB · 모델 미준비) → 같은 단계 최대 3회 재시도 → 소진 시 "결과 미도달"(목표 0). 아래 원인 5분류 · 화면 갱신 폴링 3 → 6 → 10초
**대본**
> 모델 서비스는 실패를 어떻게 다루느냐가 품질입니다. 저희는 실패를 두 갈래로 나눴습니다.
> 결과 품질이 모자라면 재시도하지 않고 바로 한 단계 낮춥니다. 움직임이 안 되면 입체로, 입체가 안 되면 액자로 갑니다. 반면 엔진이 죽거나 시간이 초과되는 인프라 장애는 낮춤이 아닙니다. 같은 단계를 최대 세 번 다시 시도하고, 그래도 안 되면 "결과 미도달"로 알리고 집계합니다. 목표는 0입니다.
> 결과에 이른 원인은 보호자 선택, 모델 낮춤, 보호자 전환, 인프라 실패, 결과 미도달의 다섯 가지로 나눠 기록하고 섞지 않습니다. 그래야 운영 지표가 거짓말을 하지 않습니다. 화면은 푸시 없이 3초, 6초, 10초 간격으로 폴링하고, 탭이 숨겨지면 멈춥니다.
**근거**: REF 작품 상태 · 낮춤 체인 · 인프라 재시도 3회 · spec Clarifications(원인 5분류) · CLAUDE.md(폴링 3→6→10초)

## 10. 모델 API를 밖으로 (1:30)
**화면**: 외부 모델 기능 — segment(분리) · classify(종류) · pose(관절, 팀 내부 키 전용) · relief(입체) · caption(설명, P0.5). 규칙: 승격된 활성 버전만 · 낮은 우선순위 대기열 · API 키 해시 저장 · 요청 한도
**대본**
> 저희 모델은 우리 서비스 안에서만 쓰이지 않습니다. 모델 기능 네 가지, 분리와 종류 판정과 관절과 입체를 API로 밖에 엽니다. 설명 생성은 다음 단계에서 엽니다.
> 밖으로 열 때 지킨 규칙이 있습니다. 평가를 통과해 승격된 활성 버전만 응답합니다. 외부 요청은 낮은 우선순위 대기열로 받아서, 보호자의 작품 처리가 늘 먼저입니다. API 키는 해시로만 저장하고 요청 한도를 둡니다. 관절 기능은 팀 내부 키 전용으로 제한했습니다. 문서는 계약 정본을 읽는 Swagger 화면으로 누구나 볼 수 있습니다.
