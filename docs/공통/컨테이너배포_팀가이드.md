# 우리 아이 미술관 컨테이너 배포 팀 가이드(배운 내용을 복습하며 진행하기)

작성 2026-10-28. 독자는 팀원 3명이다. 마스터플랜(`design/PLAN_3인디벨롭_컨테이너협업_우리아이미술관.md`)이 무엇을·언제·누가 할지 정한다면, 이 가이드는 단계마다 Linux·Git·Docker 교안의 어떤 내용을 함께 복습하고, 이 서비스에서 무엇을 직접 해 보고, 무엇으로 됐다고 판단하는지를 정한다. 교안을 옮겨 적지 않는다. 교안은 각자 다시 펴 보고, 이 문서는 "어디에 써먹는가"만 잇는다.

## 1. 함께 복습하며 일하는 방식

한 주제를 아래 순환으로 돈다. 주제 하나에 반나절에서 하루를 잡는다.

| 순서 | 하는 일 | 걸리는 시간 | 남기는 것 |
|---|---|---|---|
| ① 같이 보기 | 그 주제의 길잡이(3절 표)가 교안의 해당 장을 짧게 다시 설명하고, 이 서비스의 어느 부분에 쓰이는지 보여 준다 | 15분 | 없음 |
| ② 질문 만들기 | 나머지 두 사람이 "우리 서비스에서는 이 경우 어떻게 되나"를 2개씩 묻고 이슈로 적는다 | 10분 | 이슈 |
| ③ 각자 적용 | 이슈 하나 = 가지 하나 = PR 하나. 자기 역할의 폴더에서 한다 | 반나절 | PR |
| ④ 리뷰에서 설명하기 | 리뷰어는 "왜 이렇게 했는가"를 묻고, 작성자는 배운 원칙으로 답한다. 답하지 못하면 병합하지 않고 같이 다시 본다 | 20분 | 리뷰 기록 |
| ⑤ 한 줄 회고 | 막힌 것 하나, 새로 안 것 하나를 팀 저장소 위키(또는 `docs/공통/`)에 적는다 | 5분 | 회고 한 줄 |

- 길잡이는 돌아가며 맡는다. 자기 역할과 가장 가까운 주제를 먼저 맡는다.
- PR 설명에는 "이번에 쓴 원칙"과 "확인한 명령과 결과(숫자)"를 적는다(진행 판 부록 B 양식).
- 막히면 30분 안에 팀 채널에 묻는다. 묻을 때는 명령, 결과(오류 문구), 이미 해 본 것을 함께 붙인다.

## 2. 이 서비스로 시작할 때 먼저 알아 둘 것

- **가볍게 시작한다.** 가짜 모델(`UAM_FAKE_MODELS=1`)을 켜면 모델 없이 전체 흐름과 장애 주입 시험을 돌린다(`serving/adapters/fake.py`). 이때는 모델 묶음(PyTorch 등) 없이 기본 잠금(`serving/requirements.lock`)만 깔면 된다. 첫 이미지와 첫 compose는 이 구성으로 만들고, 실제 모델은 M1부터 하나씩 붙인다.
- **모델 묶음 잠금은 플랫폼마다 다르다.** x86_64 리눅스는 `serving/requirements-models-linux-x86_64.lock`(PyTorch CPU 전용), 맥과 arm64 리눅스는 `serving/requirements-models.lock`이다. 버전은 같다(`serving/README.md`).
- **메모리를 먼저 본다.** M1(배경 분리)은 추론 중 메모리 8.5GB를 쓴다. 메모리 8GB 가상머신에서는 가짜 모델로 시작하거나 메모리를 늘린다.
- **시험은 일반 사용자로 돌린다.** 서빙·api 시험은 임시 MariaDB를 스스로 띄운다. 리눅스에서는 `sudo apt install mariadb-server` 뒤 일반 사용자로 돌린다(시험 설정이 root용 옵션을 주지 않아 root로는 MariaDB가 뜨지 않는다).
- **주소와 설정은 지금 서버에 맞춰져 있다.** app-api와 model-api는 127.0.0.1에 묶여 있고 그 주소가 코드에 고정돼 있다(`api/src/server.ts` 14행, `serving/model_api/main.py` 8행). 다른 컨테이너에서 부르려면 이 주소를 설정 값으로 바꾸는 것부터 한다(설계서 먼저). 앱과 서빙은 `.env`를 스스로 읽지 않는다. 지금은 팀 서버의 pm2 설정(`ops/p1/ecosystem.config.cjs`)이 넣어 준다.
- **CI의 DB 시험은 지금 건너뛴다.** CI 이미지(`node:22`·`python:3.11`)에 MariaDB가 없어서다. CI에 DB를 붙이는 일은 compose를 배운 뒤 해 볼 좋은 과제다.
- **TorchServe(M3) 환경은 맥 전용 목록이다.** `serving/conda-m3.lock`은 osx-arm64 패키지 목록이라, 리눅스로 옮기려면 다시 잠가야 한다. 넣을지는 첫 회의에서 정한다(진행 판 7절).

## 3. 주제별 복습과 적용

"교안"은 이번 과정의 Linux·Git·Docker 교안이다. 장 이름은 교안의 큰 제목을 줄여 적었다.

### 3-1. 개발 단계와 협업(SDLC·Git)

| 교안 주제 | 이 서비스에서 할 일 | 손에 익힐 명령 | 됐다고 보는 기준 | 길잡이 |
|---|---|---|---|---|
| 개발 단계(SDLC) | 진행 판의 0~6단계를 분석 → 설계 → 구현 → 시험 → 배포 → 운영에 맞춰 이슈 마일스톤으로 만든다 | (도구 없음) | 마일스톤 6개와 단계마다 끝나는 조건이 이슈에 있다 | 통합 책임자 |
| Git 원격·SSH 키 | 팀 저장소를 받고 SSH 키로 push한다 | `ssh-keygen`, `git remote -v`, `git clone` | 세 사람 모두 SSH로 push된다 | 역할 3 |
| 브랜치·병합·충돌 | 기능 가지에서 일하고, 같은 파일(`.env.example`)을 둘이 고쳐 일부러 충돌을 한 번 만들어 푼다 | `git switch -c`, `git merge`, `git status`, 충돌 표시 지우기 | 충돌을 푼 PR이 하나 병합돼 있다 | 역할 1 |
| 이슈·팀 브랜치 전략 | 이슈 양식, 라벨(역할·단계), Projects 보드, 가지 이름 규칙(`feat/번호-이름`) | `gh issue create`, `gh project` | 모든 PR이 이슈 번호와 이어진다 | 통합 책임자 |
| PR·코드 리뷰 | PR 양식(진행 판 부록 B), 리뷰 순환(1→2→3→1), squash 병합, main 보호 | `gh pr create`, `gh pr review`, `gh pr merge --squash` | main 직접 push 0건, 병합된 PR마다 리뷰 1건 이상 | 역할 2 |
| 고급 기능과 이력 정리 | 내 가지를 main 위로 옮기기, 잘못 올린 커밋 되돌리기(공유 이력은 revert), 지운 가지 되살리기 | `git rebase`, `git revert`, `git reflog` | revert로 되돌린 기록이 이력에 한 번 있다 | 역할 3 |
| 큰 파일 | 모델 가중치는 저장소에 넣지 않는다. 넣어야 할 작은 시험 파일은 LFS를 검토한다 | `git lfs track`(검토만) | 저장소에 가중치 0개(`git ls-files models`) | 역할 3 |

### 3-2. 리눅스 서버 운영(Linux)

| 교안 주제 | 이 서비스에서 할 일 | 손에 익힐 명령 | 됐다고 보는 기준 | 길잡이 |
|---|---|---|---|---|
| 파일 시스템·권한 | 작품 파일 저장소(`family/`·`tmp/`·`ext/`)와 DB 자료 폴더의 주인과 권한을 정한다. 컨테이너 사용자 UID와 맞춘다 | `ls -l`, `chmod`, `chown`, `id` | 서비스 사용자만 쓰고, 입구는 읽기만 한다 | 역할 2 |
| 프로세스·자원 | 지금 서비스를 띄워 프로세스별 메모리를 잰다(M1 추론 중 8.5GB 확인) | `ps`, `htop`, `free -h`, `df -h` | 부록 A 표의 메모리 칸이 실제 값이다 | 역할 3 |
| 네트워크·원격 접속 | 서버에 SSH로 들어가고, 어떤 포트가 열려 있는지 본다. 바깥에는 9501 하나만 연다 | `ssh`, `ss -tlnp`, `curl`, `ufw` | 바깥에서 9501만 닿는다 | 역할 1 |
| 패키지·Python 환경 | 리눅스에서 가상환경을 만들고 잠금 파일로 같은 버전을 깐다(플랫폼별 잠금) | `apt`, `python3.11 -m venv`, `pip install --require-hashes` | 서빙 시험이 리눅스에서 통과한다(2절) | 역할 3 |
| 셸 스크립트·자동화 | DB 백업 스크립트와 주기 실행 | 셸 스크립트, `cron` | 하루 한 번 백업 파일이 생기고 복원이 된다 | 역할 2 |
| 모니터링·로그 | 서비스 로그를 모아 보고, 디스크·메모리를 지켜본다 | `journalctl`, `tail -f`, `docker logs`(Docker 단계 뒤) | 장애 리허설에서 원인을 로그로 찾는다 | 역할 1 |
| ML 서버 종합 운영 | 위를 묶어 배포 서버를 준비한다 | 위 명령 전부 | 문서만 보고 새 서버를 준비한다 | 전원 |

### 3-3. 컨테이너(Docker)

| 교안 주제 | 이 서비스에서 할 일 | 손에 익힐 명령 | 됐다고 보는 기준 | 길잡이 |
|---|---|---|---|---|
| 1권: 필요성, 이미지와 컨테이너 | `python:3.11`·`node:22` 컨테이너에 들어가 지금 서비스를 손으로 깔아 본다. 무엇이 필요한지 적는다 | `docker run -it`, `docker ps`, `docker exec`, `docker logs` | 손으로 깐 순서가 분석 기록에 있다 | 역할 3 |
| 1권: Dockerfile | 서비스마다 Dockerfile. 잠금 파일을 먼저 복사해 설치하고 소스는 나중에 넣는 순서를 시험한다. 웹은 빌드 단계와 실행 단계를 나눠 보고 크기를 비교한다. `.dockerignore` | `docker build`, `docker image history`, `docker image ls` | 소스 한 줄만 바꾼 다시 빌드에서 설치 층이 재사용된다(빌드 시간 비교). 이미지 크기 표가 있다 | 역할별(자기 이미지) |
| 1권: 데이터 | DB 자료와 작품 파일을 컨테이너 밖에 둔다. 모델 가중치는 이미지에 넣을 때와 읽기 전용으로 붙일 때를 비교해 정한다 | `docker volume`, 바인드 마운트, `docker volume inspect` | 컨테이너를 지우고 다시 띄워도 가족 작품이 남는다. 백업·복원이 된다 | 역할 2 |
| 1권: 네트워크 | 서비스끼리 이름으로 부른다. 먼저 코드에 고정된 바인딩 주소(127.0.0.1)를 설정 값으로 바꾼다. 입구가 실제 접속 IP를 앱에 넘기게 한다. 환경 값과 비밀을 넘긴다 | 사용자 정의 네트워크, `-p`, `-e` | 내부 서비스 포트가 호스트에 열려 있지 않다 | 역할 1 |
| 1권: Compose | 한 파일로 전체를 띄운다(가짜 모델로 먼저) | `docker compose up -d`, `ps`, `logs`, `down` | 한 명령으로 모든 서비스가 뜬다 | 역할 3 |
| 2권: Compose 심화 | 상태 확인(`/live`·`/ready`)과 기동 순서, 재시작, 개발·서버 덮어쓰기 파일 | `healthcheck`, `depends_on` 조건, 여러 compose 파일 겹치기 | DB를 늦게 띄워도 api가 죽지 않는다 | 역할 3 |
| 2권: 이미지 배포 | 태그 규칙(모든 빌드와 출시를 구분하는 방법)을 정하고, 레지스트리에 올리고, 한 판 전으로 되돌린다 | `docker tag`, `docker push`·`pull`, 다이제스트 | 되돌리기에 걸린 시간이 기록돼 있다 | 역할 3 |
| 2권: 보안·자원 | root 아닌 사용자, 읽기 전용 파일 시스템, 필요 없는 권한 빼기, M1 작업자 메모리 한도, 이미지 줄이기(CPU 전용 PyTorch) | `docker inspect`, `docker stats`, `docker image ls` | 점검표(진행 판 5절 6단계)가 0건 위반이다 | 역할 2 |
| 2권: ML 환경 | 플랫폼별 잠금 파일로 같은 버전을 깐다. 매니페스트 해시로 가중치를 확인한다. 실행 환경 지문(`image_digest`)을 실제 이미지 다이제스트로 바꿀지 정한다 | `pip install --require-hashes` | 두 사람이 따로 빌드해도 같은 버전이 깔린다 | 역할 3 |
| 2권: GPU | 선택 과제. NVIDIA GPU가 있는 Windows(WSL 2) 팀원이 있으면 GPU 태그를 시험한다. 지금 코드는 장치를 MPS 아니면 CPU로만 고른다. CUDA를 쓰려면 장치 고르기에 CUDA를 더하는 작업이 먼저다(설계서 먼저) | `docker run --gpus all`, `nvidia-smi` | CPU와 GPU 걸린 시간 비교표가 있다(하면) | 역할 3 |
| 2권: 서비스 운영 프로젝트 | 상태 확인, 로그, 장애 상황(서비스 하나 죽이기, DB 늦게 뜨기, 메모리 초과), 복구, 운영 절차서 | `docker compose logs`, `restart`, `docker events` | 운영 리허설 기록과 절차서가 있다 | 전원 |

## 5. 하지 않을 것

- 교안 문장이나 교안에 딸린 예제 파일을 이 저장소에 옮겨 붙이기.
- 한 사람이 다른 역할의 이미지를 대신 다 만들어 주기(리뷰와 짝 작업은 좋다).
- 설명할 수 없는 설정을 병합하기(4번 순환의 기준).
