# 도커로 띄우고 운영하기(팀 작업 가이드라인)

작성 2026-10-29. 독자는 팀원 3명이다. 이 문서만 보고 서비스를 띄우고, 첫 작업을 고를 수 있게 하는 것이 목적이다. 구성의 근거는 `design/SD_04_아키텍처설계서_우리아이미술관.md` 10절, 5일 계획은 `design/PLAN_3인디벨롭_컨테이너협업_우리아이미술관.md`에 있다.

## 1. 한 번에 띄우기

### 1-1. 준비(처음 한 번)

| 환경 | 할 일 |
|---|---|
| Windows | WSL2 + Docker Desktop(WSL2 엔진). WSL 메모리를 늘린다: `%UserProfile%\.wslconfig`에 `[wsl2]` 아래 `memory=12GB`, `processors=6`을 적고 PowerShell에서 `wsl --shutdown` 뒤 다시 연다. **저장소는 WSL 안(예: `~/uri-gallery`)에 받는다.** Windows 폴더에 받으면 줄바꿈이 CRLF로 바뀌어 스크립트가 깨질 수 있다 |
| macOS | Docker Desktop 또는 colima. 메모리를 14GB 안팎으로: colima는 `colima stop && colima start --cpu 6 --memory 14`. Apple Silicon 컨테이너는 Apple GPU를 쓰지 못한다. 모델은 CPU로 돈다 |
| 공통 | `docker run hello-world`가 되는지 확인한다 |

### 1-2. 띄우기

```bash
git clone https://github.com/kids-gallery/uri-gallery.git && cd uri-gallery
cp .env.example .env
# .env의 빈 비밀 값 네 개(DB_PASSWORD, MARIADB_ROOT_PASSWORD, SESSION_SECRET, AUTH_HMAC_SECRET)를 채운다
openssl rand -hex 32          # 값 하나씩 만들어 붙인다
docker compose --profile tools run --rm fetch-models   # 모델 가중치 받기(한 번, 약 1.1GB). 해시가 매니페스트와 다르면 실패로 끝난다
docker compose up -d
docker compose ps             # 모두 running, 상태 확인이 있는 것은 healthy
```

- 화면: `http://localhost:9501`(3D 미술관은 `/app/world`). 받은 메일(가입 확인): `http://localhost:8025`
- 처음 빌드는 serving 이미지(PyTorch)가 가장 오래 걸린다. 이 맥에서는 이미지 네 개가 web 130MB, api 443MB, serving 1.62GB, engine-dev 213MB였다(2026-10-29).
- `.env`의 `COMPOSE_FILE=compose.yaml:compose.dev.yaml` 덕분에 `docker compose`만 치면 개발 묶음이 뜬다. 배포 묶음은 `docker compose -f compose.yaml -f compose.prod.yaml up -d`.

### 1-3. 됐는지 확인하기

```bash
python3 ops/docker/smoke.py flow           # 가입 → 아이 → 사진 → 판정 → 입체 확정 → 승인(약 30초)
docker compose stop engine-dev
python3 ops/docker/smoke.py engine-down    # 엔진이 멈춘 채로 올리기 → 판정 3회 시도 뒤 실패 → 원본 액자로 남음(약 90초)
docker compose start engine-dev
docker compose down && docker compose up -d
python3 ops/docker/smoke.py check          # 컨테이너를 다시 만든 뒤에도 계정·작품·사진이 남는지
```

결과는 마지막 줄 JSON이다. 2026-10-29 이 맥에서 세 가지 모두 통과했다(아래 6절).

## 2. 무엇이 어디서 도나

| 서비스 | 하는 일 | 바깥에서 | 담당 |
|---|---|---|---|
| web | nginx: 화면 파일 + `/v1/*`는 app-api, `/v1/models/*`는 model-api로 | `127.0.0.1:9501` | 최호준 |
| app-api | 업로드 접수, 작업 만들기, 상태·결과 조회 | 아니요 | 신지현 |
| sweeper | 죽은 작업 이어받기, 삭제, 정리 | 아니요 | 신지현 |
| migrate | DB 스키마 넣기(한 번 돌고 끝남) | 아니요 | 신지현 |
| db | MariaDB 12.0 | 아니요 | 신지현 |
| model-api | 모델 준비 상태, 외부 모델 기능 | 아니요 | 이제민 |
| worker | 작업 꺼내기 → 모델(M1·M2·M5는 안에서, M3 관절은 엔진에 물음) → 재시도·낮춤 | 아니요 | 이제민 |
| engine-dev(개발) | **개발용 가짜 엔진.** 사람 검출을 늘 0건으로 답한다. 움직이는 그림은 만들지 않는다 | 아니요 | 이제민 |
| engine(배포) | 실제 Animated Drawings TorchServe | 아니요 | 이제민 |
| seed(개발, 한 번) | 시험 환경 모델 버전 활성화(승격 절차를 건너뜀, 배포에는 없음) | 아니요 | 이제민 |
| mailpit | 가입 확인 메일 받기 | `127.0.0.1:8025` | 신지현 |

## 3. 파일

```
compose.yaml            공통 묶음
compose.dev.yaml        개발: engine-dev + seed
compose.prod.yaml       배포: 실제 engine + 메모리 한도
.env.example            설정 값 칸(비밀 값은 .env에만)
.dockerignore           이미지에 넣지 않을 것
web/Dockerfile          화면 빌드 → nginx
api/Dockerfile          app-api · sweeper · migrate
serving/Dockerfile      model-api · worker · seed · fetch-models
engine/Dockerfile       실제 엔진(x86_64, 배포)
engine-dev/             개발용 가짜 엔진
ops/docker/nginx.conf   입구 길 나누기
ops/docker/smoke.py     시험 스크립트
serving/ops/docker_seed.py   시험 시드
serving/ops/fetch_models.py  가중치 받기
```

## 4. 일하는 규칙

- **설계서 먼저.** 구성·설정 값을 바꾸면 `SD_04` 10절을 먼저 고친다. 결과가 달라지면 다시 맞춘다.
- **이슈 → 가지 → PR.** 가지 `종류/이슈번호-설명`, 커밋 `종류: 설명 (#이슈번호)`. PR의 "확인한 것"에 실제로 돌린 명령과 결과(위 1-3의 JSON 한 줄, 이미지 크기 등)를 적는다. 리뷰봇이 먼저 보고, 사람 승인 1회 뒤 신지현이 병합한다(README "일하는 법").
- **자기 영역의 Dockerfile을 설명할 수 있어야 병합한다.** 왜 이 기반 이미지인지, 왜 이 순서로 복사하는지, 왜 이 볼륨인지.
- **가짜로 성공을 만들지 않는다.** `UAM_FAKE_MODELS`는 컨테이너에서 쓰지 않는다. 엔진 자리의 개발용 대체는 engine-dev 하나다. 시연과 검증은 실제 엔진으로 한다.

## 5. 비밀 값과 백업

- 비밀 값은 `.env`에만 둔다. 저장소·PR·채팅·이슈에 붙이지 않는다. 다른 팀원과 같은 값을 쓸 필요는 없다(각자 만든다).
- DB 백업:
  ```bash
  set -a; . ./.env; set +a
  docker compose exec -T db mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" --single-transaction --routines --triggers "$DB_NAME" > backup.sql
  ```
- 파일 백업(작품 원본·결과):
  ```bash
  mkdir -p .data/backup
  docker run --rm -v uri-gallery_store:/s:ro -v "$PWD/.data/backup":/b alpine:3.20 tar czf /b/store.tgz -C /s .
  ```
- 복원: 빈 DB에 `docker compose exec -T db mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" "$DB_NAME" < backup.sql`, 파일은 같은 명령에서 `tar xzf`로 푼다. 복원 시험은 아직 하지 않았다.
- `docker compose down -v`는 볼륨(DB·작품 파일)까지 지운다. 지울 생각이 아니면 `-v`를 붙이지 않는다.

## 6. 실제로 확인한 것(2026-10-29, 이 맥, colima 6 CPU·14GB, arm64)

| 확인 | 결과 |
|---|---|
| ① 깨끗한 상태(`down -v`)에서 `up -d` | 13초 안에 모두 시작, 약 40초 뒤 healthy 7·종료 0 둘(migrate, seed). 모델 적재 M1 2.4초·M2 2.3초 |
| ② 사진 한 장 → 작업 완료 → 결과 | `smoke.py flow` 26초. split·judge·depth_relief 모두 1회에 완료, 걸린 결과가 액자 → 입체로 바뀜 |
| ③ 엔진을 멈춘 채 올리기 | `smoke.py engine-down` 86초. 판정이 `engine_down`으로 3회 시도 뒤 `failed`, 작품은 원본 액자로 전시 중 |
| ④ 컨테이너를 다시 만들어도 남는가 | `down`(볼륨 유지) → `up` → `smoke.py check`: 같은 계정 로그인, 작품 기록과 사진 파일(8,120바이트, 올린 원본과 같은 크기) 남음 |
| ⑤ 밖에서 db·엔진에 닿는가 | 호스트에 내보낸 포트는 web·mailpit 둘뿐. 127.0.0.1:3306·9561 닫힘. `/internal/`·`/model-api/`·`/metrics` 404. 안쪽 망의 worker는 인터넷에도 못 나감 |
| 실제 엔진(배포 묶음) | **미검증.** `engine/Dockerfile`은 원본 저장소 절차를 옮긴 것이고 빌드하지 않았다(x86_64 전용, 맥에서는 에뮬레이션) |
| 움직이는 그림 렌더 | **컨테이너에 없음.** 렌더 환경이 맥 전용 목록이라 이번 배치 밖(SD_04 10-6) |

## 7. 자주 나는 오류

| 증상 | 원인과 해결 |
|---|---|
| `POST /v1/...`가 502인데 `docker compose ps`는 모두 healthy | 같은 포트(9501)를 다른 프로그램(예: `npm run dev`)이 쓰고 있어 요청이 그쪽으로 감. `.env`에서 `WEB_PORT=9601` 처럼 바꾸고 `APP_BASE_URL`도 같은 포트로(2026-10-29 실제로 겪음) |
| 빌드 중 `pip ... Read timed out`, `No matching distribution` | 패키지 서버 연결이 잠깐 느림. 다시 빌드하면 받은 파일은 캐시에서 쓴다 |
| 빌드 중 `locked ... unavailable` | 같은 이미지를 여러 서비스가 동시에 빌드. 지금 compose는 이미지마다 한 서비스(app-api, model-api)만 빌드한다 |
| worker가 메모리 부족으로 죽음 | Docker 메모리가 작음(1-1). M1 추론 중 메모리를 많이 쓴다 |
| 로그인했는데 다시 로그인 화면 | 로컬 http에서 `SECURE_COOKIES=true`면 쿠키가 안 붙을 수 있음. `.env.example` 기본은 false |
| 가입 화면에 이메일 가입이 없음 | `MAIL_ENABLED`가 꺼짐. mailpit과 함께 켠다 |
| 작업이 계속 "처리 중" | `docker compose logs worker sweeper`. engine-dev가 멈췄으면 재시도 뒤 "처리하지 못함"이 되는 것이 정상(약 90초) |
| `^M`·`bad interpreter` | CRLF. WSL 안에서 다시 받기, `.gitattributes`(#10) |
