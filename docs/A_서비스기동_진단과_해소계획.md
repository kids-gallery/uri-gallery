## 0. 결론

- **인프라는 올라와 있다.** 프로세스 8개, 팀 DB, 입구 nginx, TorchServe가 모두 응답한다.
- **보호자가 쓸 수 있는 서비스는 아직 올라오지 않았다.** 로그인한 뒤 보는 첫 화면(S4 작품 목록)부터 구현되지 않았다. 모델 5종도 모두 비활성이라 작품을 올려도 처리할 모델이 없다.
- **"우리가 구현한 서비스가 이게 끝인가"에 대한 답은 "아니다"다.** 전체 150건 중 119건(79%)을 마쳤다. 서버 쪽(API·서빙)은 거의 끝났다. 남은 31건 대부분은 **화면(웹 20건 + 운영 웹 5건)**과 **모델을 켜는 운영 절차**다.
- **해소는 두 갈래를 병행한다.**
  - 먼저 보호자 화면 6장(S4·S2·S3·S5·S6·S8)을 완성하면, 모델이 없어도 **액자 경로로 가입부터 전시까지 한 바퀴**가 돈다(§4 1단계). plan의 "MVP = US1~US4를 한 번 끝까지"와 같은 기준이다.
  - 모델은 팀 결정(U4 라이선스) → 평가 담당 계정 → 평가 그림 → 평가·승격 순서로 켠다(§4 2단계).

## 2. 원인 — 끊긴 곳 다섯 군데

원인은 서버 장애가 아니다. **서비스를 끝까지 쓰게 만드는 사슬이 다섯 곳에서 끊겨 있다.** 영향이 큰 순서로 적는다.

### 원인 1. 보호자 화면이 가입·아이 등록까지만 있다 (결정적)

| 화면 | 작업 | 상태 |
|---|---|---|
| S0 가입 · S0a 로그인 · S0b 찾기 · S1 아이 관리 | T052·T053·T054 | 구현됨 |
| **S4 작품 목록·진행(로그인 뒤 첫 화면)** | T080(+T079 C6 낮춤 안내) | 자리 표시 |
| **S2 작품 올리기** | T066 | 자리 표시 |
| **S3 판정 제안 확정** | T067 | 자리 표시 |
| **S5 결과 확인** | T094(+T092 C5 비교) | 자리 표시 |
| **S6 이야기 쓰기** | T095(+T093 C7·C8) | 자리 표시 |
| **S8 가족 전시** | T096 | 자리 표시 |
| S1b·S1c·S1d 공동 보호자 · S9 삭제 | T107 · T101 | 자리 표시 |

이 화면들이 부를 API는 모두 준비돼 있다(B 76/81, 계약 검증 0건 어긋남 `73cd625`). 그런데도 사용자는 작품을 올릴 방법 자체가 없다. **"서비스가 안 올라왔다"로 보이는 가장 큰 이유가 이것이다.**

### 원인 2. 모델 5종이 모두 비활성이다

모델을 켜려면(활성 버전) 아래 사슬이 끝까지 가야 한다. 지금은 첫 칸부터 막혀 있다.

```
팀원(평가 담당) 계정 → 후보 버전 등록 → 평가 묶음(팀원 그림) → 평가 실행 → 판단(pass)
       ↑ team_member 0     ↑ API 준비됨        ↑ T118: 그림 0장      ↑ T117 끝남    ↑ S11 없음(API로 가능)
                                                                         ↓
                                  라이선스 팀 확정(U4) ──────────→ 승격(G22) → 활성
                                  ↑ docs/A_모델_라이선스_확정.md §4 빈칸
```

- 승격 조건(`v_promotion_eligibility`): 평가 항목 전부 완료 + 판단 `pass` + `license_confirmed` + 해시 있음(D5, BR-MDL-07). 하나라도 없으면 켤 수 없다.
- 설계상 모델이 없어도 서비스는 **액자 경로로는 끝까지 돈다.**
  - 판정 모델이 비활성이면 제안 없이 보호자가 직접 확정한다(spec clarify, T116).
  - 액자(`frame_compose`)는 모델이 필요 없다(BR-PRC-01).
- 그러니 원인 2는 "움직이는 그림·2.5D가 안 나온다"는 문제다. 서비스 자체를 막는 것은 원인 1이다.

### 원인 3. 운영 화면과 팀원 계정이 없다

- `/ops/*` 5화면(T055·T111·T112·T119·T125, B)이 자리 표시다. `team_member`도 0행이라 운영자·평가 담당이 로그인할 수 없다.
- 원인 2의 사슬을 화면으로 돌릴 수 없다. 같은 일은 API를 직접 부르면(curl) 된다. 그래서 원인 3은 **느려질 뿐 막히지는 않는다.**

### 원인 4. 확인 메일이 바깥으로 나가지 않는다

- 메일은 P0 결정대로 로컬 Mailpit(127.0.0.1:1025)에 쌓인다(결정 ⑤, R-23).
- 실제 이메일 주소로는 발송되지 않는다. 그래서 **팀 밖 사람은 가입을 끝낼 수 없다.**
- 실제 발송 서비스 선정은 미해결 U19다. P0 범위(팀 내부 검증, 동시 사용자 10명 이하)에서는 설계대로의 동작이다. 다만 "공개 서비스"를 기대하면 원인이 된다.

### 원인 5. 배포가 자동이 아니고, 재부팅에 약하다

- 웹은 main에 화면이 더해져도 `ops/p1/deploy-web.sh`를 누가 돌려야 p1에 나타난다. 지금도 p1 웹 `8bda297`이 main `e1aab5a`보다 뒤처져 있다.
- 앱 API도 `npm run build` 뒤 `pm2 reload`가 필요하다.
- 호스트가 재부팅되면 pm2가 자동으로 뜨지 않는다. `pm2 startup`은 관리자 권한이 필요해 설정하지 못했다. 재부팅 뒤 `pm2 resurrect`를 해야 한다.

### 원인이 아닌 것 (확인함)

프로세스 다운, DB 연결, 공유 nginx·TLS, 포트 충돌(8080·8081은 9561~9563으로 피함), sweeper 재시작 반복(`99e7609`로 해소), `/v1/models` 경로 오배정(`4e9a9c1`로 해소).

## 4. 해소 방법 — 논리 순서

### 목표 정의

"서비스가 올라왔다"는 다음을 뜻한다고 정한다(plan 구현 전략 1 · spec Scenario 1).

- **G-1(MVP)**: 보호자가 p1에서 가입 → 아이 등록 → 작품 올리기 → 확정 → 결과 확인 → 이야기 → 가족 전시까지 끊김 없이 간다. 모델이 없으면 액자 경로로 간다.
- **G-2(모델)**: 같은 흐름에서 사람 그림은 움직임, 그 밖은 2.5D가 나온다(낮춤 포함).
- **G-3(운영)**: 운영자·평가 담당이 운영 화면으로 상태를 보고 모델을 평가·승격한다.

G-1이 가장 앞이다. G-1이 없으면 G-2·G-3을 해도 보호자는 아무것도 볼 수 없다. G-2는 G-1과 독립적으로 병행할 수 있고, G-3은 G-2를 편하게 할 뿐이다.

### 1단계 — G-1: 보호자 화면 6장 (결정 경로, C 중심)

순서는 보호자가 겪는 순서다. 각 화면이 다음 화면의 입구다.
