```
브라우저 → https://p1.sumzip.com (공유 nginx, TLS · 관리자 소유)
        → 입구 nginx 9501 (정적 웹 + 라우팅)
            ├─ /v1/*          → app-api 9521 ──(DB 큐 stage_job)──→ worker-cpu · worker-gpu → 모델 M1·M2·M3·M5(·M7)
            │                                                        └→ TorchServe 9561(M3)
            ├─ /v1/models/*   → model-api 9541 ──(DB 큐 external_job)──→ 같은 워커
            └─ /internal/* · /model-api/* → 404
M6(P0.5, 지금 꺼짐): llm-server 8200 → 공유 Ollama 127.0.0.1:11434  (모델 게이트웨이 주소는 지정받지 못함 — A9)
```

### 2-5. 구조 한 문단

요청이 들어오면 입구 nginx(9501)가 받아 `/v1/*`는 app-api로, `/v1/models/*`는 model-api로 넘긴다. app-api는 계약에서 읽은 경로·쿼리 규칙(`paramGuard`)과 경로별 zod(`.strict()`)로 검증하고, model-api는 키 인증·한도 뒤 multipart 이미지 한 장과 형식을 검사한다. 추론은 두 API가 직접 하지 않고 DB 큐(`stage_job`·`external_job`)에 작업을 넣으면 워커(worker-cpu·worker-gpu)가 어댑터로 모델을 불러 결과를 파일·DB에 남기고, API는 그 결과를 JSON(작업·결과·작품 상세)으로 돌려준다. 모델은 워커 기동 시 한 번 올라가고, 실패하면 입력 오류는 422(`detail`·`fields[].message`), 서버·모델 쪽은 503(`not_saved`·`model_not_ready`)으로 나가며 500은 내보내지 않는다. 외부 LLM(M6)은 `127.0.0.1:11434`(공유 Ollama 원본 포트)로 부르도록 되어 있으나 지금은 꺼져 있다.
