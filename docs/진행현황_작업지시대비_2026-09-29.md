## 0. 요약

- 작업지시 20개 항목 중 **끝남 12 · 일부 5 · 안 함 3**이다.
- 끝난 것은 거의 모두 **설계서·계약·서버 코드(API·서빙)**다. 사람이 브라우저에서 만나는 **화면**은 가입·로그인·찾기·아이 관리 4장뿐이다.
- 그래서 지금 문제가 생긴다. **기능은 코드에 있는데 서비스로는 안 보인다.** 작품 올리기·판정·결과·이야기·전시·삭제·공동 보호자·운영·평가·API활용은 API까지 완성되어 시험도 통과했다. 그런데 이것들을 부르는 화면이 없어서 p1에서는 "T0xx에서 만든다" 자리 표시로만 보인다.
- 해소 원칙은 하나다. **"API가 끝난 기능부터, 화면 → 배포 → 실제 확인까지 한 번에 닫는다."** 보호자 흐름 6화면을 먼저 닫고(§3 1단계), 모델 켜기와 운영 화면은 병행한다.

## 2. 왜 "코드만 있고 안 보이는가"

기능마다 **설계 → API·서빙 코드 → 화면 → 배포 → 켜기(모델·계정)**의 다섯 칸이 모두 차야 사람 눈에 보인다. 지금은 앞의 두 칸만 찬 기능이 대부분이다.

| 기능(사용자 스토리) | 설계 | API·서빙 | 화면 | p1 배포 | 켜기 | 지금 보이는 모습 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| 가입·로그인·찾기·아이 등록(US1) | ✅ | ✅ | ✅ | ✅ | ✅ | **동작함** |
| 작품 올리기·판정 확정(US2) | ✅ | ✅ | ⬜ S2·S3 | — | — | 자리 표시 |
| 진행·결과·낮춤(US3) | ✅ | ✅ | ⬜ S4 | — | ⬜ 모델 | 자리 표시 |
| 결과 확인·이야기·전시(US4) | ✅ | ✅ | ⬜ S5·S6·S8 | — | — | 자리 표시 |
| 삭제(US5) | ✅ | ✅ | ⬜ S9 | — | — | 안 보임 |
| 공동 보호자(US6) | ✅ | ✅ | ⬜ S1b~S1d | — | — | 자리 표시 |
| 운영 지표(US7) | ✅ | ✅ | ⬜ S10 | — | ⬜ 팀원 계정(오늘 1개 만듦) | 자리 표시 |
| 모델 평가·승격(US8) | ✅ | ✅ | ⬜ S11 | — | ⬜ 평가 그림·U4 | 자리 표시 |
| 외부 모델 API(US9) | ✅ | ✅ | ⬜ S12 | ✅ | ⬜ 키 발급 | 401만 |
| 설명 초안(US10, P0.5) | ✅ | 🟡 llm-server만 | ⬜ | — | — | 계획상 뒤 |
| 3D(US11, P1) | ✅ | ⬜ | ⬜ | — | — | 계획상 뒤 |

원인은 세 가지로 좁혀진다.
1. **화면 인력 병목**: 화면 25건(보호자 20 + 운영 5)이 C·B 두 사람에게 몰려 있다. 서버를 만든 A·D는 오늘 일이 거의 끝났다.
2. **"끝남"의 기준이 코드·시험까지였다**: 작업이 API 시험 통과로 끝남 처리되어, 화면에 붙어 보이는지는 누구의 완료 조건에도 없었다.
3. **배포·켜기 담당이 없었다**: p1 배포는 오늘 처음 생겼다. 모델 켜기(U4·평가·승격)는 팀 결정이 필요한데 아직 열리지 않았다.

## 3. 어떻게 할 것인가

### 원칙

- **완료 기준을 "p1에서 보인다"로 바꾼다.** 화면이 붙는 작업은 `ops/p1/deploy-web.sh` 배포 뒤 p1 주소에서 실제로 누른 스크린숏 1장을 증거로 남겨야 끝이다(390px·1440px).
- **API가 끝난 기능부터 화면을 붙인다.** 새 API를 먼저 만들지 않는다. 지금 있는 API로 화면을 채운다.
- **보호자 흐름 한 바퀴(MVP, US1~US4)를 가장 먼저 닫는다.** 모델이 없어도 액자 경로로 끝까지 간다(spec clarify, BR-PRC-01).
- **프로토타입은 p1에 연결하지 않는다.** 보이는 것은 main의 구현 결과만이다.
- **설계서 먼저 규칙을 지킨다.** 화면 설계는 SD_02에 이미 있으니 바로 구현한다. 설계에 빈틈이 보이면 SD_02를 먼저 고친다.
