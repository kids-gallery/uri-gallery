## 막힌 점과 배운 것

- Git: 초기 로컬 브랜치가 원격 main과 다른 이력이어서 파일이 없고 fast-forward가 거부됐다. 원격 main을 기준으로 새 브랜치를 만들어 확인했다.
- 모델 메모리와 시간: #16에서 M1은 256×256 합성 입력 한 장의 Ubuntu 가상환경 CPU 1회 실행에 추론 109.678초, 프로세스 최대 RSS 3284.7 MiB, 스왑 사용을 기록했고 60초 제한을 넘었다. M2·M5는 Linux 컨테이너에서 각각 성공했다. 이 결과로 모든 Windows PC에서 실행 불가능하다고 단정하지 않는다.
- 추가 측정: M1은 CPU 2개·메모리/스왑 합계 3 GiB 제한 컨테이너에서 적재 후 추론 중 OOM 종료(137)했다. M2·M5는 같은 PC의 Ubuntu 가상환경에서 각각 1회 성공했다. 환경 제한이 다르고 합성 입력이므로 성능의 직접 비교가 아니다. 자세한 수치와 한계는 #16 댓글에 있다.
- Compose 기동 순서: DB가 준비되기 전에 마이그레이션과 worker가 시작하면 초기화가 실패할 수 있다. DB healthcheck와 일회성 마이그레이션 완료 조건으로 순서를 명시했다.
- worker 상태: 컨테이너 실행 여부와 작업 준비 여부는 다르다. 가짜 모델 환경에서 공유 상태 파일과 준비 응답을 확인했다.
- #41: 기준 `51967c0`의 Windows 격리 스택에서 Codex가 가입·메일 인증·아이 등록·로비까지 확인하고 11월 3일 중간 댓글을 남겼다. 당시에는 자동화 파일 선택에서 멈춰 업로드를 검증하지 못했다. 별도로 11월 4일 02:40 KST 무렵 사용자가 사진을 직접 선택해 업로드했을 때, Codex가 `docker compose -p uam41win logs`에서 `POST /v1/artworks` HTTP 503과 DB gate_event의 `G6/db`를 확인했다. DB 날짜와 한국 날짜의 차이를 Codex가 확인했으나 해당 오류의 내부 예외는 직접 확인하지 못했다. #129는 이제민이 등록했고 #130에서 수정했다. 동결 커밋 재시험은 아직이다.

## 리뷰에서 확인한 것

#141에서는 늦은 DB 시험이 결과를 단언하지 않는 점과 고정 프로젝트의 볼륨 삭제 가능성을 Codex가 지적하고 수정 후 재리뷰했다. #91은 자체 모델 가중치 해시와 라이선스 표시의 범위를 검토했다. #97에서는 HEIC 사전 검사 뒤 부모가 다시 디코딩하는 한계를 지적했고, 시연 범위의 한계 문서화를 확인했다. #116에서는 고정 리비전 다운로드 방법과 성능 수치의 측정 조건을 요청했다. 리뷰도 Codex가 최호준의 요청에 따라 수행·제출했으며, 실제 모델의 품질과 법적 사용 가능성을 이 리뷰만으로 확정한 것은 아니다.
