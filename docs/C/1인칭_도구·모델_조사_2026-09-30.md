핵심 구조(이 프로젝트에 맞춘 요약): `.viewport{perspective}` > `.camera{transform: translateZ(p) rotateX(pitch) rotateY(yaw)}` > `.world{transform-style:preserve-3d; transform: translate3d(-x,-y,-z)}` > 벽·바닥·천장·액자 면들. 매 프레임 `requestAnimationFrame`에서 **`.world` 하나의 transform만** 바꾼다(각 면은 고정).

### 성능 한계(설계 전에 알아 둘 것)

- **면(요소) 수**: 공식 상한은 없지만 3D 변형 요소마다 합성 레이어가 생길 수 있다. 실무 경험치로 모바일에서 수십~150면 안팎이 부드러운 선 [추론 — 기기 실측 필요]. 회랑 1개 + 방 1개만 DOM에 두고, 멀리 있는 방은 `display:none`(수동 컬링)으로 줄이는 게 정석.
- **레이어 메모리**: iOS Safari는 레이어 1장당 (가로×세로×4바이트×기기배율²)를 쓴다. 3x 기기에서 390×844 전면 레이어 1장 ≈ 12 MB. 큰 벽 면을 여러 장 겹치면 금세 수백 MB → 탭이 강제 새로고침된다. 확대·줌 때 수 GB까지 치솟은 사례 보고([Medium, Deadly CSS Transforms](https://medium.com/@jeffreyrussom/deadly-css-transforms-1e12b4c23f8)).
- **텍스처 크기**: 큰 레이어는 타일로 쪼개 합성되지만, 모바일 GPU 최대 텍스처(보수적으로 4096px 가정)를 넘는 단일 비트맵·`scale()`로 키운 요소는 흐려지거나 깜빡인다. 벽 이미지는 짧은 변 1024~2048px, 반복 무늬는 `background-repeat`로 [추론 — 기기마다 다름].
- **Safari 평탄화**: 조상에 `overflow`·`filter`·`clip-path`·`opacity<1`·`mix-blend-mode`가 있으면 `preserve-3d`가 풀려 납작해진다(Safari에서 특히 흔함, [3D CSS 가이드](https://www.carmenansio.com/articles/3d-css-guide/)). 반투명 막대·스포트라이트 겹을 3D 컨테이너 **바깥**에 둘 것.
- **z-fighting·교차**: 면이 서로 뚫고 지나가면 Safari/Chrome 정렬이 다르다. 면끼리 교차하지 않게 모델링.
- `will-change: transform`은 움직이는 `.world` 하나에만. 모든 면에 달면 메모리 폭증.
- `backface-visibility:hidden`으로 뒷면 그리기 줄이기.
- **움직임 줄이기**(prefers-reduced-motion)와 멀미: 자유 1인칭은 아이·보호자 멀미 유발 가능 → 현재 §17-6의 "한 칸씩 걸어 들어가는" 방식이 오히려 안전하다.

### "언제 전환하나" 기준(하나라도 해당하면 검토)

1. 장면이 **한 번에 150면 이상**(회랑 + 방 여러 개 동시 표시)이거나, 390px 실기기(iPhone)에서 Chrome DevTools 트레이스 기준 **이동 중 프레임 50fps 미만·합성 16ms 초과**가 반복될 때.
2. **자유 이동(아무 방향으로 걷기) + 벽 충돌 + 회전 시야**가 요구로 확정될 때(지금 §17-6은 한 칸씩 이동 — 자유 이동은 새 요구).
3. 진짜 조명·그림자·반사·금속 재질이 "필수"가 될 때.
4. 아이 그림을 **입체(M5 깊이 → 메쉬 변위, P1 M7 TripoSR GLB)**로 방 안에 세워야 할 때 — GLB는 CSS로 못 그린다.

전환한다면 Vue 3 프로젝트엔 **TresJS**가 가장 자연스럽다(선언형, Vue 반응성, Vite 호환). 단 D31 규칙을 바꾸는 설계 결정이 필요하다.

### 4-2. 아이 그림 2.5D — 깊이 모델 재사용

- 프로젝트에 이미 **M5 `depth-anything/Depth-Anything-V2-Small-hf`**(25M 파라미터, **Apache-2.0** — Small·Base·Large는 Apache, Giant만 CC-BY-NC)와 **2.5D 결과 = 컷아웃 PNG + 깊이 PNG16(WebGL 시차)**(R-07)가 있다. [Depth Anything V2](https://depth-anything-v2.github.io/)
- **재사용 가능.** 걷는 미술관에서는 새 모델 없이 기존 `2.5D` 결과 파일을 가져다 쓴다.
  - CSS 3D 안에서: 깊이 PNG를 몇 단계(예: 3~5겹)로 잘라 겹마다 `translateZ`를 조금씩 주는 "종이 겹" 방식은 CSS로 가능 [추론 — 겹 수만큼 레이어 늘어남, 크게 보기에서만].
  - 진짜 픽셀 단위 시차(깊이 변위)는 WebGL 셰이더가 필요 — R-07이 이미 "WebGL 시차"라고 적어 두었으니 **크게 보기 안 작은 canvas 하나**는 D31(홈 장면 규칙)과 따로 판단할 여지가 있다 [추론 — 설계 확인 필요].
- 주의: 아이 그림(평면 선화)은 깊이 추정이 약하다(사진용 모델). M1 BiRefNet 컷아웃 후 "배경 0 / 그림 1" 두 겹만으로도 충분히 떠 보인다.
- 로컬 맥: Small은 CPU·MPS 모두 수 초 이내 [추론]. 브라우저 실행(Transformers.js)도 가능하나 이미 서버 `worker-gpu`에 있으니 불필요.

### 지금 당장 적용(3개)

1. **Playwright MCP**(`@playwright/mcp@0.0.83`, project 범위) — 걷기 장면은 "보면서 고치는" 작업이라 에이전트가 390/1440 캡처·밀기·키 조작을 직접 해 보는 게 가장 큰 도움. 기존 `@playwright/test` e2e·axe와 같은 엔진이라 추가 위험 적음.

`frontend-design` 스킬은 이미 설치돼 있으니 그대로 쓰되, 색·글꼴은 스타일가이드 §4.1 v3가 우선.
