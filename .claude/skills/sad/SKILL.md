# SAD — 구현 → 도면 동기화와 이력

설계 흐름은 **유스케이스(흐름·시퀀스) → 프로세스(SD_01) → 화면(SD_02) → DB(SD_03) → 모듈·이력(SD_04)** 이다. SAD는 구현에서 생긴 사실을 이 층마다 빠짐없이 옮기고, 언제 무엇을 옮겼는지 기록한다.

프로젝트 규정(CLAUDE.md)은 "설계서 먼저, 구현 나중"이다. SAD는 그 규정을 지키지 못하고 구현이 앞선 변경을 **따라잡는** 도구다. 그래서 이력 기록에는 항상 "역반영"이라고 적고, 앞으로의 새 기능은 여전히 설계서 먼저 고친다.

## 흐름

모든 명령은 저장소 루트(`/Users/pioneer1/project2610`)에서 실행한다. `S=.claude/skills/sad/scripts`.

### 1. 변경 탐지

```bash
python3 $S/sad_changes.py scan
```

마지막 이력 기준점 이후의 커밋 목록, 변경 파일별 영향 도면 후보, 그 사이 이미 고친 설계·명세 파일, 지난 기록 때와 내용이 같아 건너뛴 파일을 보여 준다. 이력 파일이 없으면 아래 "처음 실행"을 먼저 한다.

### 2. 구현 사실 뽑기

후보 파일마다 `python3 $S/sad_changes.py diff <path>`로 기준점 대비 diff를 읽는다. **도면에 적힐 사실**만 뽑는다.

- 엔드포인트·메서드·권한(역할)
- 상태와 전이
- 오류 사유 코드·게이트
- 테이블·컬럼·제약·트리거·뷰
- 화면·버튼·문구·라우트
- 큐·워커 규칙과 우선순위
- 모듈 의존과 배치(pm2·포트)
- 새 결정·업무규칙

리팩터·시험만 바뀐 것·오타는 "도면 영향 없음"으로 분류한다. 시험 파일(TEST)은 구현 의도를 확인하는 근거로만 쓴다. 커밋 메시지와 `docs/`의 작업 기록도 의도 확인에 쓴다.

### 3. 이미 반영됐는지 확인

사실마다 `grep -rn "<경로·코드·이름>" design .specify`로 도면에 이미 있는지 본다. scan의 "이미 고친 설계·명세" 목록과 겹치면 다시 쓰지 말고 내용만 맞는지 대조한다. 도면과 구현이 **다르면**, 어느 쪽이 맞는지 구현 쪽 근거(커밋 메시지, 시험, 계약)로 판단한다. 판단이 서지 않으면 고치지 말고 이력의 "확인 필요"에 올리고 사용자에게 묻는다.

### 4. 도면 반영 — 층 순서대로

[references/mapping.md](references/mapping.md)의 §2 "구현 사실 → 도면 위치"와 §4 "함께 고칠 곳"을 읽고 그 순서대로 고친다. 기본 순서는 이렇다.

1. REF(D#·BR·엔드포인트)
2. UC_nn과 UC_ALL 사본, UC_00
3. SD_01
4. SD_02
5. SD_03, `uri_gallery_ddl.sql`, 마이그레이션 복사
6. SD_04
7. contracts(정본 → 사본)
8. spec·plan·data-model·tasks

지킬 것:
- **각 도면의 기존 형식을 그대로 따른다.** 표 열, IPO 번호 체계(n.m), H#·G#·BR·D# 번호 이어 붙이기, `[추론]` 표시, 근거 열을 맞춘다. 형식이 애매하면 `docs/_claude/분석설계 프롬프트 - *.md`(해당 층)를 읽는다.
- 원천에 없는 판단은 `[추론]`으로 표시하고, 값을 지어내지 않는다.
- 고친 문서마다 머리에 `> **개정 (YYYY-MM-DD, SAD-nnn 역반영 — 근거)**: …` 한 줄을 넣고, 꼬리 날짜도 고친다.
- 개수(테이블·게이트·BR·도면 수)와 사본(UC_ALL, contracts, DDL = 마이그레이션)을 함께 맞춘다.
- 도면(PlantUML)을 바꾸면 시퀀스 번호와 기본흐름의 1:1 대응을 유지한다. 대체흐름은 번호 없는 `opt`/`alt`로 그린다.

### 5. 검증

```bash
python3 $S/puml_sync.py <고친 md …> --png /tmp/sad-png   # 렌더 200·Syntax Error 없음, 바뀐 블록의 링크만 갱신
cmp design/uri_gallery_ddl.sql db/migrations/0001_sd03_baseline.sql            # DDL을 고쳤다면
diff -r .specify/features/우리-아이-미술관/contracts contracts | grep -v README   # 계약 사본 차이 0
npx --yes @redocly/cli@latest lint .specify/features/우리-아이-미술관/contracts/openapi.yaml   # 계약을 고쳤다면(오류 0)
cd api && npx vitest run ../db/tests/ddl.verify.test.ts                         # DDL을 고쳤다면(개수 기대값도 갱신)
```

- 와이어프레임(salt)·스윔레인 도면은 `--png`로 받은 이미지를 Read로 **눈으로 확인**한다. HTTP 200이어도 블록이 사라질 수 있다.
- 검증이 실패하면 기록하지 않고 고친다.

### 6. 이력 기록

반영 내용을 아래 형식으로 써서 기록한다. 머리(번호·시각·기준점)와 상태 주석은 스크립트가 붙인다.

```bash
python3 $S/sad_changes.py record <<'EOF'
- 구분: 역반영(구현 → 도면)
- 변경 원천: 커밋 `abc1234` T125 … · 작업 트리 `api/src/…`

| 구현 사실 | 반영한 도면 · 절 |
|---|---|
| `POST /v1/…` 추가(운영자) | REF §4 · UC_08 A9 · SD_01 7.11 · openapi |

- 도면 영향 없음: `web/src/__tests__/…`(시험만)
- 확인 필요: (없으면 "없음")
- 검증: 도면 N개 렌더 200 · DDL 시험 n/n · 계약 lint 오류 0
EOF
```

기록한 순간의 HEAD와, 커밋되지 않은 파일의 내용 해시가 다음 실행의 기준점이 된다. 반영하지 못한 사실은 "확인 필요"에 남긴다. 그러면 다음 scan에서도 파일이 다시 후보로 뜬다(내용이 바뀌지 않았으면 건너뛰므로, 남긴 항목은 이력에서 직접 이어 받는다).

### 7. 보고

사용자에게 다음 넷을 짧게 알린다.
- 반영한 사실 수와 고친 도면
- 도면 영향이 없다고 본 것
- 확인이 필요한 것
- 이력 번호(SAD-nnn)

커밋은 사용자가 요청할 때만 한다.

## 처음 실행 (이력 파일이 없을 때)

기준점을 정하지 않고는 "이후 변경"을 알 수 없다. 사용자에게 기준 커밋을 묻는다. 기본값은 도면이 마지막으로 구현과 맞았다고 확인된 커밋이다. `python3 $S/sad_changes.py init <커밋>`으로 `design/SAD_이력.md`와 기준점 SAD-000을 만든 뒤 1단계부터 진행한다.
