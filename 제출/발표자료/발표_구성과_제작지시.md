# 우리 아이 미술관 발표 구성과 제작 지시

이 문서가 발표 자료의 설계서이자, 자료를 만들 AI 세션에 주는 지시문이다. 슬라이드와 대본은 이 문서의 뼈대, 수치와 근거, 스타일을 따른다.

작업 위치: 저장소 `kids-gallery/uri-gallery`의 가지 `docs/47-presentation-outline`. Claude 클라우드 세션에서 연다.
대상: Canva 새 프레젠테이션 1개, 그리고 이 문서
해결할 문제: 11월 5일 과정 발표에 쓸 "우리 아이 미술관" 발표 자료가 아직 없다
산출물과 통과 기준: 뼈대 검토 보고, Canva 디자인 링크, 발표자 노트가 들어간 15장 안팎의 자료. 판정은 아래 "끝나는 조건"을 따른다
권한과 한도: Canva에서 새 디자인을 만들고 고치는 것과, 이 가지의 `제출/발표자료/` 안 파일을 고쳐 커밋·push하는 것만 허용한다. `main` 직접 push, PR 병합, 코드 수정, 공개 링크 공유, 게시, 결제, 유료 요소 구매, 메일·메신저 쓰기는 금지한다. 전체를 처음부터 다시 만드는 것은 2회까지이고, 넘으면 멈추고 그때까지의 결과를 보고한다
Canva 연동이 없으면: 2·3단계(뼈대 검토와 이 문서 수정)까지 하고 멈춘 뒤 연동이 없다고 보고한다

발표자 이제민이 10~15분 안에 처음 듣는 사람에게 세 가지를 이해시키는 자료를 만든다. 지난 모델 서빙 프로젝트가 무엇이었는지, 거기에 도커 컨테이너를 어떻게 입혔는지, 결과로 무엇이 되는지다. 제출을 위한 장식이 아니라, 발표자가 판단의 이유를 설명할 수 있는 자료여야 한다.

## 절대 규칙

1. 수치와 사실을 새로 만들지 않는다. 이 문서에 없는 수치를 쓰지 않는다.
2. `[갱신]` 표시 수치는 임시 값이다. 화면에서 눈에 띄게 표시해 두고, 확정된 것처럼 꾸미지 않는다.
3. 서비스 화면처럼 보이는 그림을 AI로 생성하거나 합성하지 않는다. 캡처 자리는 비워 두고 무엇이 들어갈지 적는다.
4. 실제 아이 사진이나 그림을 쓰지 않는다.
5. 비밀번호, 키, 토큰 같은 비밀 값을 자료와 보고에 쓰지 않는다.
6. 아래 "말하지 않을 것"을 화면과 노트 어디에도 쓰지 않는다.
7. 고정 사항(발표자, 3부 순서, 10~15분)을 바꿔야 한다고 판단되면 고치지 말고 이유를 보고한 뒤 묻는다.


## 해야 할 일

**1단계. 읽기.** 입력: "먼저 읽을 것"의 파일. 산출물 없음.

**2단계. 뼈대 검토와 보고.** 입력: 아래 "현재 뼈대". 아직 Canva를 건드리지 않는다. 아래 기준으로 판단하고, 근거 없이 칭찬하거나 동의하지 않는다. 산출물은 다음 표다.

    장 | 판정(유지, 수정, 합침, 삭제) | 이유 | 어떻게 고칠지

표 위에 "이 뼈대로 만들어도 되는가"를 한 문장으로 먼저 쓴다. 문제가 없는 장은 유지로 적고 이유를 길게 쓰지 않는다.

검토 기준:
- 제목만 이어 읽어도 지난 프로젝트, 컨테이너 과정, 결과의 흐름이 이해되는가.
- 컨테이너를 배웠지만 이 서비스는 처음 보는 사람이 작업 큐, 워커, 컷아웃, 겹침 파일 같은 말을 따라올 수 있는가.
- 시간 합이 10~15분이고, 첫 실제 화면이 늦지 않은가. 시연은 지금 7분 25초에 시작해 권장선 7분을 조금 넘는다.
- 장마다 메시지가 하나이고 증거가 하나인가. 글만 있는 장이 없는가.
- "왜 그렇게 했는가"가 드러나는가. 기능 나열로 끝나지 않는가.
- 발표자는 한 명이지만 세 사람의 작업임이 드러나는가.
- 장 수가 많지 않은가. 줄여도 전달되면 줄인다.

**3단계. 뼈대 수정.** 입력: 2단계 표. 보고한 대로 이 문서를 먼저 고치고 같은 가지에 커밋한다. 커밋 형식은 `docs: 설명 (#47)`이다. 고정 사항을 건드리지 않는 수정은 다시 묻지 않고 진행한다. 산출물: 커밋 해시, 고친 장 목록(제목, 시간).

**4단계. Canva 제작.** 입력: 고친 뼈대, "스타일". 산출물: Canva 디자인 링크. "말할 것"은 발표자 노트에 넣는다.

**5단계. 점검과 보완.** 전 장을 렌더해서 하나씩 본다. 어긋난 곳을 고치고, 고친 장을 다시 본다. 산출물: 아래 끝나는 조건별 결과.


## 끝나는 조건

- 2단계 표가 보고에 있다.
- Canva 디자인 링크가 있고, 연결 공개 설정을 바꾸지 않았다.
- 전 장에 템플릿 자리 글(Lorem ipsum, reallygreatsite, 전화번호 등)이 0건이다.
- 전 장에 템플릿의 미술관 사진과 명화가 0건이다.
- 장 제목이 모두 결론 문장이고 영어 항목 이름("OUR PROJECT" 등)이 아니다. 표지와 전환 장은 예외다.
- 한글이 깨지거나 잘리거나 겹친 장이 0건이다. 렌더 확인으로 판정한다.
- 본문 18pt 이상, 장 제목 28~32pt, 근거와 쪽 번호 12pt 이상이다.
- 장별 시간 합이 10~15분 안에 있다.
- `[갱신]` 표시 수치 목록과 캡처 자리 목록이 보고에 있다.

## compose 구성도 (5장)

    브라우저 ──9501──▶ web(nginx) ─┬─ /v1/*, /live, /ready ──▶ app-api ──▶ db(MariaDB, 작업 큐)
                                   └─ /v1/models/* ─────────▶ model-api
    메일 확인 ──8025──▶ mailpit
    sweeper(정리), worker-cpu(M1 분리, M2 판정, M5 입체) ──▶ db
    한 번만 도는 것: db-migrate(스키마, 개발용 모델 활성)
    볼륨: db-data, artworks, worker-state. 실제 모델은 hf-cache 추가

그림으로 다시 그린다. 글자가 작아지면 경로 이름을 빼고 역할 이름만 남긴다.


## 서비스와 기술 사실

- 서비스: 보호자가 아이 그림을 찍어 올리면 서버 모델이 그림을 종이에서 떼어 내고 입체 작품으로 만들어 브라우저 3D 미술관에 건다. 문제(작품을 버리기 곤란한 부모)는 가설이며 수요는 검증하지 않았다.
- 원칙: 판정은 제안까지만 한다. 원본을 덮어쓰지 않는다. 아이는 별칭으로만 등록한다. 아이 사진을 외부 AI로 보내지 않는다. 결과를 보호자가 승인해야 전시가 바뀐다.
- 지난 구성: 화면 Vue 3, 앱 API Node·Express, 모델 API FastAPI, 워커 Python, DB MariaDB(도메인 자료와 작업 큐를 함께 둠), 한 서버에서 pm2로 실행.
- 모델: M1 BiRefNet(그림 분리), M2 OpenCLIP(무엇을 그렸는지 판정), M5 Depth Anything V2 Small(입체). 움직이는 그림(M3)과 3D 조각(M7)은 가짜 어댑터, 작품 설명(M6)은 끔.
- 3D 화면: Vue와 three.js. 방 배치와 캐릭터는 기기에 저장하고, 작품만 서버를 쓴다.
- 컨테이너: 상시 서비스 7개(web, app-api, sweeper, db, mailpit, model-api, worker-cpu)와 한 번 도는 db-migrate. 뺀 것은 worker-gpu, TorchServe, 설명 서버, 레지스트리, 모니터링이다.

## 말하지 않을 것

- 보호자의 만족이나 수요.
- 실제 아이 그림에서의 품질. 합성 그림과 팀이 그린 그림으로만 시험했다.
- 시험 결과가 나오기 전의 "세 PC 통과".
- 움직이는 그림이 된다는 말.
- 조건을 뺀 처리 시간.
- "Windows에서는 실제 모델이 안 돌아간다"는 단정. 한 PC의 1회 측정이다.
- 시연 모델과 세 PC 결과를 #41·#43과 최종 결정 전에 확정값처럼 쓰는 것. 이어받기가 항상 끝까지 완료된다거나 특정 시간이 걸린다고 말하는 것(78~230초였고, 한 번은 제한 시간을 넘겨 원본 액자로 남았다).
- "완벽", "혁신적", "최초" 같은 말.


## 시연 대비

- 맥에서 `docker compose -f compose.yaml -f compose.real.yaml up -d --build`로 미리 띄운다(자체 모델이면 마스터플랜 3-6대로 발표용 사본을 만들고, 명령 앞에 `OWN3_MANIFEST=./models/own3/manifest.demo.yaml`을 붙여 `compose.own3.yaml`을 더 겹친다. 사본 없이는 `db-migrate`가 멈춘다). `--build`를 빼면 오래된 이미지로 M1이 뜨지 않을 수 있다.
- 첫 처리는 느리니 리허설 때 한 장 돌려 둔다. 그래도 늦으면 미리 처리한 작품임을 말하고 보여 준다.
- 시연 전에 다른 컨테이너, 브라우저 시험, 빌드를 모두 끈다. 분리 제한이 60초이고 넘으면 입체 대신 액자로 낮아진다. M1은 다른 작업이 없으면 17~20초지만, 겹치면 28~40초로 늘고 51초까지 가거나 60초를 두 번 넘겨 액자로 남았다(마스터플랜 7절, #41). own3는 같은 합성 그림에서 사진 올림부터 분리·판정 끝까지 3초 안에 끝났다(1회).
- 그림은 팀이 그린 것을 쓴다.
- 자르기 창에서 네 모서리를 종이에 맞춘 뒤 올린다. 처음 네모는 거의 사진 전체다. 그대로 누르면 own3는 책상 무늬가 남고 어두운 사진은 그림이 뜯기며, BiRefNet은 종이째 깔끔하게 따지만 손은 남는다. 맞춰 올리면 합성 시험 사진 7장에서 둘 다 대체로 깔끔했다. own3는 어두운 사진의 선이 거칠고 2장에서 작은 동그라미가 사라졌으며, 손을 그대로 남겼다. 리허설에서 실제 사진으로 다시 본다.
- 시연 로그인은 카카오다(#93, 마스터플랜 3-3 #88). `.env`에 `KAKAO_REST_API_KEY`·`KAKAO_CLIENT_SECRET`이 있는 저장소 폴더에서 띄우고 `http://localhost:9501`로 연다. `.env`가 없는 복제본에서 띄우면 카카오 버튼 없이 이메일 화면이 나온다. 화면을 여는 주소, `APP_BASE_URL`, 카카오 콘솔 Redirect URI는 글자까지 같아야 한다. 리허설 때 실제 계정으로 한 번 돌려 본다.
- 막히면 맥 compose로 넘어간다. 영상은 찍지 않는다. 넘어가는 기준은 리허설에서 정한다.

## 보고 형식

1. 이 뼈대로 만들어도 되는가: 한 문장.
