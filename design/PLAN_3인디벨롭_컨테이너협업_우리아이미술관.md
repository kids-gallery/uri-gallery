# 우리 아이 미술관 마스터플랜(모델 서빙 서비스에 3D 화면을 입혀 Docker Compose로 완성하고 발표하기, 5일)

작성 2026-10-28, 고침 2026-10-29(화면을 3D 미술관으로 바꿈). 독자는 함께 작업할 팀원 3명이다. 날마다 교안의 무엇을 함께 복습하고 무엇으로 확인하는지는 `docs/공통/컨테이너배포_팀가이드.md`에 있다.

**무엇을 바꾸나(사용자 결정 2026-10-29).** 모델 서빙(app-api · 작업 큐 · 워커 · 모델 · DB)은 지난 판 그대로 쓴다. 보호자 화면만 브라우저 3D 미술관(`web/src/app/world/`, 주소 `/app/world`)으로 바꾼다. 3D 미술관은 지금 서버 없이 기기 안에서만 돈다(배경 지우기는 브라우저 규칙, 저장은 IndexedDB). 그래서 이번 작업의 개발 몫은 **3D 화면이 모델 서빙 API를 쓰게 잇는 것**이고, 나머지는 전체를 컨테이너로 감싸는 것이다.

## 1. 이루려는 것(5일)

- **핵심 하나.** `docker compose up -d` 한 명령으로 서비스가 뜬다. 3D 미술관에서 가입 → 사진 올리기 → 서버 모델이 분리(M1)·판정(M2)·결과(M5 부조 또는 액자) → 보호자가 확정 → 입체 작품이 3D 미술관에 걸리는 한 바퀴가 된다.
- **발표.** 그 한 바퀴를 실제 화면으로 시연하고, 모델 서빙을 컨테이너로 어떻게 나눴는지 설명한다(6절).
- **작업 기록.** 각자 맡은 부분을 자기 PR로 만들고, 고른 것과 버린 것을 설명할 수 있게 남긴다(7절).
- 기간이 짧아서 핵심 흐름에 필요 없는 일은 하지 않는다(10절). 시간이 남아도 범위를 늘리지 않고 발표 준비에 쓴다.
- 팀원 3명이 직접 만든다. 저장소에는 미리 만든 Dockerfile·compose 파일·연결 코드가 없다.

## 3. 만들 것(5일 범위)

### 3-1. 완성 기준

```
3D 미술관(브라우저) ──/v1/*──▶ app-api ──한 트랜잭션──▶ DB(작품 + 원본 액자 + 작업 등록)
                                                          │
                       worker-cpu ◀── stage_job 작업 표 ──┘   M1 분리 → M2 판정 → (확정 뒤) M5 부조 또는 액자
   3D 미술관 ◀── 작품 상태·컷아웃·결과 파일 ── app-api ◀── DB
```

- 사진을 올리면 원본 액자가 먼저 걸린다(서버 규칙). 보호자가 부조 결과를 승인해 걸리면 3D 화면이 컷아웃으로 입체를 다시 만든다(3-3 "전시 목록", #40).
- 권유 확정과 결과 결정은 3D 화면 안의 작은 창 두 개로 한다.
- 모델은 CPU로 돈다(`GPU_ENABLED=false`). 움직이는 그림(M3)·3D 조각(M7)은 가짜 어댑터(`UAM_FAKE_MODELS=M3,M7`). 설명(M6)은 끈다. 메모리가 작은 PC는 전부 가짜(`UAM_FAKE_MODELS=1`)로 같은 흐름을 돈다.
- 3D 화면의 방 배치·캐릭터·놀이 진행은 지금처럼 기기에 둔다(이번 범위 밖). 서버 판에는 백업을 두지 않는다(3-3, #124).

### 3-2. compose 구성(설계 PR #20에서 확정, 2026-10-30)

| 서비스 | 이미지 | 바깥 포트 | 볼륨 | 상태 확인 | 담당 |
|---|---|---|---|---|---|
| web(입구) | 빌드 단계 `node:22.23.4-bookworm-slim`(`VITE_WORLD_SERVER=1 npm run build:world`) → 실행 단계 `nginx:1.28.0-alpine` | 9501 | 없음 | `/` 응답 | 신지현 |
| app-api | api 이미지(`node:22`) | 없음 | 작품 파일 | `/live`·`/ready` | 이제민 |
| sweeper | app-api와 같은 이미지, 실행 명령만 다르다 | 없음 | 작품 파일 | 프로세스가 살아 있음 | 최호준(서비스 설정), 이제민(이미지) |
| db | MariaDB 공식 이미지(12.0 계열) | 없음 | DB 자료 | 공식 이미지의 확인 스크립트 | 최호준 |
| mailpit | Mailpit 공식 이미지 | 8025(메일 화면) | 없음 | 없음 | 최호준 |
| model-api | serving 이미지(`python:3.11`) | 없음 | 작품 파일(쓰기: 외부 요청 사진), 작업자 상태 폴더(읽기·쓰기: 워커 상태 읽기, 지금 불러오기 요청 쓰기) | `/internal/ready` HTTP 응답(자기 프로세스) | 최호준 |
| worker-cpu | model-api와 같은 이미지 + 모델 묶음, 실행 명령만 다르다 | 없음 | 작품 파일(쓰기), 작업자 상태 폴더(쓰기), 모델 가중치(읽기 전용), 모델 쓰기 캐시 | 상태 파일이 60초 안에 갱신됨 | 최호준 |

- nginx: `/`는 `dist-world` 정적 파일(없는 경로는 `index.html`), `/v1/*`·`/live`·`/ready`는 app-api, `/v1/models/*`는 model-api. 화면과 API가 같은 출처라 CORS가 필요 없다(쿠키 세션 그대로).
- 기동 순서: db 준비 → db-migrate(스키마, 개발 환경이면 모델 첫 활성까지) 완료 → app-api·sweeper·model-api·worker-cpu. 준비됨의 기준은 3-5 6번 표. 상시 서비스는 `restart: unless-stopped`, db-migrate는 `restart: "no"`. 모든 서비스 `init: true`(종료 신호 전달용이고 정상 종료를 보장하지는 않는다, 3-5 6번).
- 메일을 끄면 이메일 가입도 꺼지므로(`api/src/modules/auth/routes.ts` 66행) Mailpit을 둔다.
- 비밀 값(사용자 결정 2026-10-30): 비밀번호·키(`DB_PASSWORD`, `SESSION_SECRET`, `AUTH_HMAC_SECRET` 등)는 compose `secrets:`로 `secrets/` 폴더의 파일을 컨테이너에 넣는다(`/run/secrets/…`). 환경 변수와 달리 `docker inspect`에 값이 보이지 않는다. `secrets/`의 실제 값 파일은 `.gitignore`로 저장소에 올리지 않고, 빈 예시(`secrets/*.example`)만 올린다. 리뷰어 확인 목록(4-1)의 "비밀 값"에 이 폴더를 넣는다. 비밀이 아닌 설정(주소, 포트, 켜고 끄는 값)은 `.env`(`env_file`)로 넘긴다. MariaDB 공식 이미지는 `MARIADB_PASSWORD_FILE`을 바로 읽고, app-api는 `*_FILE` 값을 읽도록 고친다(3-4). 파일은 `ops/docker/make-secrets.sh`로 만든다. 파일은 400, 폴더는 700이고, 리눅스에서는 소유자를 컨테이너 사용자 번호(1000)로 둔다. compose의 파일 비밀은 호스트의 소유자와 권한을 그대로 들고 들어가고 `uid`, `mode` 지정이 적용되지 않으므로, 서버 계정 번호가 1000이 아니면 읽지 못한다. 체험 서버에 올려 처음 찾았고(#136) 맥과 WSL에서는 보이지 않았다(#140). 처음에 고른 444는 모든 계정이 읽는 권한이라 리뷰에서 버렸다.
- **#66 리뷰 반영:** 컨테이너 예시는 APP_HOST=0.0.0.0, MAIL_ENABLED=true를 각각 한 번 둔다. TRUST_PROXY의 compose망 CIDR과 고정 subnet은 #32에서 함께 정하며, 예시의 loopback은 그 전까지 기본값으로 명시한다. 호스트 pm2 배포 문서에는 주소·저장 경로·쿠키 값을 호스트 기준으로 설정하는 절차를 분리한다.
- **#25 설정 예시:** `.env.example`은 컨테이너용 비밀이 아닌 값만 둔다. DB는 `db:3306/uam`, 메일은 `smtp://mailpit:1025`, 모델 API는 `http://model-api:9541`, 메일 링크는 `http://localhost:9501`이다. HTTP 개발에서만 `SECURE_COOKIES=false`이고 HTTPS에서는 true로 바꾼다. 저장소 폴더에 `.env`가 있으면 `.env.example` 값을 덮어쓴다. pm2용으로 만든 옛 `.env`는 옮겨 두고 필요한 값만 넣는다. `secrets/db_password.example`, `session_secret.example`, `auth_hmac_secret.example`은 빈 안내 파일이며 실제 파일은 Git에서 제외한다. DB의 root 비밀번호도 개발 compose에서는 db_password 파일을 공유한다(#18 목록). API 파일 읽기는 #21, serving은 #23이 선행되어야 한다. `.env`를 프로그램이 자동으로 읽지 않으므로 로컬 개발 시험에는 환경 변수를 직접 넘긴다.
- 띄우지 않는 것: worker-gpu, TorchServe, 설명 서버.

- **#26 입구 이미지:** 저장소 루트에서 `docker build -f web/Dockerfile .`. 의존성 파일을 먼저 복사하고 `npm ci`한 뒤 웹 소스를 복사한다. `VITE_WORLD_SERVER=1`을 빌드 단계에서 고정한다. 실행 이미지는 `dist-world` 전체(생성된 `/licenses/THIRD_PARTY.txt` 포함)를 정적 루트에 담고 80번에서 받는다. API 라우팅과 SPA 대체는 #27에서 설정한다. 루트 `.dockerignore`를 재사용하며 `web/.dockerignore`는 만들지 않는다.

- **#27 nginx 계약:** 컨테이너 80번. `/v1/models/`는 `model-api:9541`, `/v1/`·정확한 `/live`·`/ready`는 `app-api:9521`로 원래 URI를 전달한다. `/internal`과 하위 경로는 404. `proxy_connect_timeout 3s`(앱을 끈 직후 사라진 IP에 연결을 기다리면 14초 동안 응답이 없어 끊김 안내가 늦다. 같은 망이라 정상 연결은 3초 안에 끝난다), `client_max_body_size 21m`, 개인 파일은 프록시·브라우저 캐시를 모두 금지한다. `Host`와 실제 직접 접속 주소 `$remote_addr`를 `X-Forwarded-For`로 전달하여 임의 전달 헤더 위조를 막는다. SPA는 `try_files`로 처리한다. #32는 web 9501:80과 #60의 신뢰할 프록시 CIDR을 함께 설정한다. Docker DNS를 요청 때 다시 조회하도록 server 안에 resolver 127.0.0.11 valid=5s ipv6=off와 app/model 주소 변수를 둔다. proxy_pass는 URI 접미사 없이 변수를 써 경로·쿼리를 보존한다. 앱 재생성으로 IP가 바뀌어도 5초 캐시 뒤 복구하고, 상류 이름이 아직 없어도 nginx 자체는 기동한다.

- **#32 compose 구현:** 빌드 이미지는 web·api·serving 3개를 재사용하고, 상시 7개와 db-migrate 일회성 서비스를 둔다. web·app-api·model-api만 연결하는 입구 망은 `172.30.88.0/24`로 고정하고 app-api의 TRUST_PROXY도 그 대역으로 제한한다. 대역 충돌 시 둘을 함께 바꾼다. 비밀은 파일 기반 compose secrets, 설정은 `.env.example` 뒤 선택적인 `.env` 순서로 주입한다. 가짜 모델 기본이며 실제 모델 의존성·가중치 마운트는 #42에서 추가한다. 모델 캐시는 #76에서 정한 `/data/hf-cache`를 따르되 해당 이미지 반영 전에는 사용하지 않는다. db-migrate의 이미지 경로와 모델 첫 활성은 #33 선행 미완료로 실제 기동은 막힐 수 있다.

**권유 확정 창(#38).** 상태 묻기가 받은 상세에서 `state`가 `awaiting_review`·`failed`가 아니고 `confirmedKind`가 null이며 `choices`가 있으면 화면 아래 알림에 연다. 보호자가 눌러야 창이 뜨며 자동으로 선택하지 않는다. `choices`만 활성 버튼으로, `unavailableChoices`는 이유와 함께 비활성으로 보인다. `confirmKind`로 확정하고 성공 후 `artWatch.add([id])`로 상태 묻기를 잇는다. 409는 상세를 다시 읽어 선택지를 갱신하고, 이미 확정된 작품이면 창을 닫고 안내한다. 확정과 409로 받은 상세는 바로 `details`에 넣어 옛 알림이 남지 않게 한다. 끊김 안내가 있으면 확정 알림을 숨긴다. 창을 연 작품이 더는 확정 대상이 아니면 창을 닫고 다음 작품의 알림을 보인다. 고른 선택지는 테두리와 굵기로 구분하고 상태 묻기로 받은 상세도 열린 창에 반영한다. M3이 가짜인 동안 3D 화면은 움직임을 권하지도 고르게 하지도 않는다.
**결과 결정 창(#39).** `state`가 `awaiting_review` 또는 `failed`인 상세는 화면 아래 알림에 둔다. 보호자가 눌러야 창을 열며, 결정 선택지는 API `choices`와 `unavailableChoices`를 따른다. 원본과 결과를 미리 보고 낮춤 안내를 표시한다. `retake`는 확인을 한 번 더 받고 응답의 `retake.childId`를 `selectedChild`에 보존한다. 결정 중 중복 제출을 막고 실패하면 상세를 새로 읽는다. `retake`로 지워진 작품은 `details`에서 빼고 전시를 다시 읽는다. 결정 응답의 상세는 바로 `details`에 넣는다. 알림은 끊김 안내, 결정, 확정 순으로 하나만 보인다. 창을 연 작품이 더는 결정 대상이 아니면 창을 닫고 다음 작품의 알림을 보인다. 미술관 화면을 떠난 뒤 도착한 결정 응답은 선택 아이·작품 목록·알림을 바꾸지 않는다. 미리 보기의 두 그림에는 "올린 사진"과 "결과" 이름표를 붙인다. 선택지는 그림의 칸과 겹쳐 읽히지 않게 한 열로 둔다. 작품이 움직이는 동안 명패를 접고, 끝나면 다시 보인다. 춤 메뉴는 명패 위에 뜬다(#119).

### 3-3. 3D 화면 ↔ API 연결(이번 작업의 개발 몫, 대응표는 #19)

`store.ts`(기기 저장) 옆에 서버를 쓰는 층을 하나 두고, 작품 관련 부분만 서버로 바꾼다.

| 3D 화면 지금(기기) | 바꿀 것(app-api) |
|---|---|
| 가족·아이를 기기 안 계정으로 만든다(`Account`) | 카카오로 시작(`/v1/auth/kakao/start`, 키가 있을 때). 키가 없으면 이메일 가입·로그인(`/v1/auth/signup`·`/v1/auth/login`, 확인 메일은 Mailpit). 아이 등록·선택(`/v1/children`) |
| 사진을 기기에서 처리한다(`processImage` → 브라우저 배경 지우기) | `POST /v1/artworks`로 올린다. 원본 액자가 바로 걸린다 |
| 입체를 바로 만든다 | `GET /v1/artworks/{id}`로 상태를 본다. 승인되어 걸린 결과가 부조면 `/v1/gallery`의 컷아웃(`auxUrl`)으로 입체를 다시 만든다(`buildRelief`는 그대로) |
| (없음) | 권유 확정 `POST /v1/artworks/{id}/confirm`, 결과 결정 `POST /v1/artworks/{id}/decision`: 3D 화면 안의 작은 창 두 개 |
| 작품 목록(`listArtworks`) | `GET /v1/gallery`·`GET /v1/artworks`, 파일은 `/v1/files/{token}` |
| 방 배치·설정·캐릭터·놀이 진행 | 그대로 기기에 |
| 함께 그린 그림 보관 | `POST /v1/artworks`(올린 사진과 같은 흐름, #124). 그대로 다시 보내면 같은 요청 번호로, 그림을 고쳤으면 새 번호로 보낸다. 같은 번호면 서버가 앞선 그림을 돌려주기 때문이다. [한계] 첫 요청이 저장되고 응답만 잃은 뒤 고쳐 보내면 앞선 그림도 작품으로 남는다 |
| 백업, 견본(시작 화면의 샘플 버튼 포함), 기기 자료 지우기 | 서버 판에 두지 않음(서버 작품을 담거나 지우지 못한다, #124). [한계] 캐릭터와 화면 설정은 백업할 수 없고, 작품은 보관함에서 한 점씩 내려받는다 |

- 서버에 닿지 않으면 화면에 알리고 다시 시도하게 한다. 기기 판으로 몰래 바꾸지 않는다(두 저장소가 섞이지 않게).
- 입장 준비의 셰이더 미리 컴파일(`compileAsync`)은 최적화일 뿐이라 8초까지만 기다린다(#131). three 0.170은 컴파일 중 재료가 지워지면 오류를 내고 약속을 끝내지 않아, 이 약속만 기다리면 "미술관을 준비하고 있어요"에서 멈춘다.
- 응답 타입은 OpenAPI에서 생성한 타입(`web/src/api/types.gen.ts`, `npm run gen:api`)을 쓴다.
- 개인정보 안내(`WorldPrivacy.vue`)를 바꾼다: 사진은 우리 서버로 보내 처리하고, 원본은 덮어쓰지 않으며, 아이 사진은 외부 API로 보내지 않는다.
- 서비스 워커(#44)는 앱 셸과 정적 자산만 캐시하고 `/v1`·`/live`·`/ready`·`/_files`는 가로채지 않는다. 활성화할 때 이전 `uam-world-*` 캐시를 삭제해 기존 개인 응답을 제거한다. 서버 판과 기기 판의 개인정보 안내는 각각 실제 저장 경로를 설명한다. 서버 판 설정 창은 작품이 미술관에 저장된다고 안내하고 기기 저장 상태 표시, 백업, 기기 자료 지우기를 두지 않는다(#124).

**서버 연결 층(`web/src/app/world/server/`, #28).** 3D 화면의 창들은 서버를 이 층으로만 부른다.

- 새 HTTP 코드를 만들지 않는다. `/app` 화면이 쓰는 `web/src/api/client.ts`(같은 출처·쿠키 세션·Problem Details → `ApiError`)와 `web/src/app/artwork.ts`의 작품 타입을 그대로 쓴다. `loadArtwork`는 `noRedirect` 없이 부르는 `/app` 화면용이라 쓰지 않는다. 이 층에는 #19 대응표 한 줄에 함수 하나만 둔다: `signup`·`verifyEmail`·`resendVerify`·`login`·`logout`·`me`·`listChildren`·`addChild`·`uploadArtwork`·`listArtworks`·`getArtwork`·`deleteArtwork`·`confirmKind`·`decide`·`gallery`.
- 모든 호출은 `noRedirect`로 부른다. 401이나 409 `no_family`가 와도 `/app/login` 등으로 화면을 옮기지 않고, 3D 화면 안에서 처리한다(401은 로그인 창 #30).
- 오류는 `failureOf(e)` 하나로 세 가지로 나눠 창에 넘긴다.

| 종류 | 언제 | 창이 할 일 |
|---|---|---|
| `offline` | 서버에 닿지 않음(네트워크 실패, 5xx. 단 503 `not_saved`는 아래 `refused`) | 연결되지 않는다고 알리고 다시 시도하게 한다. 화면 글에 "서버"를 쓰지 않는다(D48). 기기 저장으로 바꾸지 않는다 |
| `login` | 401 | 로그인 창을 연다 |
| `refused` | 서버가 거절(그 밖의 4xx, `not_saved`) | 이유 문장(`problemCopy`의 `reason`, `/app`과 같은 사전)과 칸별 이유(`fields`) |

**아이 고르기(`WorldChildren.vue`, #36).** 서버 판에서는 `/v1/children` 목록·등록을 쓰고 별칭 외 개인정보는 입력하지 않는다. 아이가 없으면 등록을 먼저 요구하고, 한 명이면 자동 선택, 여러 명이면 고른 아이만 전시한다. `selectedChild`를 업로드와 `GET /v1/gallery?child=`에 함께 전달한다. 아이를 바꾸면 전시 메모리를 비우고 새 목록을 읽어 이전 아이 작품이 남지 않게 한다. 아이 바꾸기로 들어오면 1명이어도 자동으로 고르지 않고 창을 유지한다. 화면의 아이 이름은 모두 고른 아이의 별칭을 쓴다. 세션을 지우면 아이 변경 모드도 초기화한다.

**사진 올리기(`web/src/app/world/server/upload.ts`, #31).** 올리기 창(`WorldUpload.vue`)이 서버로 사진을 보내고, 받은 원본 액자를 바로 건다.

- **켜는 값: 빌드 설정 `VITE_WORLD_SERVER=1`.** 값이 없으면 지금처럼 기기 판이다. compose의 web 이미지는 이 값으로 빌드한다(#26), 개발 서버는 `VITE_WORLD_SERVER=1 npm run dev`.
  - 고른 이유: 로그인(#30)·아이 선택(#36)·서버 전시(#40)가 끝나기 전에 전부 바꾸면 3D 화면이 그동안 쓸 수 없다. 세션이 있는지로 자동 전환하면 로그인이 풀렸을 때 기기 판으로 몰래 바뀌어 위 규칙을 어긴다. 한 빌드는 한 저장소만 쓴다.
  - 기기 판을 없애는 일은 #40 뒤에 따로 정한다.
- **요청 번호(`Idempotency-Key`):** 사진마다 UUID 하나를 만들어 다시 시도할 때도 그대로 쓴다. 서버가 UUID만 받는다. `crypto.randomUUID`는 https나 localhost에서만 되므로(#41의 `http://<IP>:9501`에서는 없음) `crypto.getRandomValues`로 대신 만든다.
- **작품 자르기(#118, 2026-11-03 이제민 결정).** 서비스 입력은 아이가 작품을 들고 찍은 사진이다. 그런 사진을 통째로 넣으면 M1·own3 모두 아이가 남고(17장, 눈으로 본 판단), 작품 부분으로 자른 뒤 넣으면 M1이 작품만 딴다. 그래서 서버 판은 사진마다 네 모서리를 확인한 뒤 **자른 판만 보낸다.** 선택 영역 밖은 전송되지 않는다. 영역 안에 얼굴이 남을 수 있으므로 보호자의 확인이 필요하고, 자동 얼굴 확인은 없다. 고른 이유: 모델을 고치지 않고 오늘 되는 유일한 방법이고 얼굴이 서버로 갈 위험도 줄인다. 자동으로 빼는 모델은 시험 중이다(own5). 사진마다 먼저 아이가 같이 찍혔는지와 그림인지 만들기인지 묻고, 둘 다 답하기 전에는 [이대로 쓰기]를 누를 수 없다. 그림은 벽 액자에, 만들기는 받침대에 조각상처럼 선다(D45, D46. 이제민 지시 2026-11-03: 다 액자에 걸면 안 된다). 이 종류는 `POST /v1/artworks`의 `making`으로 보내고, 답을 기본값으로 두지 않는다. 기본값을 두면 지금처럼 만들기가 액자에 걸린다. 모델이 종류를 권하는 일은 재기 전이라 쓰지 않는다. 같이 찍혔으면 위 38%를 뺀 아래쪽 넓은 사각형으로, 작품만 찍었으면 거의 전체로 시작한다. 답 없이 세로 사진을 아래쪽으로 시작했더니 깨끗한 세로 그림의 머리와 팔이 잘린 채 전시됐다. 아래쪽 사각형은 아이가 든 실제 사진 15장에서 사람이 잡은 작품 상자의 97% 이상을 담는다(측정, 작은 표본). 자동 판단은 쓰지 않는다. 자동 찾기(`detectPaper`)는 세로 견본 6장에서 0장, 아이가 든 사진 15장에서 3장만 찾았고, 얼굴 찾기는 그림 속 얼굴을 얼굴로 잡거나 놓쳤을 때의 대가가 크다. 편집판의 틀이 사진 비율과 어긋나 보이는 곳과 잘리는 곳이 달랐던 결함도 함께 고친다. 손에 든 작품을 찾지 못한다고 팀 기록에 있다. 여러 장은 차례로 확인한다. 건너뛴 사진은 올리지 않는다. 자른 판이 서버의 원본이 되므로 서버 판 화면은 이것을 '원본'이라 부르지 않고 '올린 사진'이라 부른다(보관함, 가까이 보기, 내려받기, 지우기 물음). 작품 종류 이름 '원본 액자'는 옛 화면과 함께 쓰는 말이라 두고, 동결 뒤 판단한다. [한계] 처음 사진은 어디에도 보관하지 않는다. 만들기처럼 네모가 아닌 작품은 손이 남을 수 있다. 실제 휴대폰 조작은 재지 않았다.
- **올리기 전 안내:** JPEG·PNG·HEIC, 한 장 20MB까지. 빈 파일·큰 파일·다른 형식은 서버에 보내지 않는다. 그래도 서버가 내용을 다시 검사하므로 깨진 사진은 서버 이유 문장으로 보인다.
- **다시 시도:** `offline`·`login`과 503 `not_saved`만 다시 시도할 수 있다. 그 밖의 `refused`는 같은 사진으로 다시 해도 안 되므로 버튼을 두지 않는다. `login`은 #30의 로그인 창이 생기기 전까지 안내 문장만 보인다.
- **어느 아이의 작품인가:** `selectedChild`(#36이 정함)를 먼저 쓰고, 없으면 아이가 1명일 때 그 아이로 한다. 0명이거나 여러 명인데 고르지 않았으면 올리지 않고 안내한다. 다른 아이 작품으로 들어가는 일을 막기 위해서다.
- **원본 액자 걸기:** 202의 `photoUrl`을 받아 화면용 사본을 만들고(`processImage`, 배경 지우기 없음) 3D 화면에 건다. 서버 판은 기기 저장소의 작품을 섞지 않는다. 올린 뒤 나이·주제 질문과 돌리기 버튼도 두지 않는다(서버가 이야기를 채우고 올린 작품은 고칠 수 없다, D46). 기기에 저장한다는 안내 띠와 브라우저 배경 지우기 결과 문구도 보이지 않는다. 화면이 그리지 못하는 사진(HEIC를 못 여는 브라우저)은 서버에는 보관됐으므로 실패로 치지 않고 안내만 한다.

**#29 가입·메일 확인 화면(2026-11-02).** #19 제안대로 미술관 입장 전 첫 화면에서 `/app/signup`으로 가입한다. 단독 배포 라우터에 `/app/verify`를 명시해 토큰이 사라지지 않게 한다. 링크 토큰은 화면에 표시·저장하지 않고 확인 직후 주소에서 제거한다. 확인 실패는 잘못되었거나 만료된 링크라는 안내와 이메일 재발송을 제공하며, 통신 실패는 성공으로 처리하지 않고 다시 시도한다. 가입은 이메일·비밀번호·비밀번호 확인을 기존 연결 층으로 전달한다. 성공 후에는 확인 메일 안내만 보이고 로그인 성공으로 간주하지 않는다. 390px에서는 한 열 카드, 1440px에서는 가운데 카드다. 로그인·세션은 #30이 담당한다. 메일 확인 성공은 세션 생성 완료이므로 미술관으로 들어가기를 안내한다. 토큰 없는 확인 화면은 me()로 세션을 확인해 성공하면 /app/world로 이동한다. 통신 장애는 failureReason으로 안내하고 같은 동작을 다시 시도하며, 401일 때만 확인 링크 재발급을 안내한다.

**#30 로그인 경계(2026-11-02).** 서버 판 `/app/world`는 `WorldSession`에서 `me()` 확인 후에만 미술관을 생성한다. 로그인 입력은 기존 `login`을 쓰며 성공 뒤 `me()`로 다시 확인한다. 새로고침·탭 복귀 시 세션을 확인하고 통신 실패는 다시 시도를 제공한다. failureOf는 부작용 없이 오류만 분류한다. me와 인증된 작품·아이 호출의 401만 만료 이벤트를 보내며 잘못된 로그인 비밀번호는 이벤트를 보내지 않는다. 복원 실패가 login일 때만 작품을 지운다. 로그인한 상태의 offline은 같은 미술관·작품을 유지하고 상태 묻기의 안내에 맡긴다. 로그아웃 버튼은 더보기 메뉴 안에 두어 기존 메뉴를 가리지 않는다. 로그아웃·만료 시 `WorldView`를 제거해 작품·선택·엔진 상태를 버리고, 메모리 작품 목록과 `selectedChild`를 지운다. 지연된 업로드가 로그아웃 뒤 작품을 다시 넣지 못하도록 세대 번호로 차단한다. 로그아웃 통신 실패도 사적인 화면은 비우되 완료로 표시하지 않고 다시 로그아웃 버튼을 둔다. 기기 판은 기존대로 동작한다. 가입 링크는 #29의 `/app/signup`으로 연결하며 두 PR 병합 후 함께 사용할 수 있다. 아이 등록·선택은 #36에서 연결한다.

**상태 묻기(`web/src/app/world/server/watch.ts`, #37).** 올린 작품의 처리 상태를 묻고, 통신 실패를 알린다.

- **언제 묻는가:** 3-5 5번의 기준대로 `stages`에 대기·실행 중 단계가 있는 작품만 묻는다. 간격과 숨긴 탭 처리는 `/app`의 `usePolling`을 그대로 쓴다. 화면을 벗어나면 멈춘다.
- **실패:** 위 표의 세 종류로 나눈다.

| 종류 | 묻기 | 화면 |
|---|---|---|
| `offline` | 계속 묻는다. 서버가 돌아오면 안내가 저절로 사라진다 | 안내와 다시 시도 버튼 |
| `login` | 멈춘다. 다시 시도하면 이어서 묻는다 | 안내와 다시 시도 버튼(#30 뒤에는 로그인 창) |
| `refused` | 그 작품만 묻기를 그만둔다(지워진 작품 등) | 이유 문장과 닫기 버튼 |

- **늦게 도착한 응답:** 묻기마다 번호를 매겨, 다시 시도·로그아웃·화면 이탈 뒤에 도착한 옛 응답은 버린다. 다시 시도를 기다리는 중에 화면을 벗어나도 묻기가 되살아나지 않고, 벗어난 뒤에는 작품을 더해도 묻지 않는다.
- 받은 상세는 `details`에 두며, 창(#38·#39)과 입체 교체(#40)가 이 값을 쓴다. 새로 고침하면 `GET /v1/artworks`의 작품을 한 번씩 다시 읽는다. 고른 아이가 있으면 그 아이의 작품만 읽는다. 진행 중인 작품만 고르면 확정·결정을 기다리는 작품의 창이 다시 뜨지 않기 때문이다. 진행 중이 아닌 작품은 한 번 읽고 묻기에서 빠진다. 목록을 못 읽으면 빈 목록으로 넘기지 않는다. 통신 실패 안내를 띄우고, 다시 시도할 때 목록부터 다시 읽는다(#85 리뷰). 목록은 첫 전시를 읽은 뒤 읽는다(먼저 읽으면 전시 재구성과 겹쳐 사진을 두 번 받는다). 로그아웃 뒤 도착한 목록 응답은 성공·실패 모두 버린다. 지운 작품은 묻기와 `details`에서 뺀다. 지운 작품이 남으면 알림이 사라지지 않고 전시 재구성이 되풀이된다. 전시가 달라졌을 때의 다시 읽기는 같은 차이에 대해 되풀이하지 않는다(못 여는 사진이 있으면 차이가 영구히 남기 때문이다).

**전시 목록(`web/src/app/world/server/gallery.ts`, #40).** 서버 판의 3D 화면은 `GET /v1/gallery`에 있는 작품만 건다.

- **만들기는 동상(#133, 2026-11-03 이제민 지시).** 그림은 액자에, 만들기는 받침대에 동상처럼 놓는다. 승인된 만들기 부조는 빌드 값과 상관없이 결과 깊이를 받아 앞뒤가 있는 둥근 입체를 만든다(`cutout.ts`의 `buildRelief`, #90에서 가져옴). 그림은 지금처럼 액자에 걸고, 깊이는 `VITE_RELIEF_DEPTH`로만 켠다. 승인 전과 액자로 고른 만들기는 사진 판으로 선다. 깊이를 못 받으면 두께판으로 낮춘다. [한계] 뒷면은 앞면을 본뜬 추정이고 뒤에서 본 진짜 모습이 아니다. 품질은 마스크와 깊이 모델에 달렸다. 실제 사진 2점(BiRefNet, Depth Anything)에서 1점은 작품만, 1점은 든 팔까지 입체가 됐다(눈 판단).
- **벽에 거는 판(#122, 2026-11-03 이제민 지적).** 자른 사진을 그대로 걸면 손과 옷이 보이고 모델 결과가 벽에 나타나지 않는다. 승인되어 걸린 부조는 컷아웃을 종이색 위에 놓고 색을 맞춘 전시용 판을 벽에 건다(`exhibit.ts`). 밝은 쪽 95% 분위를 흰색 기준으로 맞추되 1.35배까지만 밝힌다. 어두운 작품을 억지로 밝히지 않기 위해서다. 그림을 다시 그리지 않고 생성 모델을 쓰지 않는다(아이 그림이 아니게 된다). 보관함의 원본은 그대로다. 승인 전과 액자로 고른 작품은 자른 사진이 걸린다. 부조에서 액자로 바뀌면 판을 버리고 사진에서 다시 만들어 건다. 판을 만들지 못하면 자른 사진을 건다. [한계] 그림자 제거와 빠진 손 자리 복원은 하지 않는다. 품질은 모델 마스크에 달렸다.
- **컷아웃은 승인 뒤에만 쓴다.** 상세의 `cutoutUrl`은 판정 중에도 오지만 쓰지 않는다. `/v1/gallery`는 걸린 결과만 보여 주므로 `kind`가 `relief`일 때의 `auxUrl`만 입체에 쓴다. 고른 이유: 보호자 승인 없이 전시 모습이 바뀌지 않아야 하고, 새로 고침해도 같은 화면이어야 한다. 3-1·3-3의 옛 문장("컷아웃이 오면 입체")과 #40의 끝나는 조건("승인 뒤 교체, 미승인 비전시")이 어긋나 #40을 따랐다.
- **어느 아이:** `selectedChild`(#36)가 있으면 그 아이, 없으면 가족의 모든 아이. `/v1/gallery`는 `child`가 필수다.
- **받은 파일:** 작품마다 메모리에 두고, 결과 종류가 바뀔 때만 컷아웃을 받는다. 파일 주소는 5분 뒤 만료되므로(`api/src/modules/files/token.ts`) 받지 못하면 목록을 한 번 다시 읽어 새 주소로 받는다.
- **파일을 받지 못할 때:** 사진을 받으면 작품은 전시에서 사라지지 않는다. 깊이를 받거나 읽지 못하면 컷아웃 두께판으로, 컷아웃을 받거나 읽지 못하면 사진 액자로 낮춰 건다. 전시 화면에는 낮춤 원인을 표시하지 않으므로(BR-EXH-07) 안내를 띄우지 않는다. 못 받은 파일은 그 자리에서 목록을 한 번 다시 읽어 새 주소로 받고, 그래도 안 되면 다음 목록 읽기에서 다시 받는다. 컷아웃을 못 받은 작품은 액자로 보이므로 `hungResultKind`와 달라 상태 묻기가 목록을 다시 읽는다. 사진까지 못 받으면 그릴 것이 없어 이번 목록에서 빠지고 같은 방법으로 다시 받는다. 손상된 파일 하나가 전시 전체를 멈추지 않게 읽기를 `cutout.ts`의 `reliefMask` 한 곳에서 처리한다. [한계] 손상된 컷아웃은 입체와 전시에서는 낮춰지지만 보관함 미리보기는 깨진 그림으로 보인다. 미리보기가 파일을 그대로 쓰기 때문이다.
- **교체 시점:** 상태 묻기의 `hungResultKind`가 보이는 결과와 다르면 목록을 다시 읽는다.
- **실패:** 목록을 못 읽으면 보던 작품을 그대로 두고 상태 묻기와 같은 안내와 다시 시도를 보인다. 고른 아이가 있으면 그 아이의 작품만 남긴다. 다른 아이의 작품을 대신 보이지 않는다.
- **로그아웃(#30):** `clearGallery()`로 지운다. 그 전에 시작한 요청은 어느 단계에서 끝나든(파일, 방 읽기·저장) 옛 가족의 작품을 캐시·방·반환값에 남기지 않는다.
- **방 저장 실패:** 전시와 따로 다룬다. 기기 저장소 문제를 연결 실패로 알리지 않는다.
- **고치기와 지우기:** 올린 작품은 고칠 수 없으므로(D46) 서버 판에서 돌리기·제목과 추억 고치기·이야기 남기기를 보이지 않는다. 비어 있는 이야기 칸과 "나중에 적어도 돼요" 안내도 두지 않는다(#124). 지우기는 `DELETE /v1/artworks/{id}`로 보낸다.
- [한계] 움직임(`animated`) 결과는 3D 화면에 재생 경로가 없어 사진으로 보인다. 놀이에서 그린 그림은 기기에 저장되어 서버 판 목록에 나오지 않는다. 방 배치는 지금처럼 기기에 둔다.

**입력 사진의 방향과 HEIC.** API는 받은 바이트를 그대로 저장하므로(FR-22) 휴대폰 사진은 저장 방향과 표시 방향이 다를 수 있다. 지금 모델은 저장 방향으로 읽어 마스크, 컷아웃, 깊이가 저장 방향으로 나오고, 3D 화면은 표시 방향으로 그려 윤곽이 어긋난다. 자체 모델 어댑터로 합성 그림에서 잰 값으로, EXIF 방향 6일 때 어댑터는 `ok`를 돌려주지만 표시 방향 정답과의 IoU가 0.288이었다(방향을 맞추면 0.915). 어댑터가 저장 방향으로 읽는 것은 M1, M2, M3 코드도 같다. HEIC는 API가 받지만 워커가 열지 못해 `storage`로 끝났다. 그래서 `serving/common/images.py` 한 곳에서 표시 방향으로 열고 HEIC도 연다. M1, M2, M3 관절과 품질 검사가 이 함수를 쓰고, 파일 경로를 넘기는 M3 렌더에는 돌린 사본을 준다. M5는 표시 방향 컷아웃을 읽으므로 따라온다. HEIC는 pillow_heif가 열 때 회전 정보(irot)를 적용하고 EXIF를 1로 되돌리므로 두 번 돌지 않는다(irot이 든 합성 HEIC로 확인, 실제 아이폰 사진은 재지 않았다). irot 없이 EXIF 방향만 있는 HEIC는 돌지 않는다. 저장된 원본은 바꾸지 않는다. 이미 처리한 작품의 결과는 그대로이고, 다시 처리해야 맞는다.

**깨진 입력 사진.** EXIF가 깨져도 픽셀이 멀쩡하면 방향 없는 사진으로 처리한다. 방향 정보 때문에 전에는 되던 사진이 실패하면 안 된다. 읽지 못하는 파일은 형식과 상관없이 `OSError`로 모아 `storage`로 기록한다. PIL은 형식에 따라 `ValueError`, `SyntaxError`, `RuntimeError` 같은 다른 예외를 내고, 그대로 두면 `engine_down`으로 기록되어 파일 문제와 서버 문제를 나누지 못한다. `storage`도 인프라 실패라 재시도한다. 깨진 사진은 분리와 판정이 각각 3회 시도한 뒤 끝나므로, 끝날 때까지 재시도 대기만 최소 140초이고 자식 검사가 모두 시간 제한을 넘으면 최대 320초다(`limits.yaml`로 계산). 머리가 깨진 HEIC 일부는 libheif 안에서 프로세스를 죽여 파이썬에서 잡을 수 없다. 합성 HEIC 593바이트의 머리 바이트를 뒤집은 시험에서 약 100건 중 1건이 신호 11로 끝났고, 그 파일은 API 업로드 검사(`heic-decode`)를 통과했다. 한 작품의 입력이 워커와 다른 작업을 멈추면 안 되므로 HEIC는 자식 프로세스에서 먼저 디코드한다. 자식은 픽셀만 디코드하고 EXIF는 읽지 않는다. EXIF만 깨진 HEIC도 멀쩡한 사진이기 때문이다. 자식이 신호로 죽거나 실패하거나 시간 제한(`limits.yaml`의 `image.heif_check_timeout_s`)을 넘으면 `OSError`로 바꿔 `storage`로 기록하고, 원인은 경로 없이 반환 코드만 로그에 남긴다(BR-PRV-01). 워커는 살아 있고 다음 작업을 이어 간다. 고른 이유: HEIC 입력을 모두 거절하면 휴대폰 사진이 입체가 되지 못한다. JPEG와 PNG는 자식을 만들지 않는다. 통과한 파일은 경로, 크기, 수정 시각이 같으면 다시 검사하지 않는다. 통과한 HEIC의 추가 비용은 같은 워커에서 한 장에 한 번이다. 통과하지 못한 파일은 시도마다 다시 검사하므로 자식이 최대 6번 돈다. 컨테이너(CPU 2, 합성 그림, 5회 중앙값)에서 1024×768은 0.44초, 4032×3024(2.3MB)는 1.51초이고, 그중 디코드 자체가 0.05초와 0.99초다. JPEG와 PNG는 머리를 읽는 0.01ms뿐이다. 실제 아이폰 사진은 재지 않았다. [한계] 이 검사는 완전한 격리가 아니다. 자식의 디코드 결과를 쓰지 않고, 통과하면 부모가 같은 파일을 다시 연다. 그래서 검사 뒤 파일이 바뀌거나 자식과 부모의 디코더 상태가 다르면 부모가 죽을 수 있다. 입력 불변 조건은 저장한 원본을 덮어쓰지 않는 것이고(FR-22), 경로, 크기, 수정 시각이 같으면 같은 파일로 본다. 이번 시연 범위의 임시 조치로 둔다(2026-11-03 이제민 판단). 시연 사진은 JPEG로 한다. 공개 운영 전에 부모가 HEIC를 디코드하지 않게 바꾼다.

**컷아웃의 숨은 배경.** M1 컷아웃은 원본 크기에 알파만 더해 투명한 곳의 색이 파일에 남는다. 같은 가족은 원본도 볼 수 있으므로 추가 노출이 아니지만, 이웃 방문(`GET /v1/visit/children/:id/gallery`)은 부조 작품에 컷아웃만 주고 원본은 주지 않는다. 이 경로에서는 알파를 지우면 원본에서 가린 배경이 보인다. 이번 3D 배포본 화면에는 이웃 기능이 없어 API를 직접 부를 때만 해당한다. 또 투명한 곳의 색 때문에 컷아웃이 커져 합성 12MP 사진에서 24.63MB였다(잡음을 넣은 그림 기준). 그래서 `serving/common/cutout.py`에서 알파가 정확히 0인 화소의 RGB를 0으로 쓴다(같은 그림 5.37MB, 실제 사진의 감소폭은 재지 않았다). 보이는 화소와 부드러운 경계의 색은 그대로이고, 저장된 원본은 바꾸지 않는다. 컷아웃의 색을 읽는 M5, M7, 3D 화면은 투명한 곳의 색을 쓰지 않는다. API, DB, 모델 규칙은 바꾸지 않는다. 이미 만든 컷아웃은 그대로이고, 다시 처리해야 지워진다.

   - **실제 모델 이력(#42, 2026-11-03).** 가짜 행에 실제 어댑터가 붙으면 작업 기록이 실제 모델 결과를 `fake`로 남긴다. `compose.real.yaml`은 db-migrate에 `DEV_REAL_MODELS=M1,M2,M5`를 준다. 이 목록의 모델은 `MODEL_MANIFEST`의 `weights_sha256`, `config_hash`, `runtime`으로 활성 행을 만든다. 컨테이너에는 CPU 워커만 있으므로(`GPU_ENABLED=false`) `exec_device`는 `cpu`이고, 맥에서 잰 `runtime`의 `-mps`는 `-cpu`로 기록한다. M3는 가짜 어댑터이므로 `fake` 행을 유지한다.
     - 켜고 끌 때 활성 행도 따라간다. 활성 행이 개발용(`dev-` 이름)이고 지금 설정과 값이 다르면 `retired`로 내리고 새 행을 넣는다. 그래서 같은 볼륨에서 가짜↔실제, BiRefNet↔자체 모델로 바꿔도 활성 행과 어댑터가 어긋나지 않는다.

     - 켜는 명령에 `--build`를 붙인다. 이미지 태그가 남아 있으면 compose가 다시 빌드하지 않아, 옛 db-migrate가 `DEV_REAL_MODELS`를 조용히 무시하고 옛 워커가 돈다.

   - 빌드 맥락은 저장소 맨 위, `.dockerignore`는 맨 위에 하나(`node_modules`, `.env`, `secrets/`, `models/hf/`, `.data/`, 시험 결과물 제외). 의존성 파일을 먼저 복사해 설치하고 소스는 나중에. 정확한 판 번호는 각 이미지 PR에서 `docker pull`로 확인해 적는다(`latest` 금지). 기반 이미지는 판 번호 태그에 다이제스트를 함께 적는다(#140). 태그는 옮겨질 수 있고 다이제스트는 내용을 가리킨다. 여러 CPU의 목록을 가리키는 다이제스트라 arm64와 amd64가 같은 줄을 쓴다. 이미지는 각 PC가 빌드하므로 같은 이미지가 아니라 같은 레시피다. 레지스트리에서 같은 이미지를 받는 일은 하지 않았다(10절).
   - api 이미지는 운영 의존성과 빌드 결과만 담는다. [확인] `tsx`는 개발 의존성이고 빌드 결과는 `dist/src/server.js`·`dist/scripts/migrate.js`다. 그래서 명령은 `npm run …`이 아니라 `node`로 부른다. 이미지에 `/data/store`를 `node` 소유로 미리 만든다. 없으면 app-api가 새 작품 볼륨을 먼저 붙일 때 폴더가 root 소유가 되어 쓰지 못한다.

     | 서비스 | 명령 |
     |---|---|
     | app-api | `node dist/src/server.js`(지금 `package.json` `start`의 `dist/server.js`는 틀려서 고친다, #22) |
     | sweeper | `node dist/src/sweeper/main.js` |
     | db-migrate | `node dist/scripts/migrate.js`(`MIGRATIONS_DIR`은 이미지에 있음, #22) |

   - 이미지 안 경로는 저장소 구조를 따른다.

     | 무엇 | 이미지 안 경로 | 설정 값 |
     |---|---|---|
     | 앱 서버 빌드 결과 | `/app/api/dist` | |
     | SQL 마이그레이션 | `/app/db/migrations` | `MIGRATIONS_DIR` |
     | API 계약 | `/app/contracts` | `CONTRACTS_DIR` |
     | 모델 매니페스트 | `/app/models/manifest.yaml` | `MODEL_MANIFEST` |

3. **CPU 종류와 메모리.** 모델 묶음 잠금 파일은 빌드 인자로 고른다(arm64 `requirements-models.lock`, amd64 `requirements-models-linux-x86_64.lock`, #24). 기본은 전부 가짜 모델(`UAM_FAKE_MODELS=1`). 맥 arm64 컨테이너에서 세 모델을 한 프로세스로 돌렸다(아래). compose 안에서 도는 것은 [미검증]이다(#42·#43).
   - [확인] 워커 하나가 M1·M2·M5를 한 프로세스에 함께 올린다(`preload_all`). `limits.yaml`에 M1 CPU 추론 RSS 8.5GB가 적혀 있다. 이번 재측정에서는 재현되지 않았다. 최호준 PC의 Ubuntu 가상환경은 3284.7MiB(스왑 사용), 이제민 맥의 CPU 2스레드는 4827.1MiB다(#16, PR #64, 각 1회). 차이의 원인은 [미확인]이므로 8.5GB를 버리지 않고 #43에서 다시 잰다. 이제민 맥의 colima 가상 머신은 CPU 6개·메모리 14GiB다. 같은 PC에서 db·api·web도 메모리를 쓰므로, 할당량만으로 실행 가능하다고 보지 않는다.
   - [확인] 최호준 PC는 메모리 7.73 GiB, WSL 3.8 GiB다(#15, 2026-10-30). 이 PC에서 M1은 돌아가지만 추론이 109.678초로 `limits.yaml`의 split 제한 60초를 넘고, 그 값도 스왑을 쓴 1회 측정이다(#16). 신지현 PC도 메모리 7.70 GiB, WSL 3.7 GiB(사용 가능 2.4 GiB)로 비슷하다(#15). 그래서 Windows 두 대는 가짜 모델로 개발하고, 실제 M1·M2·M5 실행과 실측은 맥(이제민 PC)에서 이제민이 맡는다(2026-11-02 결정, #42·#43). Windows에서 M1 컨테이너 측정은 하지 않는다. [미검증] 가짜 모델 compose 전체도 WSL 사용 가능 메모리 2~3 GiB 안에 들어가는지는 #41에서 잰다. 모자라면 `%UserProfile%\.wslconfig`의 `memory`를 늘린다(PC 전체의 절반 이상).
   - #41(Windows WSL: 가짜 모델 compose의 메모리)과 #43(맥: M1·M2·M5)에서 `docker stats` 최대치를 재서 worker 메모리 한도를 정한다. [확인] 맥 컨테이너(CPU 6개, 2026-11-02, 800×600 합성 그림, 2회)에서 M1 추론 32.18·35.7초, M2 0.08·0.14초, M5 1.93·2.25초, 세 모델을 함께 올린 컨테이너 최대 메모리 6471.3·6547.9MiB다. 다른 작업이 돌던 때의 값이라 #43에서 다시 잰다. 메모리 3GiB 제한(CPU 2개)에서는 M1 단계에서 메모리 부족으로 죽었다(종료 코드 137). 그래서 worker 한도는 7GiB 아래로 두지 않는다. 최종 값은 #43에서 정한다.
   - [추론] 메모리가 모자라 worker가 죽으면 재시작되고, 맡던 작업은 점유 60초가 지난 뒤 다시 시도된다. 3번 실패하면 "결과 미도달"이다(`limits.yaml` `claim.seconds 60`, `retry.max_attempts 3`).

### 3-6. 자체 모델 선택 실행(기본 꺼짐)

M1(분리)과 M5(깊이) 자리에 자체 모델 own3를 켜서 쓸 수 있게 한다. 끄면 지금과 같다. 저장소 기본값은 BiRefNet·Depth Anything이다. 이번 발표 시연은 own3로 한다(2026-11-03 이제민 결정). 저장소의 `license_confirmed`는 `false`이고, 발표용 사본에서만 `true`로 둔다(아래 켜는 조건). 학습 자료는 합성 그림과 Quick, Draw!(CC BY 4.0)이고 시작 가중치는 없다. 후처리 값을 고를 때 연구 동의 자료를 썼고, 상업 조건의 전문가 확인 전이다.

- **이유.** CPU 한 번 실행 0.55~0.81초, 파이썬 프로세스 최대 메모리 0.82GB(맥, 임의 입력 448px)로 가볍다. M1이 60초 제한을 넘던 PC에서도 돌 수 있는지 볼 수 있다(그 PC에서는 아직 재지 않음). 합성 그림과 Quick, Draw!(CC BY 4.0)로 시작 가중치 없이 학습했다.
- **켜는 법과 시연 절차.** ① 가중치를 `models/own3/own3.ts`에 둔다. 저장소에 없는 파일이고, SHA-256이 `models/manifest.own3.yaml`의 `weights_sha256`과 같아야 올라간다. ② 포트나 망이 겹치는 다른 스택을 내린다. ③ 발표용 사본을 만든다(아래 켜는 조건). ④ `OWN3_MANIFEST=./models/own3/manifest.demo.yaml docker compose -f compose.yaml -f compose.real.yaml -f compose.own3.yaml up -d --build`. `--build`가 없으면 옛 이미지가 쓰여 3D 화면의 깊이가 꺼진 채로 남는다. ⑤ 시연 사진은 JPEG, 긴 변 1500 이하로 쓰고 그림이 화면을 가득 채우게 찍는다. own3는 그림이 작은 사진에 약하다. ⑥ 전시 방식은 입체 그림을 고른다. 약점은 3-6-1에 있다. 값은 `serving/config/own3.yaml`에 둔다.
- **구조.** `UAM_OWN_MODEL=M1,M5`이면 `serving/adapters/registry.py`가 own3 어댑터를 고른다. 출력 형식(마스크, 컷아웃, 깊이 PNG16)과 실패 처리(`quality_below`)는 M1·M5와 같다. 입력과 출력도 M1·M5와 같은 함수를 쓴다. 원본은 `open_upright`로 표시 방향에 맞춰 열고(3-4 입력 사진의 방향, 깨진 HEIC 처리 포함), 컷아웃은 `cutout_image`로 만들어 투명한 곳에 원본 배경을 남기지 않는다(3-4 컷아웃의 숨은 배경). 매니페스트는 `OWN3_MANIFEST`로 준 파일을 쓰고, 값이 없으면 `models/manifest.own3.yaml`을 쓴다.
- **가중치 확인(BR-MDL-01).** 적재할 때 파일 내용의 SHA-256을 `MODEL_MANIFEST`에 적힌 자기 자리(M1, M5)의 `weights_sha256`과 비교한다. 값이 다르거나 비어 있으면 적재 실패로 처리하고 모델을 올리지 않는다. 그 단계는 다른 모델의 적재 실패와 같이 `model_not_ready`로 닫힌다. 고른 이유: `model_version`에는 매니페스트 해시가 기록되므로, 파일이 바뀐 채 올라가면 결과가 다른 모델의 이력으로 남는다. 읽은 내용을 비교하고 그 내용을 그대로 올리므로 비교한 것과 실행하는 것이 같다. M1과 M5가 같은 파일을 쓰므로 프로세스에서 한 번만 읽는다. 23.3MB를 읽고 해시하는 데 맥 arm64에서 14~20ms, 컨테이너에서 첫 회 258ms와 이후 20ms 걸린다(각 5회). 실제 가중치로 M1 적재는 torch 불러오기를 포함해 1.72초, 이어지는 M5 적재는 0.007초다.
- **켜는 조건(BR-MDL-07).** 저장소의 `models/manifest.own3.yaml`은 M1·M5 `license_confirmed`가 `false`다. 활성화 코드는 용도를 구분하지 못하므로, 저장소에 `true`를 두면 발표 범위라는 제한을 코드가 지키지 못한다(#91 리뷰). 그래서 겹침 파일만으로는 켜지지 않는다. `db-migrate`가 종료 코드 1로 멈춘다. 발표 때만 가중치가 있는 PC에서 커밋되지 않는 사본을 만들어 경로를 명시한다.
  ```bash
  awk '/source: own3/{o=1} /license_confirmed:/{if(o){sub(/false/,"true");o=0}} 1' models/manifest.own3.yaml > models/own3/manifest.demo.yaml
  ```
  `models/own3/`는 `.gitignore`에 있다. 사본의 `true`는 2026-11-03 이제민의 발표 범위 판단이고, 상업 판단이 아니다. 발표가 끝나면 사본을 지운다. 지우지 않아도 `OWN3_MANIFEST`를 주지 않으면 읽지 않는다. 팀 서버와 운영 DB에는 사본을 쓰지 않는다. 이미 활성화한 DB의 행은 사본을 지워도 남으므로, 시연 DB를 내려 지운다. 서비스에 쓰려면 ① 상업 조건의 전문가 확인을 받고 ② 그 결과를 PR에 적어 팀이 검토한 뒤 ③ 저장소 값을 바꾼다. 대안인 `true` 유지와 수동 되돌리기는 병합된 값의 범위 밖 사용을 막지 못해 버렸고, 활성화 코드에 용도 검사를 넣는 안은 발표 하나를 위해 BR-MDL-07 경로를 넓혀 버렸다.
- **3D 화면의 깊이(`VITE_RELIEF_DEPTH=1`로 빌드할 때만).** 지금 3D 화면은 컷아웃으로 두께판을 만들고 결과 깊이(`primaryUrl`)를 읽지 않는다. 켜면 걸린 부조의 깊이를 받아 둥근 입체를 만든다(`cutout.ts`의 `buildRelief`). 앞면과 뒷면이 가장자리에서 만나고, 윤곽은 마스크로 자른다. 값은 `RELIEF_SURFACE`에 둔다. 깊이를 받거나 읽지 못하면 3-3의 "파일을 받지 못할 때"대로 낮추고 다음 목록 읽기에서 다시 받는다. 깊이를 켠 합친 판에서 파일 응답을 망가뜨려 확인했다(1440, 서비스 워커를 끈 상태, 깊이 503, 깊이 손상, 컷아웃 503, 컷아웃 손상). 작품 3점이 모두 남았고 깊이 실패는 두께판, 컷아웃 실패는 사각 판으로 보였으며, 응답을 되돌리면 둥근 입체로 돌아왔고 페이지 오류는 0건이다. 서비스 워커를 켠 상태의 실패는 시험 도구가 응답을 바꾸지 못해 보지 못했다. 끄면 깊이를 받지 않고 지금과 같다. 컷아웃을 받거나 읽지 못할 때 액자로 낮추는 것은 끈 빌드에도 같이 적용한다. 켜고 끄는 값은 웹 이미지 빌드 인자이며 `compose.own3.yaml`이 켠다.
- **출처 표기.** own3는 Quick, Draw!(CC BY 4.0) 획을 고쳐 만든 그림으로 학습했다. `web/public/licenses/MODEL_DATA.txt`에 출처와 변경 사실을 적고, 개인정보·이용 안내에 링크한다. 링크는 깊이를 켠 빌드(`VITE_RELIEF_DEPTH=1`)에서만 보인다. 기본 빌드의 기능은 own3로 배우지 않았으므로 안내하면 사실과 다르다. 활성에는 DB 제약상 `license_confirmed`가 필요하므로(`chk_mv_license_active`), 위 켜는 조건의 발표용 사본으로 켠다.

#### 3-6-1. own3와 기존 모델의 비교 결과(2026-11-03)

**판단.** 자른 그림에서는 own3가 낫고 실제 사진에 가까운 원본에서는 비겼다. 기본값은 바꾸지 않되 시연은 own3로 한다. 이유는 시간과 메모리가 크게 적고 품질은 원본에서 비겼기 때문이다. 약점은 작은 그림과 깊이 얼룩이다.

**시간과 메모리는 own3가 적게 든다.** 컨테이너 CPU 6개, 다른 일이 없는 상태에서 견본과 Quick, Draw! 10장을 운영 어댑터 값으로 쟀다.

| 적재(두 모델 합) | 0.87초 | 4.41초 |

전체 compose에서 worker의 `memory.peak`는 own3 스택 2.39GiB, 기존 모델 합본 8.35GiB다. 둘 다 M2를 포함하고 입력이 서로 달라 참고값이다.

원본 묶음을 그림이 차지하는 비율로 나누면 차이의 방향이 갈린다. 비율이 작으면 BiRefNet이, 크면 own3가 낫다. 비율 0.1 미만 18장의 평균 차이는 −0.149, 0.1 이상 42장은 +0.081이다.

실패 방식도 다르다. own3는 배경까지 잡고(정답 밖이 크다), BiRefNet은 그림을 덜 잡는다(놓침이 크다). BiRefNet의 분리 실패가 더 많은 것은 그림이 2% 아래로 잡혀서로 보인다(추론). 이 경우 액자로 낮아지므로 나쁜 결과는 아니다.

**눈으로 본 차이(견본 20장과 Quick, Draw! 20장, 가리지 않은 AI 판단, 사람 판정 아님).** BiRefNet은 깨끗한 그림의 경계가 또렷하고 Depth Anything의 깊이가 매끈하다. own3는 선 그림 안쪽을 채우고 떨어진 요소를 남기지만, 반만 채우거나 종이를 잡는 경우가 있고 깊이가 얼룩지며 선을 따라간다.

**이 표로 정하지 않은 것.** 위 판단은 사람 그림 참고값과 AI 판단에 기댄다. 사람의 판정, 새 묶음 판정, 망가짐 눈가림 재판정은 하지 않았다. 실제 가족 사진은 쓰지 않았다. 휴대폰과 Windows는 재지 않았다.

**시연 준비(2026-11-03 측정 반영).**

- 사진은 JPEG로, 긴 변 1500 이하로, 그림이 화면을 대부분 채우게 찍는다. 3D 화면 업로드에는 자르기가 없고, 전경이 작을수록 분리 품질이 낮다(M1·own3 공통, 공개 그림 원본 60장에서 전경 비율 0.1 미만은 IoU 중앙값 0.65 이하까지 떨어짐, 그림이 작을수록 더 낮다). 12MP 사진은 작품 하나에 수십 MB를 받을 수 있다(합성 그림 계산값, 휴대폰 미측정).
- 입체를 보여 줄 작품은 '입체 그림'을 고른다. M3이 가짜라 '움직이는 그림'은 재생되지 않는다.
- 시연 직전 사진 한 장을 올려 모델을 데운다. 다른 시험 스택은 내린다. 메모리가 빠듯하면 split이 60초 제한에 걸려 액자로 낮아진다(측정한 첫 split 24초, 맥 한 대에서 다른 작업이 겹칠 때 그림 하나가 100초를 넘은 적이 있다).
- 켜는 명령에 `--build`를 붙여 새 이미지로 띄운다.

## 8. 끝나는 조건

#45 실행 안내: 새 복제본에서 비밀 값 세 파일을 각기 생성하고 가짜 모델 compose를 빌드·시작한다. `down`에는 볼륨 삭제 옵션을 붙이지 않고 다시 시작해 작품 유지를 확인한다.

- 설계 PR이 구현 PR보다 먼저 병합돼 있다.
- 깨끗한 PC에서 `docker compose up -d` 뒤 가짜 모델로 3D 미술관 한 바퀴(가입 → 사진 → 확정 → 전시)가 된다.
- 맥에서 실제 모델(M1·M2·M5)로 한 바퀴가 된다.
- `docker compose down` 뒤 다시 `up` 해도 가족 작품이 남는다.
- 저장소에 `.env`·비밀 값·모델 가중치가 0건이다.
- 발표를 마쳤고 7절 수치와 각자 작업 기록이 있다.

## 10. 하지 않을 것

- 지난 판 평면 화면(`/app/...`의 3D 미술관 밖 화면)을 살리거나 고치기.
- 서비스 기능 바꾸기(모델 서빙 규칙·DB·API 계약). 3D 화면 연결에 꼭 필요한 것만 설계서를 먼저 고친 뒤 바꾼다.
- 3D 화면에 새 기능 더하기(연결 외). 작품 자르기(#118)는 이제민 결정으로 뺀 예외다.
- CI 옮기기와 이미지 자동 빌드, 레지스트리에 올리기, 태그별 되돌리기, 모니터링(Prometheus·Grafana), 장애 리허설과 운영 절차서, 백업 스크립트, 보안 점검표, GPU 이미지.
- M3·M6·M7을 실제로 컨테이너에 넣기.
- 게임 규칙(미션, 점수) 더하기.
- compose 한 바퀴 자동 확인(#140)은 위 CI 항목에서 이제민 결정으로 뺀 예외다.
- Dockerfile·compose를 한 사람이 대신 다 만들어 주기(리뷰와 짝 작업은 좋다).
- Kubernetes 같은 묶음 운영 도구, 유료 서비스, 승인 없는 공개 배포. 시연 체험 서버는 이제민이 승인한 예외다(3-5 #135).
- 시간이 남아도 위 항목을 다시 넣지 않는다.

`.github/ISSUE_TEMPLATE/`에 두 가지를 둔다(2026-10-30 추가). GitHub는 기본 가지(`main`)에 있는 양식만 보여 준다.

| 양식 | 쓰는 때 | 칸 | 칸을 둔 이유 |
|---|---|---|---|
| 작업 | 5절 표의 일 하나 | 한 줄 설명 · 이루려는 것 · 근거 · 대상 경로 · 해야 할 일 · 끝나는 조건 · 순서와 담당(날짜·담당·선행·리뷰어) | 한 줄 설명은 처음 보는 팀원이 제목만으로 모르는 일을 바로 알게 한다. 근거 칸은 그 일이 계획 범위 안인지(10절 "하지 않을 것"을 막음) 확인하게 한다. 대상 경로는 `CODEOWNERS`의 폴더 주인과 맞춰 리뷰어를 정하게 한다. "설계서 먼저" 체크는 절대 규정, 끝나는 조건은 8절처럼 남이 확인할 수 있는 결과, 선행은 "설계 PR이 먼저"와 compose 충돌 순서, 리뷰어는 4절 |
| 문제 | 작업 중 안 되거나 막힘 | 무엇이 안 되나 · 다시 만드는 방법 · 기대와 실제 · 근거 · 막는 범위 · 끝나는 조건 | 세 사람 환경(맥 arm64, Windows WSL x86_64)이 달라 환경과 명령 없이는 재현할 수 없다. 막는 범위는 그날 끝 확인(5절)에 걸리는지 보고 먼저 고칠 것을 정하게 한다 |

5절 일정을 이 양식대로 나눈 이슈 35개와 순서는 `docs/공통/이슈설계_컨테이너협업.md`에 있고, `docs/_claude/이슈올리기.py`가 그 목록을 양식 칸 순서대로 본문으로 만든다(양식 칸과 다르면 점검에서 멈춘다). 담당자 아이디와 리뷰어는 4절 표에서 읽으므로, 배정을 바꾸면 4절 표만 고친다. 이슈는 날짜별 마일스톤(`준비`, `1일차 10-30(금)` … `5일차 11-05(목)`)에 묶어, 마일스톤 화면에서 그날 이슈와 진행률만 보게 한다. 작업 중 올린 "문제" 이슈는 올린 날의 마일스톤에 넣는다. 제목은 작업 `[N일차·MM-DD 요일 · 담당] 대상과 할 일`(셋이 함께 맡으면 담당 자리에 `공통`), 문제 `[문제 · 올린 사람] 한 문장`이다. 목록과 알림에서 누가 볼 이슈인지 바로 보이게 하려는 것이다. 작업 이슈 제목의 담당은 스크립트가 이슈 목록의 "담당" 칸으로 만들므로, 배정을 바꾸고 다시 실행하면 제목도 함께 바뀐다. 가지·커밋·PR에는 이슈 번호를 쓴다(4-1). 이슈와 PR은 번호를 같이 쓰므로 둘의 번호는 맞지 않는다.
