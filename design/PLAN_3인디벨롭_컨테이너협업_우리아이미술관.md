# 우리 아이 미술관 마스터플랜(모델 서빙 서비스에 3D 화면을 입혀 Docker Compose로 완성하고 발표하기, 5일)

작성 2026-10-28, 고침 2026-10-29(화면을 3D 미술관으로 바꿈). 독자는 함께 작업할 팀원 3명이다. 날마다 교안의 무엇을 함께 복습하고 무엇으로 확인하는지는 `docs/공통/컨테이너배포_팀가이드.md`에 있다.

**무엇을 바꾸나(사용자 결정 2026-10-29).** 모델 서빙(app-api · 작업 큐 · 워커 · 모델 · DB)은 지난 판 그대로 쓴다. 보호자 화면만 브라우저 3D 미술관(`web/src/app/world/`, 주소 `/app/world`)으로 바꾼다. 3D 미술관은 지금 서버 없이 기기 안에서만 돈다(배경 지우기는 브라우저 규칙, 저장은 IndexedDB). 그래서 이번 작업의 개발 몫은 **3D 화면이 모델 서빙 API를 쓰게 잇는 것**이고, 나머지는 전체를 컨테이너로 감싸는 것이다.

## 1. 이루려는 것(5일)

- **핵심 하나.** `docker compose up -d` 한 명령으로 서비스가 뜬다. 3D 미술관에서 가입 → 사진 올리기 → 서버 모델이 분리(M1)·판정(M2)·결과(M5 부조 또는 액자) → 보호자가 확정 → 입체 작품이 3D 미술관에 걸리는 한 바퀴가 된다.
- **발표.** 그 한 바퀴를 실제 화면으로 시연하고, 모델 서빙을 컨테이너로 어떻게 나눴는지 설명한다(6절).
- **작업 기록.** 각자 맡은 부분을 자기 PR로 만들고, 고른 것과 버린 것을 설명할 수 있게 남긴다(7절).
- 기간이 짧아서 핵심 흐름에 필요 없는 일은 하지 않는다(10절). 시간이 남아도 범위를 늘리지 않고 발표 준비에 쓴다.
- 팀원 3명이 직접 만든다. 저장소에는 미리 만든 Dockerfile·compose 파일·연결 코드가 없다.

## 3. 만들 것(5일 범위)

### 3-1. 완성 기준

```
3D 미술관(브라우저) ──/v1/*──▶ app-api ──한 트랜잭션──▶ DB(작품 + 원본 액자 + 작업 등록)
                                                          │
                       worker-cpu ◀── stage_job 작업 표 ──┘   M1 분리 → M2 판정 → (확정 뒤) M5 부조 또는 액자
   3D 미술관 ◀── 작품 상태·컷아웃·결과 파일 ── app-api ◀── DB
```

- 사진을 올리면 원본 액자가 먼저 걸린다(서버 규칙). 서버가 M1 컷아웃을 만들면 3D 화면이 그 그림으로 입체를 다시 만든다.
- 권유 확정과 결과 결정은 3D 화면 안의 작은 창 두 개로 한다.
- 모델은 CPU로 돈다(`GPU_ENABLED=false`). 움직이는 그림(M3)·3D 조각(M7)은 가짜 어댑터(`UAM_FAKE_MODELS=M3,M7`). 설명(M6)은 끈다. 메모리가 작은 PC는 전부 가짜(`UAM_FAKE_MODELS=1`)로 같은 흐름을 돈다.
- 3D 화면의 방 배치·캐릭터·놀이·백업은 지금처럼 기기에 둔다(이번 범위 밖).

### 3-2. compose 구성(설계 PR에서 확정)

| 서비스 | 이미지 | 바깥 포트 | 볼륨 | 상태 확인 | 담당 |
|---|---|---|---|---|---|
| web(입구) | 빌드 단계 `node:22`(`npm run build:world`) → 실행 단계 nginx | 9501 | 없음 | `/` 응답 | 최호준 |
| app-api | api 이미지(`node:22`) | 없음 | 작품 파일 | `/live`·`/ready` | 신지현 |
| sweeper | app-api와 같은 이미지, 실행 명령만 다르다 | 없음 | 작품 파일 | 프로세스가 살아 있음 | 신지현 |
| db | MariaDB 공식 이미지(12.0 계열) | 없음 | DB 자료 | 공식 이미지의 확인 스크립트 | 신지현 |
| mailpit | Mailpit 공식 이미지 | 8025(메일 화면) | 없음 | 없음 | 신지현 |
| model-api | serving 이미지(`python:3.11`) | 없음 | 작품 파일, 작업자 상태 폴더, 모델 가중치(읽기 전용) | `/internal/ready` | 이제민 |
| worker-cpu | model-api와 같은 이미지 + 모델 묶음, 실행 명령만 다르다 | 없음 | 위와 같음 | 상태 폴더 기록 | 이제민 |

- nginx: `/`는 `dist-world` 정적 파일(없는 경로는 `index.html`), `/v1/*`·`/live`·`/ready`는 app-api, `/v1/models/*`는 model-api. 화면과 API가 같은 출처라 CORS가 필요 없다(쿠키 세션 그대로).
- 기동 순서: db가 준비된 뒤 app-api·model-api·worker-cpu(`depends_on`의 `service_healthy`). 모든 서비스 `restart: unless-stopped`.
- 메일을 끄면 이메일 가입도 꺼지므로(`api/src/modules/auth/routes.ts` 66행) Mailpit을 둔다.
- 띄우지 않는 것: worker-gpu, TorchServe, 설명 서버.

### 3-3. 3D 화면 ↔ API 연결(이번 작업의 개발 몫)

`store.ts`(기기 저장) 옆에 서버를 쓰는 층을 하나 두고, 작품 관련 부분만 서버로 바꾼다.

| 3D 화면 지금(기기) | 바꿀 것(app-api) |
|---|---|
| 가족·아이를 기기 안 계정으로 만든다(`Account`) | 이메일 가입·로그인(`/v1/auth/signup`·`/v1/auth/login`, 확인 메일은 Mailpit), 아이 등록·선택(`/v1/children`) |
| 사진을 기기에서 처리한다(`processImage` → 브라우저 배경 지우기) | `POST /v1/artworks`로 올린다. 원본 액자가 바로 걸린다 |
| 입체를 바로 만든다 | `GET /v1/artworks/{id}`로 상태를 본다. 컷아웃(`cutoutUrl`)이 오면 그 그림으로 입체를 다시 만든다(`buildRelief`는 그대로) |
| (없음) | 권유 확정 `POST /v1/artworks/{id}/confirm`, 결과 결정 `POST /v1/artworks/{id}/decision`: 3D 화면 안의 작은 창 두 개 |
| 작품 목록(`listArtworks`) | `GET /v1/gallery`·`GET /v1/artworks`, 파일은 `/v1/files/{token}` |
| 방 배치·설정·캐릭터·놀이·백업 | 그대로 기기에 |

- 서버에 닿지 않으면 화면에 알리고 다시 시도하게 한다. 기기 판으로 몰래 바꾸지 않는다(두 저장소가 섞이지 않게).
- 응답 타입은 OpenAPI에서 생성한 타입(`web/src/api/types.gen.ts`, `npm run gen:api`)을 쓴다.
- 개인정보 안내(`WorldPrivacy.vue`)를 바꾼다: 사진은 우리 서버로 보내 처리하고, 원본은 덮어쓰지 않으며, 아이 사진은 외부 API로 보내지 않는다.
- 서비스 워커가 `/v1/`을 캐시하지 않는지 확인한다.

### 3-4. 컨테이너로 옮기며 고칠 코드(작게, 설계서 먼저)

| 고칠 것 | 왜 | 담당 |
|---|---|---|
| app-api 바인딩 주소를 설정 값으로(기본값은 127.0.0.1) | 코드에 고정돼 다른 컨테이너가 부를 수 없다(`api/src/server.ts` 14행) | 신지현 |
| app-api 프록시 신뢰 범위를 설정 값으로 | 입구가 다른 컨테이너가 되면 요청 한도가 모든 사용자에게 한 IP로 걸린다(`api/src/app.ts` 24행) | 신지현 |
| model-api 바인딩 주소를 설정 값으로 | 같은 이유(`serving/model_api/main.py` 8행) | 이제민 |
| 모델 묶음 잠금을 CPU 종류에 따라 고르는 빌드 인자 | 맥(arm64)과 Windows(x86_64)가 같은 Dockerfile을 쓴다 | 이제민 |
| `.gitattributes`(줄바꿈 LF) | Windows에서 셸 스크립트가 CRLF가 되면 컨테이너에서 깨진다 | 최호준 |

### 3-5. 설계 PR에서 답할 질문

설계 PR(1일차 끝~2일차 오전)이 아래에 답하고 3-2·3-3을 확정한다.
1. **서비스 나누기.** 3-2의 7개로 충분한가. 같은 코드를 쓰는 둘(app-api·sweeper, model-api·worker-cpu)은 이미지 하나를 나눠 쓰는가.
2. **이미지.** 기반 이미지와 판 번호, 의존성을 먼저 깔고 소스를 나중에 넣는 순서, `.dockerignore`.
3. **CPU 종류와 메모리.** 잠금 파일을 빌드 인자로 고르는 방법. M1 추론 중 8.5GB를 어떻게 다루는가(메모리 한도, 작은 PC는 가짜 모델).
4. **데이터.** 볼륨 4개(DB, 작품 파일, 작업자 상태 폴더, 가중치)를 어떻게 붙이는가. 가중치는 어디서 받는가(`models/manifest.yaml`).
5. **연결.** 3-3 표의 화면 흐름: 로그인 화면을 3D 화면 어디에 두는가, 상태를 얼마 간격으로 묻는가, 확정·결정 창은 어디에 뜨는가, 서버에 닿지 않을 때 무엇을 보이는가.
6. **기동.** 서비스마다 "준비됨"의 기준, DB 스키마를 넣는 때(`npm run db:migrate`).

### 4-1. PR 자동 검사(리뷰봇)

**이루려는 것.** 핸드북 규칙과 이 계획서의 범위를 지키지 않은 PR을 사람 리뷰 전에 걸러낸다. 걸러진 PR에는 무엇이 왜 문제이고 어떻게 고치는지를 남긴다. 사람 리뷰를 대신하지 않는다. 승인은 사람이 하고, 병합은 팀장이 한다.

**파일.** `.github/workflows/review-bot.yml`(실행), `.github/review-bot/rules.json`(규칙 값), `.github/review-bot/review.py`(적용), `.github/review-bot/test_review.py`(시험 25개, `python3 .github/review-bot/test_review.py`), `.github/pull_request_template.md`(부록 B), `.github/CODEOWNERS`(폴더 주인).

**동작.**
- PR을 열 때, 새 커밋을 올릴 때, 본문·라벨을 바꿀 때, 닫힌 PR을 다시 열 때 돈다(`.github/workflows/review-bot.yml`).
- 검사 코드는 PR 가지가 아니라 `main`의 것을 쓴다(`pull_request_target`). PR이 검사 코드를 고쳐 스스로 통과하지 못하게 하려는 것이다. PR의 코드는 실행하지 않고, 바뀐 내용만 GitHub API로 읽는다.
- 판정은 두 단계다.
  1. **규칙 검사**: 아래 표의 규칙을 `.github/review-bot/rules.json`에서 읽어 적용한다. 규칙을 바꿀 때는 이 표와 그 파일을 같이 고친다.
  2. **AI 비판 검토**: Claude API(Messages API, 사용자 결정 2026-10-29)가 바뀐 내용을 이 계획서의 핵심 범위(3절)와 Docker·Git 원칙에 비춰 비판적으로 읽는다. 키는 저장소 비밀 `REVIEW_AI_KEY`, 모델은 `rules.json`의 기본값(`claude-haiku-5-5`)이고 저장소 변수 `REVIEW_AI_MODEL`로 바꿀 수 있다. 지적마다 파일·문제·고칠 방법·심각도(막음·고침 권함·참고)를 적는다. "막음" 지적은 그 파일이 PR에 실제로 있을 때만 판정에 넣는다. 같은 커밋·같은 본문이면 지난 결과를 다시 쓰고 API를 부르지 않는다(비용). 키가 없거나 호출이 실패하면 "AI 검토를 하지 못했다(꺼져 있다)"고 적고 규칙 검사로만 판정한다. 통과로 꾸미지 않는다. 처음 고른 GitHub Models는 2026-07-30에 서비스가 끝나(실행에서 응답이 `OK`뿐임을 확인) 쓰지 않는다. OpenAI 호환 방식은 Claude 문서가 시험용이라고 적고 있고 `temperature` 1 미만을 거절해서 쓰지 않는다.
- **결과**:
  - 막음이 하나라도 있으면 변경 요청 리뷰를 남기고, 라벨 `리뷰봇-막음`을 붙이고, **PR을 닫고**, 검사를 실패로 둔다. 닫힌 PR은 병합할 수 없다. 워크플로 토큰은 PR을 초안으로 바꿀 권한이 없어서(2026-10-29 실행에서 "Resource not accessible by integration" 확인) 닫는 방식을 쓴다. 닫기에 실패하면 댓글에 그렇게 적는다.
  - 본문을 고치면 바로 다시 검사하고, 통과하면 봇이 PR을 다시 연다. 코드를 고쳤으면 커밋을 올린 뒤 작성자가 다시 연다(닫힌 PR에는 새 커밋 신호가 오지 않는다). 다시 열면 검사가 다시 돈다. 막음이 없으면 검사를 통과로 둔다. 결과는 PR 댓글 하나에 계속 고쳐 쓴다.
- **봇은 승인(Approve)하지 않는다.** 이 작업의 목적이 리뷰에서 설명하며 배우는 것이고(가이드 1절), 봇은 설계 의도까지 판단하지 못한다. 그래서 봇 통과는 "사람 리뷰 차례"라는 뜻이다.
- **예외**: 범위·크기·리뷰봇 자체 수정 규칙과 AI의 막음 지적은 작성자가 아닌 사람이 라벨 `리뷰봇-예외`를 붙이고, 본문에 `예외 이유:`를 적으면 경고로 바뀐다. 비밀 값·금지 파일·이슈 연결·양식 규칙은 예외가 없다.
- **한계**: 이 저장소는 무료 조직의 비공개 저장소라 브랜치 보호(필수 검사, 승인 강제)를 쓸 수 없다(2026-10-29 GitHub API 403 확인). 그래서 PR을 닫아서 막는다. 쓰기 권한이 있으면 다시 열 수 있지만, 열면 검사가 다시 돌아 다시 닫힌다. 팀장은 검사가 초록이고 사람 승인이 1회 있을 때만 병합한다.
- 비용: 비공개 저장소 Actions는 무료 조직에서 월 2,000분이다. 한 번에 1분이 안 걸린다.

| 규칙 | 내용 | 근거 | 결과 |
|---|---|---|---|
| 이슈 연결 | 본문에 `Closes #번호` 또는 `Refs #번호` | 핸드북 규칙 1 | 막음 |
| PR 양식 | "관련 이슈·변경 사항·확인한 것"이 비어 있지 않다 | 부록 B | 막음 |

## 8. 끝나는 조건

- 설계 PR이 구현 PR보다 먼저 병합돼 있다.
- 깨끗한 PC에서 `docker compose up -d` 뒤 가짜 모델로 3D 미술관 한 바퀴(가입 → 사진 → 확정 → 전시)가 된다.
- 맥에서 실제 모델(M1·M2·M5)로 한 바퀴가 된다.
- `docker compose down` 뒤 다시 `up` 해도 가족 작품이 남는다.
- 저장소에 `.env`·비밀 값·모델 가중치가 0건이다.
- 발표를 마쳤고 7절 수치와 각자 작업 기록이 있다.

## 10. 하지 않을 것

- 지난 판 평면 화면(`/app/...`의 3D 미술관 밖 화면)을 살리거나 고치기.
- 서비스 기능 바꾸기(모델 서빙 규칙·DB·API 계약). 3D 화면 연결에 꼭 필요한 것만 설계서를 먼저 고친 뒤 바꾼다.
- 3D 화면에 새 기능 더하기(연결 외).
- CI 옮기기와 이미지 자동 빌드, 레지스트리에 올리기, 태그별 되돌리기, 모니터링(Prometheus·Grafana), 장애 리허설과 운영 절차서, 백업 스크립트, 보안 점검표, GPU 이미지.
- M3·M6·M7을 실제로 컨테이너에 넣기, 카카오 로그인.
- Dockerfile·compose를 한 사람이 대신 다 만들어 주기(리뷰와 짝 작업은 좋다).
- Kubernetes 같은 묶음 운영 도구, 유료 서비스, 승인 없는 공개 배포.
- 시간이 남아도 위 항목을 다시 넣지 않는다.

## 부록 B. PR 양식

`.github/pull_request_template.md`에 들어 있다. 핸드북 양식에 "설계서"와 "확인한 것(명령과 결과)"을 더했다. 리뷰봇이 이 제목들로 칸을 찾는다.

```text
## 관련 이슈
Closes #번호

## 설계서
설계서: 계획서 3-2 / SD_04 ○절 (문서만 바꾸면 "해당 없음")

## 변경 사항
- (파일과 한 줄 설명)

## 확인한 것
- 실행한 명령과 결과(종료 코드, 수치). 이미지를 바꿨으면 크기와 빌드 시간
- 화면이 바뀌었으면 캡처

## 남은 것
- (확인하지 못한 것과 이유)

## 리뷰 요청 사항
- (리뷰어가 특히 봐 줄 곳)
```
