# 우리 아이 미술관 3인 디벨롭 판(모델 서빙 서비스를 컨테이너로 배포하기)

작성 2026-10-28. 독자는 이 저장소에서 함께 작업할 팀원 3명이다. 대상은 지난 모델 서빙 팀 프로젝트(우리 아이 미술관 팀 판, `main` 브랜치 `7c6a8ab`, 2026-09-30)다. 서비스 기능과 모듈 경계(`SD_04_아키텍처설계서_우리아이미술관.md`)는 그대로 두고, 실행·배포·운영 방식과 협업 방식만 다시 짓는다. 담당자 이름은 첫 회의에서 정해 4절 표에 적는다. 단계마다 교안의 무엇을 함께 복습하고 무엇으로 확인하는지는 `docs/공통/컨테이너배포_팀가이드.md`에 있다.

## 1. 이루려는 것

- 지난 모델 서빙 프로젝트를 Docker 컨테이너로 다시 짓고 리눅스 서버에 배포해, 실제로 띄우고 지키는 서비스로 운영한다. 누구든 같은 명령으로 같은 서비스를 띄운다.
- 팀원 3명이 직접 한다. 지금 구성을 분석하고(부록 A) 배운 원칙으로 컨테이너 구성을 설계한 뒤, 구현·시험·배포·운영까지 간다(3절). 저장소에는 미리 만든 Dockerfile·compose 파일이 없다. 그 파일은 팀이 쓴다.
- 세 사람이 같은 저장소에서 이슈 → 가지 → PR → 리뷰 → 병합 순서로 동시에 작업해도 서로의 작업을 깨지 않는다.

### 2-1. 팀 작업 전에 바탕을 정리한 것(2026-10-28)

Docker 파일은 만들지 않았다. 팀원 환경(리눅스, x86_64·arm64)에서 같은 서비스를 깔고 시험할 수 있게, 리눅스에서 막히던 곳만 고쳤다. 확인은 Debian 기반 `python:3.11` 컨테이너에서 root가 아닌 사용자로 했다. 그 컨테이너 설정은 저장소에 남기지 않았다(팀이 직접 만든다).

| 막히던 것 | 고친 것 | 확인 |
|---|---|---|
| 모델 묶음 잠금(`serving/requirements-models.lock`)이 맥 기준으로 풀려 있어, x86_64 리눅스에서 PyTorch가 요구하는 CUDA 패키지(`nvidia-*`)가 잠금에 없어 설치가 멈춘다 | x86_64 리눅스용 잠금 `serving/requirements-models-linux-x86_64.lock`. 맥 잠금과 버전이 모두 같고 PyTorch·torchvision만 CPU 전용(`+cpu`)이다. CUDA 패키지 0개 | 고치기 전: arm64 리눅스는 설치 풀기 통과, x86_64는 해시 없음으로 실패. 고친 뒤 x86_64(흉내 실행): 설치 종료 0, CUDA 패키지 0개, `torch 2.4.1+cpu`, 가상환경 1.5GB, 서빙 시험 145개 통과·5개 건너뜀(arm64와 같다) |
| 서빙 시험이 MariaDB 실행 파일을 맥 경로(`/opt/homebrew/bin`) 한 곳에서만 찾는다. CI는 `/usr/sbin` 한 폴더만 넘겨 Debian에서는 깨진다 | 시험 설정이 PATH·`/usr/sbin`·`/usr/bin`에서 찾는다(`MARIADB_BIN`을 주면 그 폴더). CI의 넘김을 뺐다 | arm64 리눅스: 서빙 시험 140개 통과·9개 건너뜀(가짜 모델용 기본 잠금만), 145개 통과·5개 건너뜀(모델 묶음까지). `caption` 시험 26개 통과 |
| 기본 잠금만 깐 환경에서 numpy를 쓰는 시험 때문에 시험이 모이지도 않는다(맥 개발 환경은 모델 묶음까지 깔려 있어 가려졌다) | numpy·scipy가 없으면 그 시험만 건너뛴다 | 같은 실행 |
| 서빙 안내 문서가 맥 설치만 적었다 | `serving/README.md`에 플랫폼별 잠금 표와 리눅스 시험 방법 | 없음 |

손대지 않은 것: TorchServe(M3) 환경 목록 `serving/conda-m3.lock`은 맥(osx-arm64) 전용 그대로다(7절 결정). 실행 환경 지문 계산(`serving/ops/models.py` 173~175행)은 맥 잠금을 재료로 쓰는 그대로다(3절 데이터·배포 질문).

## 3. 진행 방식: 분석 → 설계 → 구현 → 시험 → 배포 → 운영

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 0 바탕 | 팀 저장소와 협업 규칙, 각자 개발 환경 | 팀 저장소, PR 양식(부록 B), 환경 확인 기록 |
| 1 분석 | 지금 구성을 직접 띄우거나 읽어 부록 A의 "확인할 것"에 답한다. 실행 명령, 포트, 설정 값, 데이터 위치, 메모리, 기동 순서를 실제 값으로 적는다 | 부록 A를 채운 분석 기록(누가, 어떤 명령으로 확인했는지) |
| 2 설계 | 아래 질문에 답하는 컨테이너 구성을 설계서에 쓴다. 지금 pm2 배치를 적은 곳을 모두 고친다: SD_04(1-1 배치 칸, 4-1·4-2 기술 층과 자원·내부망 배치 표, 4-3 배치), `.specify/…/plan.md`(40·76~77·87·196~197행)·`research.md`(R-02)·`quickstart.md`의 "Docker 없음" 결정, DEPLOY. 저장소 `CLAUDE.md`의 기술 컨텍스트 표는 `update-agent-context.sh`가 만드는 관리 블록이라 직접 고치지 않고 다시 만든다. 구현 PR보다 설계 PR을 먼저 병합한다(저장소 `CLAUDE.md` 절대 규정) | 설계 PR 하나(셋이 모두 리뷰) |
| 3 구현 | 역할마다 자기 영역의 이미지를 만들고(4절), 역할 3이 compose로 묶는다 | 이미지·compose·CI PR |
| 4 시험 | 컨테이너 안에서 기존 시험(검사 4종, `web/e2e`)과 상태 확인이 통과하는지 본다. 깨끗한 컴퓨터에서 처음부터 띄워 본다 | 시험 기록 |
| 5 배포 | 리눅스 서버에 이미지를 받아 띄우고, 한 판 전으로 되돌려 본다 | 배포 기록, DEPLOY 개정 |
| 6 운영 | 백업·복원, 장애 상황 대응, 로그 보기를 실제로 해 보고 운영 절차서로 남긴다 | 운영 절차서, 리허설 기록 |

2단계 설계서가 답해야 할 질문:
- **서비스 나누기.** 한 컨테이너에 한 가지 일을 둔다면 무엇이 몇 개인가. app-api와 sweeper처럼 같은 빌드를 쓰는 둘은 이미지 하나를 나눠 쓰는가.
- **이미지.** 기반 이미지와 버전은 무엇인가(CI가 쓰는 `node:22`·`python:3.11`과 맞출지). 빌드 단계와 실행 단계를 나누면 크기가 얼마나 줄어드는가. 소스만 바꿨을 때 의존성 설치를 다시 하지 않게 순서를 짰는가. 빌드에 넣지 않을 파일(`node_modules`, `.env`, 모델 가중치, 시험 결과물)은 무엇인가. 크기와 빌드 시간을 처음 잰 값으로 적고 목표를 정한다.
- **CPU 종류.** 팀원과 서버의 CPU가 x86_64와 arm64로 섞이면 이미지는 어느 쪽으로 만드는가(한쪽만, 또는 둘 다). 모델 라이브러리(PyTorch, TorchServe)가 두 종류에서 같은 버전으로 설치되는가.
- **메모리.** M1 추론 중 메모리 8.5GB(매니페스트 기록)는 메모리 8GB 가상머신보다 크다. 가짜 모델(`UAM_FAKE_MODELS`)로 먼저 띄울지, 서버 메모리를 늘릴지, 모델 작업자에 한도를 얼마로 둘지 정한다.
- **GPU.** 애플 GPU를 쓰던 모델(M2·M5·M6·M7)은 리눅스 컨테이너에서 무엇으로 도는가. Docker Desktop 공식 문서의 컨테이너 GPU 사용은 Windows(WSL 2)와 NVIDIA GPU만 적는다(2026-10-28 확인, docs.docker.com/desktop/features/gpu). CPU로 돌 때 걸리는 시간을 재고, NVIDIA GPU가 있는 팀원·서버가 있으면 GPU 이미지를 선택으로 둔다.
- **M3(움직임).** worker-cpu가 관절은 TorchServe에 묻고, 렌더는 `serving/.venv-m3`의 파이썬으로 하위 프로세스를 띄워 OSMesa로 그린다. 이때 맥 전용 `DYLD_FALLBACK_LIBRARY_PATH`를 넘긴다(`serving/adapters/m3_render.py` 6~7행). 리눅스 컨테이너에서는 이 렌더를 어떻게 돌리는가(또는 M3를 가짜로 두는가, 7절).
- **데이터.** 컨테이너를 지워도 남아야 하는 것(DB 자료, 가족 작품 파일, 모델 가중치)은 어디에 두는가. 모델 가중치와 M3 모델 묶음(`.mar`)은 저장소에 없다(`.gitignore`, `models/README.md`). 어디서 받아 어디에 두는가. 가중치는 이미지에 넣는가, 읽기 전용으로 붙이는가. model-api와 작업자는 상태 폴더(`UAM_RUN_DIR`, 기본 `serving/.run`)를 함께 쓴다. 다른 컨테이너로 나누면 이 폴더를 어떻게 함께 붙이는가. DB 백업과 복원은 어떤 명령으로 하고, 복원이 되는지 어떻게 확인하는가.
- **네트워크와 입구.** 바깥에 여는 포트는 몇 개인가(지금은 nginx 9501 하나). 서비스끼리는 이름으로 찾는가. app-api(`api/src/server.ts` 14행)와 model-api(`serving/model_api/main.py` 8행)는 127.0.0.1에 묶여 있고 이 주소가 코드에 고정돼 있다. 다른 컨테이너에서 부르려면 먼저 이 주소를 설정 값으로 바꿔야 한다(설계서 먼저). 입구는 공유 nginx가 보낸 실제 접속 IP를 앱에 넘긴다(요청 한도). app-api는 루프백에서 온 프록시만 믿는다(`api/src/app.ts` 24행). 컨테이너 사이에서 이 신뢰를 어떻게 다시 정하는가. 호스트의 공유 서비스(Ollama)는 컨테이너에서 어떻게 부르는가.
- **설정과 비밀.** 환경마다 바뀌는 값(개발·서버)은 어떻게 나누는가. 지금은 pm2 설정이 `.env`를 읽어 넣는다. 컨테이너에서는 무엇이 넣는가. 비밀 값(`DB_PASSWORD`, `SESSION_SECRET`, `AUTH_HMAC_SECRET`, `KAKAO_REST_API_KEY`·`KAKAO_CLIENT_SECRET`, 시험 호출 키 `API_GUIDE_TEST_KEY`)이 이미지와 저장소에 들어가지 않게 어떻게 넘기는가. 팀 서버는 메일을 보내지 않는다(`MAIL_ENABLED=false`, R-23 결정 갱신 2).
- **상태 확인과 기동 순서.** 서비스마다 "준비됨"을 무엇으로 판단하는가(app-api `/live`·`/ready` 등). DB가 준비되기 전에 api가 떴다 죽는 일을 어떻게 막는가. 죽으면 다시 뜨는 규칙은 무엇인가.
- **보안과 자원.** 컨테이너를 root가 아닌 사용자로 돌리는가. 쓰기가 필요 없는 곳을 읽기 전용으로 두는가. 필요 없는 권한을 빼는가.
- **배포와 되돌리기.** 이미지 이름과 태그 규칙은 무엇인가(모든 빌드와 출시를 구분). 어느 레지스트리에 언제 올리는가. 서버는 무엇을 받아 띄우고, 한 판 전으로 되돌리는 명령은 무엇이며 얼마나 걸리는가.
- **운영.** 로그는 어디서 보는가. 한 서비스가 죽을 때, DB가 늦게 뜰 때, 메모리가 넘칠 때 각각 무엇을 보고 어떻게 되살리는가.

## 4. 역할 분담

세 사람이 모두 컨테이너를 직접 만든다. 각자 자기 영역의 이미지를 맡고, 역할 3이 전체를 묶어 배포한다.

|---|---|---|---|---|---|
| 1. 입구·화면 | `web/`, `ops/p1/nginx.conf`(지금 쓰는 입구), `ops/server/nginx.conf`(단독 서버 견본) | 웹 이미지(팀 판 `npm run build` 결과와 배포 확인용 `version.json`을 입구 nginx에 담기), nginx 라우팅을 서비스 이름 기준으로, 실제 접속 IP 넘기기, 바깥 포트, 화면 흐름 시험(`web/e2e`)이 컨테이너 묶음을 대상으로 돌게 | 2의 API 주소를 받아 쓴다. 3의 compose에 웹·입구 서비스가 들어간다 | 역할 2 | (첫 회의) |

- 리뷰는 1→2→3→1로 돈다. 자기 역할의 PR을 자기가 합치지 않는다.
- 설계 판단과 통합 책임은 셋 중 한 명이 겸한다(첫 회의에서 정한다). 설계서를 고치는 PR은 통합 책임자가 리뷰에 들어간다.
- 모든 작업은 "설계서 수정 → 구현 → 결과가 달라지면 설계서 다시 맞춤" 순서다.

## 6. 끝나는 조건

- 부록 A 분석 기록과 컨테이너 구성 설계(SD_04·DEPLOY)가 구현 PR보다 먼저 병합돼 있다.
- Docker만 설치한 깨끗한 컴퓨터에서 저장소 받기 → `.env` 채우기 → compose로 띄우기 뒤 모든 서비스가 healthy다(가짜 모델). 걸린 시간을 처음 잰 값으로 기준을 정한다. 실제 모델은 가중치를 받은 뒤 M1부터 같은 방법으로 확인한다.
- 리눅스 서버에 배포한 서비스에서 가입부터 작품 전시까지 한 바퀴가 된다. 한 판 전으로 되돌리기가 된다.
- PR마다 검사 4종(DB 시험이 실제로 도는 것 포함)과 이미지 빌드가 돈다. main 직접 push 0건, 병합된 PR마다 리뷰 1건 이상.
- 저장소와 이미지에 비밀 값이 0건이다(검사 명령과 결과를 남긴다).
- 운영 리허설(백업·복원, 장애 3가지) 기록과 운영 절차서가 있다.

## 8. 하지 않을 것

- Dockerfile·compose·CI 이미지 빌드를 미리 만들어 두기(팀이 직접 한다).
- 서비스 기능 바꾸기, SD_04에 없는 모듈 새로 만들기.
- Kubernetes 같은 묶음 운영 도구, 승인 없는 공개 배포, 유료 서비스.
- GPU를 기본으로 요구하기. 기본은 CPU로 돌고 GPU는 선택이다.
